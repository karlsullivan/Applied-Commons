Cross-platform, open-source desktop (and, via companion apps, mobile) GIS engine: view, edit, analyze and print vector/raster/mesh/point-cloud data in dozens of formats and consume WMS/WFS web services; integrates GDAL, PostGIS, GRASS, SAGA and MapServer and a large Python/C++ plugin ecosystem. This is the de-facto open standard and the general-purpose engine that hosts the other candidates (InaSAFE is a QGIS plugin; Mergin syncs QGIS projects). Who it helps: governments, NGOs, researchers and local GIS staff needing a free, locally-owned mapping/analysis platform instead of proprietary GIS. Maturity: in development since 2002, current stable 4.2.3, GPL-2.0+, ~14.8k GitHub stars, very high activity (pushed on the retrieval date). General-purpose (not cold-climate-specific), but fully offline-capable.

Assembly

Tools: apt / dnf (Debian/Ubuntu/Fedora package manager), gnupg (GPG repository-key handling), Apache 2 + libapache2-mod-fcgid, or NGINX + spawn-fcgi / fcgiwrap, systemd (service enablement), curl / a web browser (verifying OGC endpoints), QGIS Desktop (authoring/styling the served project), Docker + Docker Compose (optional self-hosted QFieldCloud leg), PostgreSQL / PostGIS (optional QFieldCloud sync database), git (optional: source builds or configuration management)
Skills: Linux system administration (Debian/Ubuntu), HTTP-server and reverse-proxy configuration (Apache/NGINX, TLS, auth), systemd service management, QGIS project design (styling layers, setting OGC WMS/WFS capabilities), OGC WMS / WFS concepts, Basic SQL / PostGIS (optional sync database)
Time: Core single QGIS Server node (Apache, one project, verified via GetCapabilities and GetMap): roughly 1-3 hours. Add 30-60 min for the QGIS Desktop companion install. Adding the self-hosted QFieldCloud (Docker + PostGIS) sync backend and provisioning field devices adds roughly 0.5-1 day.

  1. 1. Provision the host (the BOM) Create a Debian 12 (bookworm) or Ubuntu 24.04 (noble) / 22.04 (jammy) VM or bare-metal Linux box; these codenames appear in QGIS's supported-distributions table. Suggested minimum (an assumption, NOT an upstream number): 2 vCPU, 4 GB RAM, 40-80 GB disk, an SSH-accessible address, and an OS codename from the table. Software licensing cost is $0 (GPL-2.0+). Source: qgis.org
    Caution: N/A (software). Keep the box on a private network or behind a firewall until TLS and authentication are in place (see steps 6-7).
  2. 2. Add the official QGIS apt repository and GPG key On Debian/Ubuntu: 'sudo apt install gnupg software-properties-common'; fetch the signing key to /etc/apt/keyrings/qgis-archive-keyring.gpg (wget -O ... download.qgis.org); write /etc/apt/sources.list.d/qgis.sources with URIs qgis.org, Suites=<your-codename>, Components: main, Signed-By /etc/apt/keyrings/qgis-archive-keyring.gpg; then 'sudo apt update'. Source: qgis.org
    Caution: Verify the GPG key fingerprint before trusting the repo. The guide's expected key is rsa4096 'QGIS Archive Automatic Signing Key (2022-2027) <qgis-developer@lists.osgeo.org>', id 2D7E3441A707FDB3E7059441D155B8E6A419C5BE; match it before installing.
  3. 3. Install QGIS Server Install the headless server: 'sudo apt install qgis-server' (the install guide says to add qgis-server to the apt install line; use --no-install-recommends for a minimal headless install). The package installs the FastCGI binary at /usr/lib/cgi-bin/qgis_mapserv.fcgi - confirm its location with 'locate qgis_mapserv.fcgi'. Source: qgis.org
    Caution: N/A (software). Avoid installing client and server on the same shared workstation (the install guide flags this as not common practice).
  4. 4. (Optional) Install QGIS Desktop to author the project On a machine used to design/style layers: 'sudo apt install qgis qgis-plugin-grass'. This is where you create the .qgs/.qgz project that QGIS Server will serve. Source: qgis.org
    Caution: N/A (software).
  5. 5. Sanity-check the FCGI binary Run '/usr/lib/cgi-bin/qgis_mapserv.fcgi' in a terminal. A correct install prints 'Loading native module' lines (libwms, libwfs, libwfs3, libwmts, libwcs, liblandingpage, libdummy) followed by 'Server: QGIS FCGI server - QGIS version <ver>'. A 'Status: 400' here ('Bad request error' / 'Service unknown or unsupported') is EXPECTED - the guide states it is not a bug and shows the server binary is functioning, because there is no active HTTP session. Source: docs.qgis.org
    Caution: N/A (software). The 'Unable to find driver ECW / JP2ECW to unload from GDAL_SKIP' warnings are benign (proprietary drivers).
  6. 6. Install an HTTP server in front of the FCGI binary Recommended: Apache ('apt install apache2 libapache2-mod-fcgid') or NGINX ('apt install nginx' plus a FastCGI wrapper such as spawn-fcgi, or 'apt install fcgiwrap'). Source: docs.qgis.org
    Caution: Do not expose the service to the internet on port 80 without TLS and authentication; QGIS Server has no built-in end-user auth (see gaps). Use a reverse proxy with TLS + auth, or keep it on an internal network.
  7. 7. Configure the virtual host / FastCGI block with QGIS env vars Apache: create a VirtualHost setting FcgidInitialEnv for locale (LANG/LC_ALL=en_US.UTF-8), QGIS_SERVER_LOG_STDERR=1, QGIS_SERVER_LOG_LEVEL=0, SetEnv QGIS_PROJECT_FILE=/home/qgis/projects/world.qgs, and QGIS_AUTH_DB_DIR_PATH to a directory writable by the FCGI user. NGINX: a location block with fastcgi_param for the same env vars and fastcgi_pass to the socket, with the binary launched via spawn-fcgi. Source: docs.qgis.org
    Caution: Keep DB credentials in QGIS_AUTH_DB_DIR_PATH with restrictive permissions (e.g. 0600) owned by the FCGI user; never hard-code passwords in the web-server config.
  8. 8. Build and point to a QGIS project In QGIS Desktop, load your open layers (GeoPackage / SpatiaLite / PostGIS / OSM-derived basemap, WASH point data), style them, set the project CRS, then open Project > Properties > QGIS Server tab to fill in the WMS/WFS/WCS capabilities and enable the services you want. Save the project as the .qgs/.qgz referenced by QGIS_PROJECT_FILE. Source: docs.qgis.org
    Caution: N/A (software). Ensure the project file and its underlying data are readable by the FCGI process user.
  9. 9. (Headless rendering) Provide Xvfb if needed If the server must render on a headless box, install Xvfb so QGIS has a virtual display (Xvfb is installed under 'Installation on Debian-based systems' in the Server manual, alongside QGIS Server). Source: docs.qgis.org
    Caution: N/A (software).
  10. 10. Enable and start the service Create/enable a systemd unit (e.g. /etc/systemd/system/qgis-server.service with ExecStart=spawn-fcgi -s /var/run/qgisserver.socket -U www-data -G www-data -n /usr/lib/cgi-bin/qgis_mapserv.fcgi), then 'systemctl enable --now qgis-server'. Source: docs.qgis.org
    Caution: N/A (software). Confirm the unit runs as the non-root www-data user.
  11. 11. TEST: verify the running instance After enabling the vhost/site and restarting Apache, point the name at the server (add '127.0.0.1 <your-host>' to /etc/hosts) and check the guide's literal example: GET <host> in a browser and expect an XML WMS capabilities document; the QGIS Server landing page should also appear. A GetMap request (REQUEST=GetMap with BBOX/CRS/WIDTH/HEIGHT/LAYERS) returns a map image. Source: docs.qgis.org
    Caution: N/A (software). Do this while the service is still on an internal/private network or behind TLS+auth before exposing it.
  12. 12. (Optional, field-collection leg) Self-host QFieldCloud Deploy the open-source QFieldCloud backend (a Django service) with Docker + Docker Compose ('docker compose up -d --build'). It needs an external PostgreSQL/PostGIS database (the only supported way) plus object storage - either the bundled 'rustfs' S3-compatible store or an external S3 provider with versioning. Copy .env.example to .env and set the POSTGRES_* and STORAGE_* variables. Create a superuser ('manage.py createsuperuser') and add your QGIS project as a QFieldCloud project. Source: raw.githubusercontent.com
    Caution: Run it behind the nginx reverse proxy with SSL (the guide advises avoiding Django's built-in dev server for this) and set DJANGO_ALLOWED_HOSTS / QFIELDCLOUD_HOST to your real host. Restrict the PostGIS database to the compose network and use strong credentials - do not reuse the sample password shown in the README.
  13. 13. TEST: verify QFieldCloud Use the documented healthcheck: 'curl <host>; and confirm the 'database' and 'storage' keys both report 'ok' status. If it fails, inspect the nginx and app logs ('docker compose logs nginx app'). Source: raw.githubusercontent.com
    Caution: N/A (software). Verify over the nginx/SSL route, not the Django dev server on :8011.
  14. 14. (Optional) Connect QField on a device Install the QField app on an Android phone/tablet; at sign-in, enter your self-hosted QFieldCloud server URL to reach the instance, then download the project for offline use (the backend provides online-offline work with change tracking between QGIS (+ QFieldSync plugin) and QField). Source: raw.githubusercontent.com
    Caution: N/A (software). Device minimum-hardware is not specified in the retrieved sources - see gaps.
  15. 15. (Alternative sync) Mergin Maps (commercial) If a managed sync server is preferred over self-hosting QFieldCloud, Mergin Maps server is a commercial option that syncs QGIS/QField projects; on-prem/hosted pricing is not published in the retrieved doc (contact sales). Source: merginmaps.com
    Caution: N/A (commercial hosted/on-prem service).

Failure modes

FailureEffectMitigation
QField app update wipes local, unsynced projectsAll local projects and app-folder contents emptied after an update, losing up to 10 days of unsynced field data (reported on Android 13 / Galaxy S20 after a 4.3.3 update).Treat the server/GeoPackage as the source of truth: sync frequently and keep an off-device copy of the GeoPackage before every app update or re-package.
Older hardware/OS cannot run current QFieldDevices on very old Android (e.g. 6.0) are stuck on an old QField (1.x) while newer projects require a newer QField; projects can fail to open or run slowly on weak/older hardware (device-compatibility questions on StackExchange and the QField forum, incl. an old Intel/x86 tablet note, show this is a recurring field complaint).Standardize on a known QField-ready device (ARM tablet/phone, adequate RAM) from the QField-ready device list; test the exact device+OS combo with the target project before deployment, not in the field.
Self-hosted sync server misconfiguredQFieldCloud/Mergin fails its own health check: missing base URL, missing contact email, uninitialized DB, or data-folder permission errors; sync silently breaks for field devices.Run the documented health check (QFieldCloud /api/v1/status/ ; Mergin 'flask server check') and fix each reported error before hand-out; keep DB and storage on persistent, backed-up volumes.
QFieldCloud upgrade path skippedUpgrading from < v26.22 (or without backfill_project_details) to a newer version can lose project metadata.Follow the release-note upgrade order: v26.29 -> run backfill_project_details -> then newer versions; take a DB backup first.
Data staleness (pipeline not re-run)Organizations that collect once and stop updating end up with data too old years later, forcing re-collection (observed across African agencies).Make the update pipeline part of operations, not a one-off: schedule re-runs and track freshness/completeness of the dataset over time.
CRS / layer mismatch in analysisHazard + exposure + WASH layers in different CRS/units produce an analysis model that errors or yields silently wrong statistics.Reproject all layers to one project CRS before running the model; sanity-check output on a sample region against a known-correct reference.
Low-power / connectivity limits in fieldCollection or transfer stalls where broadband is unreliable or power fails; cloud-only GIS is unusable.Run the whole collect->edit->package loop offline; reserve the network only for the sync-back step; use low-power, field-replaceable hardware and chargeable devices.

Known gaps

What the original design does not document:

  • QGIS and QField publish no official hardware minimums (confirmed via the community thread and StackExchange answer); the workstation spec above is a practitioner recommendation, not a documented requirement.
  • No retrieved source gives a retail unit price for the Samsung Galaxy Tab Active5, the Happy Mini Q GNSS receiver, or the QGIS workstation - unit_cost left null rather than guessed.
  • QFieldCloud self-hosting docs point to the upstream README for CPU/RAM/OS specifics without stating fixed numbers, so the server spec is a practical minimum, not an upstream-published one.
  • Mergin Maps CE (open source) is a documented alternative sync backend, but its exact self-host server sizing was not pinned from a retrieved page this run.
  • InaSAFE is included as the MHEWS 'risk knowledge' layer the need brief names, but it is a separate project (GPL v3, github.com/inasafe/inasafe) rather than part of the QGIS/QField build; its upstream BOM was not indexed.
  • Cost basis is list price only; bulk/education/NGO discounts (e.g. QFieldCloud free NGO plan up to EUR30k revenue, Academic EUR25/mo) and local procurement/taxes are not included.
  • No upstream hardware sizing for a production self-hosted deployment: QFieldCloud's README states the standalone single-server setup is 'entirely at your own risk' and its official docs point back at the repo, but no repo or doc states CPU/RAM/storage minimums; Mergin likewise documents install steps without sizing. Any BOM hardware figures are engineering estimates, not upstream-specified.
  • QGIS Server has no documented concurrent-rendering capacity guidance (workers, FastCGI sizing, RAM per active map); INSTALL.md covers build flags (WITH_SERVER, FastCGI) but not sizing.
  • Mergin Maps dual licensing (AGPL-3.0 vs MerginMaps Commercial) is stated in README/LICENSES but the commercial licence terms and pricing are not published in the repo; AGPL's network-use obligations are not explained for deployers.
  • No unified reference deployment exists combining QGIS Server + a sync backend (QFieldCloud or Mergin) + InaSAFE in one documented architecture; each project documents its own deployment independently.
  • InaSAFE is only documented as a QGIS desktop plugin (plugin manager install); there is no server-side or headless deployment path upstream (its docker-compose.yml in-repo is a QGIS test environment, not a deployment).
  • Offline geodata sources (basemaps, DEMs, projection grids) are referenced (e.g. projsync for PROJ grids, QGIS OGC services) but no upstream bill-of-materials for offline data downloads with sizes/costs is provided.
  • QField mobile app hardware requirements (supported device tiers, minimum Android version) are not stated in the repo README/docs index; docs index only points to app-store downloads.
  • QFieldSync upstream licence inconsistency: the README says 'GPLv3 or later' but the in-repo LICENSE file is GNU Lesser GPL v3 (LGPL-3.0); this pack carries the LICENSE file (LGPL-3.0) as authoritative.
  • No minimum/recommended hardware spec (CPU/RAM/disk, or OS version beyond codename) for QGIS Server in the retrieved official docs; the VM sizing in step 1 is an assumption, not an upstream number. The two retrieved community hardware threads are stale user Q&A, not an official spec.
  • QGIS Server has no built-in end-user authentication; the Getting Started guide documents only environment variables plus a DB-auth directory, not how to secure a public endpoint (TLS + authn/authz must be added in front). Not documented for this section.
  • No published cost for self-hosted infrastructure, and Mergin Maps on-prem/hosted pricing is not in the retrieved doc (contact sales) - so the BOM cost column is $0 software plus unquantified hosting.
  • QField: no official minimum device spec in the retrieved sources (the 'system requirements' thread is a user Q&A, and the StackExchange thread is a 2020 ARMv7-era question). Field-device sizing is not documented.
  • The dedicated QGIS Server 'installation.html' page returned an http_error on retrieval; the install steps for this section come from the Debian-based section of the Getting Started guide plus the main install guide.
  • Windows QGIS Server deployment is listed in the Getting Started table of contents but was not fully retrieved; only the Debian/NGINX/Xvfb server steps are documented here.
  • Offline operation of the server itself is not documented (it needs a network); the offline capability for the need brief comes from QField plus local GeoPackage/SpatiaLite, not the server.
  • No high-availability / multi-node / load-balancing guidance in the Getting Started guide; this deployment is single-node.
  • No upstream published acceptance test that ties a running QGIS/QField install to a specific humanitarian use case (village basemaps, post-disaster damage mapping, WASH point data) - the R1-R7 criteria above must be authored and run locally; results are deployment-specific, so no third-party target numbers exist.
  • QField/QFieldCloud docs document how to install, package, and health-check, but not a repeatable end-to-end 'verify a finished deployment' checklist or CI-style regression test a district could run unattended.
  • No documented benchmark for the 'within hours of onset' damage-mapping SLA (R4) - the time-to-usable-map must be measured per deployment, not taken from upstream.
  • Upstream does not publish dataset freshness/completeness SLAs or a standard data-quality report (uniqueness, missing-geometry rate, staleness) for the WASH/village layers; those metrics must be defined locally.
  • QField hardware list documents 'ready' devices but not per-device pass/fail against a target project size (layer count/size); a device+project-size compatibility test must be run per deployment.
  • Local-language / low-literacy form quality (R6) is a feature to configure, not a tested property; no upstream test verifies legibility or comprehension for a specific community/language.

Safety

Software + COTS hardware only. No gas, pressure, structural, chemical, water-food or biological-medical hazard. Two low-severity physical hazards (village charging, Li-Po battery) are not covered by the pack and need the controls below; the operational hazards the pack already lists (data loss, privacy, server credentials, DB upgrade) are covered.

HazardSeverityControls
Charging the COTS field tablet and GNSS receiver from village mains/USB; the pack documents no charging infrastructure, so an untrained builder could use an unapproved charger or a faulty outlet.lowCharge only with the vendor-supplied USB-C/battery charger and cable; Charge on a circuit with RCD/GFCI protection; no improvised adapters or wall-tap wiring; Do not charge a device whose battery, cable or case is damaged
Removable Li-Po 5050 mAh cell (Samsung Galaxy Tab Active5) and the GNSS receiver's internal Li-ion cell can heat/vent/ignite if punctured, crushed, or left in hot tropical/arid conditions (the pack lists tropical and arid climates).lowNever puncture, crush, or bend the battery; keep it out of direct sun and hot vehicles; Swap to a fresh spare cell in the field; retire visibly swollen or damaged cells as hazardous waste (do not bin); Comply with UN 38.3 for any transport/shipping of spare cells
RF emissions from the field devices: GNSS (GPS/GLONASS/BDS/GALILEO receive), cellular LTE/5G, Wi-Fi, Bluetooth 5.3. Measured SAR 0.53 W/kg (head) / 0.90 W/kg (body) on the Tab Active5 - below the 2.0 W/kg limit. Cellular operation is on a licensed network; GNSS reception is unlicensed.lowUse only QField-Certified COTS devices (pack already does) so RF exposure and cellular band allocation are pre-assessed by the vendor; Register the cellular device with a local operator for band licensing; no user-controlled RF transmitter is built
Loss of unsynced field data: a QField app update (or reinstall) can empty the local projects folder - documented reports include 10 days of unsynced field data lost on Android 13 / Galaxy S20 after a 4.3.3 update, and repeated reports on iOS and GitHub #6603.mediumTreat the server/GeoPackage as the source of truth: sync frequently; Copy the GeoPackage off the device before every app update or re-package
Privacy: field-collected point data can reveal sensitive locations (at-risk facilities, community members) in openly distributed GeoPackages or on the sync server.mediumApply access control on the sync server; Keep raw PII and sensitive locations out of openly distributed GeoPackages
Server credential and exposure risk: QFieldCloud's README ships a sample Postgres password with sslmode=disable, and QGIS Server has no built-in end-user authentication, so a misconfigured public endpoint is reachable/unauthenticated.mediumSet strong, unique Postgres/QFieldCloud credentials; never reuse the README sample password; Place nginx + TLS + authentication in front; keep the DB on a private network; restrict exposed ports to intended services
Data loss on QFieldCloud upgrade/migration: the README states 'migration to a newer database version is a risky operation to your data, so prepare and test the backup of the postgres_data volume' and skipping the documented upgrade path can lose project metadata.mediumTake a tested backup of the postgres_data volume before any upgrade; Follow the documented upgrade path (e.g. upgrade to the required version, run backfill_project_details, then continue)

Evidence

The strongest findings from Applied Commons research on this project:

  • Software cost is $0 and unlimited: QField is free open-source (MIT) with unlimited users, and reads QGIS projects directly, so there is no per-seat or per-feature license cost for the field app.
  • Multilingual support is a first-class, low-effort lever: QField auto-loads .qm Qt translation files per device locale and translates layer names, field aliases, value maps, and project metadata — this is the primary low-literacy / non-English accessibility mechanism and requires no code, only a translated .qm file shipped with the project.
  • Both open-source sync backends are free to self-host with unlimited users/projects/history: QFieldCloud CE (production-ready Django service) and Mergin Maps CE; the vendors monetize the hosted/managed front end, not the code.
  • QFieldCloud self-hosted is a production-ready open-source (MIT) Django backend that requires an external PostgreSQL/PostGIS database and exposes a full REST API; self-hosting gives full data-residency and user-management control but you own the operations.
  • QGIS publishes no formal CPU/RAM/storage minimums; the official installation guide lists only supported platforms (Windows, macOS, Linux, FreeBSD, OpenBSD, Android, iOS) and recommends LTR installers.
  • QField publishes no numeric hardware spec; validation is per-device via a three-tier program (QField Certified / QField Native RTK / Works with QField). Certified tier examples: Samsung Galaxy Tab Active 5 (Exynos 1380 octa-core, expandable storage to 1 TB microSD), Samsung XCover 7 (MIL-STD-810H, octa-core, 6 GB RAM), Happy MiniQ GNSS.
  • Tab Active 5 detailed specs: 6/8 GB RAM, 128/256 GB + microSD, Exynos 1380 (4x2.4 GHz Cortex-A78 + 4x2.0 GHz Cortex-A55), 5050 mAh Li-Po REMOVABLE battery, MIL-STD-810H (1.8 m drop), IP68, Android 14, ~700 EUR (Jan 2024), sold as a business/rugged tablet.
  • QField operates fully offline: projects transfer via local/cable transfer without network, so loss of connectivity/sync-server power does not interrupt field collection. QField is available on Android, iOS, macOS, Windows, Linux.
