The long-standing open-source (BSD-2-Clause) plain-text double-entry accounting engine by John Wiegley. Ledgers are plain text files, so the books are fully offline, readable in any language, auditable, and re-runnable/idempotent: re-posting the same entries never double-counts, which is exactly the correction-safety the brief demands of group/co-op ledgers. It is a dependency-free command-line tool, cheap, and locally maintainable; it is a computational engine (no UI), so a local-language front end or an app like a cooperative ledger would be built on top of it. Chosen because it directly satisfies the 're-runnable double-entry, runnable on one device without a cloud' requirement.

Assembly

Tools: curl (HTTPS fetch of .deb and Packages index), dpkg-deb (rootless .deb extraction, no apt/dpkg install), sha256sum (hash verification against distro index), ldd / /usr/bin/ld.so --library-path (shared-library staging and launch), python3 (JSON validation of this result object)
Skills: Rootless .deb deployment: extract with dpkg-deb and stage shared libraries instead of apt install (no root), Hash-verifying distro artifacts against the official Packages index before running anything, Resolving the merged-usr dynamic linker path (/usr/bin/ld.so) for a --library-path launcher wrapper, Authoring a balanced double-entry journal to prove re-runnable, idempotent accounting
Time: 15-30 minutes end to end on a host with outbound HTTPS: fetch+verify the .deb and 3 boost deps, extract, stage libs, write the wrapper, and run the verification suite. One-time; a second unit on the same host is a few minutes (debs already cached).

  1. 1. Obtain the ledger artifact Download the official Ubuntu resolute pool .deb over HTTPS: au.archive.ubuntu.com (2,097,260 bytes). The pool path, version and Depends are documented at packages.ubuntu.com (universe, 3.4.0-1build2).
    Caution: Do not run the binary from an unverified artifact; the next step pins its hash.
  2. 2. Verify the artifact against the distro index Fetch au.archive.ubuntu.com, extract the ledger stanza, and compare its SHA256 to sha256sum of the downloaded .deb. Observed match: 4842d1c7aaa2bb8b1a00c687a353441622f39d7ca0e6a243a4a17a2da03c6558.
    Caution: Abort if the hash does not match the index; a mismatch means a tampered or stale artifact.
  3. 3. Resolve shared-library dependencies rootlessly ledger 3.4.0-1build2 depends on libboost-filesystem/iostreams/python 1.90.0, libgmp10, libmpfr6, libpython3.14, libc6, libgcc-s1, libstdc++6 (from the index Depends line). On this host only gmp/mpfr/libpython3.14/c6/gcc-s1/stdc++6 were present; the three boost 1.90 runtimes (main component) were fetched over HTTPS and hash-verified against the resolute main Packages index (3f78b71b..., f2b4576e..., 5473d273...). ldd showed only libledger.so.3 (inside the ledger .deb) and libboost_filesystem as 'not found'; iostreams/python are dlopen'd only when the optional Python bridge is used.
    Caution: Hash-verify each dependency .deb against the same Packages index before extracting; do not mix untrusted libraries into the launch path.
  4. 4. Extract and stage the runtime (no root) dpkg-deb -x the ledger .deb and each boost .deb into a local tree, then copy the needed shared objects (libledger.so.3 from usr/lib/ledger/, libboost_filesystem/iostreams/python314 .so.1.90.0) into a single ./lib directory. ldd with --library-path against ./lib resolves with no 'not found'.
    Caution: Keep the extracted tree inside the working directory; do not copy into system paths (requires root and defeats the offline/re-runnable guarantee).
  5. 5. Launch via a static library-path wrapper Write a one-line launcher that execs the system dynamic linker on the extracted binary: exec /usr/bin/ld.so --library-path "$LIBS" "$BIN" "$@" (the host is merged-usr, so the interpreter is /usr/bin/ld.so, not /lib64/ld-linux-x86-64.so.2). This avoids LD_LIBRARY_PATH and any root.
    Caution: Pin the absolute interpreter and library dir; confirm the wrapper is the only launch path so a later env change cannot silently re-resolve to a system copy.
  6. 6. Verify a running instance (the test) Run: --version (returned 'Ledger 3.3.2-20230330 ... with Python support' - the 3.4.0-1build2 binary mis-reports its version, the exact bug the v3.4.1 release notes call 'Fix version number in binary'); balance on a multi-currency KES+USD journal (bottom line exactly 0, double-entry holds); a 0.9% fee on 0.10 USD reported as 0.0009 USD exactly in the account register (no rounding/erosion, GMP arbitrary precision); and a byte-identical re-run of balance (diff empty) proving idempotent re-posting. All four passed on this host.
    Caution: Treat the balance bottom line of 0 as the acceptance gate; a non-zero total means an unbalanced or mis-posted journal, not a tool failure.

Known gaps

What the original design does not document:

  • No web UI or HTTP/JSON API - terminal CLI only; a member-facing UI must be built on top.
  • No multi-user/auth/access control - single-user local process.
  • No built-in P&L/balance-sheet/cash-flow report commands - must be composed from balance/register/period queries.
  • No 'import' command - CSV ingested via 'convert' or manual editing; 'csv' is export-only.
  • No patronage/surplus-allocation command - needs a custom compute layer (ledger Python bridge or external script).
  • No built-in scheduled backup or push notifications - journal files are static; schedule backup (cron+git or rsync) yourself.
  • Reporting-only by design: ledger never writes to data files; transaction entry is manual or scripted (entry command, convert, or an external importer).
  • build.files is a curated size-limited representative subset (67 files) chosen to fit the result transport limit; the COMPLETE commit-pinned design index is 314 non-test files (136 core src/, all build config, docs, data, vendored libs, GPL example app), on disk at src/result_full.json and fully reproducible from the pinned commit in repositories[]. Every omitted file's path is a deterministic subpath of the pinned tree at api.github.com.
  • Test suite omitted by design: test/ (5015 fixture/baseline .test/.dat files, 21 dirs) plus contrib/non-profit-audit-reports/tests/ (13 files) = 5028 blobs, present at the pinned commit.
  • ledger-semantics is a dev/CI dependency only (Lean semantics + bisimulation oracle pinned in flake.lock rev 368d027f...); NOT a runtime dependency of the shipped CLI.
  • Vendored third-party libs lib/immer and lib/utfcpp/v4 are in-tree and compiled in; each licensed Boost-1.0 (own LICENSE), not part of the root BSD-3-Clause grant.
  • contrib/non-profit-audit-reports/ is GPL-3.0-or-later (its LICENSE states that scope does not impact any other part of Ledger; standalone example app via the Python API, not imported into core).
  • Latest release v3.4.1 (2025-10-26) ships a source tarball only - no prebuilt binary; deployment builds from source (or external image dcycle/ledger).
  • GitHub API reports licence NOASSERTION/'Other'; BSD-3-Clause is derived from the three-condition LICENSE.md text + README badge. The need-brief summary's 'BSD-2-Clause' is a transcription error corrected here.
  • Upstream does not document a rootless/deb-extraction install path; the ledger manual (ledger-cli.org) documents only build-from-source and normal package installs, so steps 3-5 (dpkg-deb extraction, boost library staging, ld.so --library-path wrapper) are filled from the distro index and ldd output retrieved here, not from an upstream doc.
  • The dependency set is version-pinned to Ubuntu resolute (boost 1.90, libpython3.14); on a different distro or point release the exact .so names and the -py314 python-bridge companion differ, so step 3 must be re-run against that distro's own Packages index rather than reused verbatim.
  • No cost figure for hosting: the deployment runs on a single general-purpose x86_64 machine (any laptop or small VPS); the .deb and boost debs total under 10 MB, so the only recurring cost is the machine itself, which upstream does not price. For the brief's offline single-device target, this is a zero-cloud, free-software (BSD-2-Clause) footprint.
  • ledger provides no UI, mobile-money/USSD rail, metering, or collection-automation; the build pack covers the accounting engine only. The payment/metering/collection layers named in the brief must be built and integrated on top (see the fit field: those are MISSED or PARTLY at the product level).

Safety

No significant physical hazard in building, installing, using or maintaining this software stack. Electrical, radio and (absent) battery risks are low and covered by the spec. Apply the two listed controls — active/adequate cooling plus an unsealed case in hot climates, and a tested 3-2-1 offsite backup of the journal — and it is safe to build in homes, farms and villages without specialist help.

HazardSeverityControls
Powered only from a 5V/3A USB-C supply (SELV); no mains wiring, no internal earthing, no high current in the enclosure.lowUse a certified 5V/3A USB-C PD supply; specify the official or a CE/UL/RCM-certified adapter rather than the unspecified 'cheaper generic PD chargers' the BOM mentions.; Do not combine or share the PSU with heavy USB loads beyond the Pi's rated budget.
Fanless Raspberry Pi 4 (0-50C ambient rated) in the target tropical/arid climates, where summer ambients exceed 35-40C. In a sealed or poorly ventilated case the SoC/RAM reach 80-85C and the Pi soft-throttles (clock cut) and shuts down near 90C, causing freezes and stressing the microSD card (and, in rare sustained cases, solder joints); no cooling, heatsink, case or airflow is in the bill of materials.mediumFit heatsinks on the SoC and RAM, or a small 5V fan / official Active Cooler; keep the case open or well-ventilated rather than a sealed plastic box.; Place the device in a cool, ventilated position; do not run it in direct sun or a hot, enclosed cabinet.; Monitor temperature (vcgencmd measure_temp / get_throttled) and add a fan or relocate if the soft-limit flag is set; prefer an A2 microSD and avoid sustained heavy load in hot months.

Data integrity / loss of the cooperative's books: the entire record is one plain-text journal file on a single microSD card with no backup, offsite copy, or versioning (the BOM gap itself notes 'schedule backup yourself'). Losing, corrupting or dropping the card — or a filesystem failure from thermal stress — destroys the group's financial record irreversibly. This is not a physical safety hazard but a high-consequence operational one for co-op ledgers.highApply a 3-2-1 backup of the journal: three copies, two media types, one offsite or immutable copy.; Schedule automated backup (e.g. cron+git or rsync) and test restores periodically to prove recovery.; Version the journal in git (the BOM's own suggestion) and checksum it at close; optionally use GPG-encrypted journals (gpgme) for confidentiality.

Evidence

The strongest findings from Applied Commons research on this project:

  • Every amount is stored as an infinite-precision rational (GMP multi-precision rationals with commodities); floating-point math is never used. So cents, partial units, and recurring decimal shares (e.g. 1/3) are exact, and per-commodity totals never drift from rounding.
  • A single account may hold multiple commodities with separate totals per commodity, and commodities are open-ended user strings (not a fixed currency list), so a mixed group pot (USD cash + loans + insurance reserves + fees, plus a second currency) is expressible directly.
  • ledger's official manual (ch.13 'Extending with Python') documents a first-class embedded Python API: read_journal() loads a Journal, journal.query() 'accepts every argument you can specify on the command-line, including --options', queries iterate postings exposing post.amount/post.account, Amount/Balance types carry commodities, and user-defined Python functions become value-expression functions. This is a complete, documented path for a Python/Kivy front end.
  • Balance assertions are inline '= <amount>' posting lines that are a hard ERROR by default when the account total does not match; the --permissive flag quiets them. A treasurer can read each assertion as a literal expected balance. Mismatches are fatal, not warnings, by default.
  • In a multi-commodity account an assertion verifies only the one named commodity ('only the one asserted is verified'); the single cross-commodity assertion is the bare value 0, which asserts the account is totally empty. You cannot pin a multi-currency pot total with one assertion.
  • Canonical project is ledger/ledger (C++ command-line double-entry accounting). Latest release v3.4.1 published 2025-10-26. GitHub releases carry no prebuilt static binary, and the official download page lists only distro packages (Ubuntu/Debian/brew/Arch/Nix, etc.) - no official static SBC/Android artifact.
  • A self-contained static binary needs more than 'GMP': ledger's CMakeLists.txt (v3.4.1) requires CMake 3.16.2+, Boost 1.72+ (components: filesystem, iostreams, date_time, regex, unit_test_framework), GMP 6.1.2+, MPFR 4.0.2+ (which itself depends on GMP), and ICU 63 for unicode regex, plus the utf8cpp header (utf8.h). So the static dependency tree is GMP+MPFR+5 Boost libs (+ICU, utf8cpp).
  • Measured real-world footprint (dynamic, not single-file): Alpine 3.23 community armv7 ledger 3.4.1-r0 = 1.1 MiB compressed / 2.9 MiB installed, 7 shared-library deps (boost_filesystem, boost_iostreams, libc.musl-armv7, libgcc_s, libgmp, libmpfr, libstdc++). Termux main aarch64 ledger 3.4.1-5 = 1,306,188 bytes compressed / 7420 KB installed, 6 shared-library deps (boost, libc++, libedit, libmpfr, libgmp, python). Both are well under a ~10 MiB one-device storage budget.
