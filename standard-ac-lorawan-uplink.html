LoRaWAN reaches kilometres on milliwatts, so river, rain and soil nodes can run for years on a battery where there is no power or mobile signal. It is an ITU-T recommendation (Y.4480) with open network servers, and one community gateway can serve every sensor in a village.

Specification

Remote, battery-powered sensor nodes send telemetry over LoRaWAN L2 1.0.4 (LoRa Alliance TS001-1.0.4, which ITU-T Y.4480 is technically equivalent to), with radio parameters per the LoRa Alliance Regional Parameters RP002-1.0.4 for the deployment's region (EU863-870 in Europe, US902-928 in North America and so on) and the national radio rules (in Europe the ETSI EN 300 220 duty-cycle limits). Devices join by OTAA, never ABP, with keys unique to each device and held by the deployment. Battery nodes are Class A. Payloads are compact binary with the byte layout documented per module (a few to about 20 bytes), sent no more often than the data needs (minutes, not seconds). Alerts start on the node as uplinks: when a node's threshold or rate-of-rise logic trips, it sends an immediate uplink with a trip flag, and the gateway issues any warning (ac-early-warning-message). Downlinks are for configuration only and can take hours to reach a Class A device, so no alert path depends on them. A mains-powered device that must receive commands promptly (a siren or a valve) uses Class C. Network server: a self-hosted open network server on the site gateway (for example ChirpStack), so the network works without internet; a public community network may be added for redundancy within its fair-use limits (on The Things Network, 30 s of uplink airtime and 10 downlinks per device per day). Decoded readings are republished on the local MQTT broker (ac-mqtt-iot-bus).
