Open Food Facts
NeedFood and nutrition
StatusBuild pack ready
LicenceNone found
SafetyControls needed
The safety review found hazards that need controls when building or using this design.

Free, open database of food products with ingredients, allergens, and nutrition facts (4.7M+ products), open-licensed and volunteer-run, used to make better food choices and power public-health research. Helps anyone checking nutritional adequacy/label transparency, plus researchers and app builders. Maturity: very high - large non-profit with active infrastructure and apps.

Known gaps

What the original design does not document:

  • There is no BOM file in the project; this bill of materials was reconstructed from docker-compose files, Makefiles and deployment docs.
  • Production hardware sizing is not documented - only dev recommendations (8 GB / 6 cores); the production OVH 200/201 VMs are referenced but their specs are not in the retrieved pages.
  • ML model inventory: docs say models live on the Hugging Face Hub, but no per-model weights list, license, or download size is in the retrieved pages (only the TRITON_URI_* env names).
  • No pricing of any kind exists in the project (software is free; no hardware bill, no cloud-cost table).
  • The official dump catalog pages (dumps.openfoodfacts.org/data/ and wiki.openfoodfacts.org/Data_Dumps) could not be retrieved (403 via the extraction proxy), so the catalog listing itself is unverified; the dump URLs and sizes above come from the project's own Makefile and direct HTTP HEAD against static.openfoodfacts.org.
  • Robotoff .env required values (TAG, COMMON_NET_NAME, ELASTIC_PASSWORD, etc.) are referenced in compose but a complete variable reference was not in the retrieved pages.
  • No documented real-time data-update mechanism for third-party caches (internal REDIS only; a 3rd-party notification API is 'being explored').
  • No published test-coverage target or threshold: coverage is measured (Devel::Cover) and uploaded to Codecov per test group, but no numeric target or branch-protection threshold is documented in the retrieved test docs or CI workflow
  • No published performance or load SLA for the public API: no latency percentiles, throughput targets, or rate-limit numbers appear in the API docs or tutorials retrieved
  • No documented end-to-end acceptance test for the scanner -> API -> display flow in the app: the app README documents build/run steps only; scan-flow guidance lives in the server's UX tutorial, not in automated tests
  • No container HEALTHCHECK in the official Dockerfile (issue #14749, open), so self-hosting acceptance has no built-in liveness endpoint to reuse
  • Not-found semantics are not documented consistently across API paths or code validity classes: the tutorial documents status:0 for not-found, but the bare path returns status:0 for existing products, /api/v2/product/{code}.json returns status:0 only for structurally invalid codes (status:1 otherwise), placeholder products under valid codes make status unreliable for found-ness, and v3 has the contradictory-error bug (issue #12848)
  • No integrity manifest for delta files: index.txt lists filenames only - no checksums or sizes - so cache syncers must verify content themselves
  • No ODbL write-back compliance test: share-back through the WRITE API is stated as a licensing requirement in the caching tutorial but is not covered by any documented test
  • No published ISO-style standard for label-data accuracy: the closest published metric set is the arXiv 2510.03570 OCR benchmark (CER/WER/BLEU/ROUGE-L/F1) for label-text extraction; no standard governs database-level accuracy or completeness

Safety

Software-only build; physical hazards are those of running a standard Linux server (low-medium, ordinary IT controls). The dominant hazard is informational (water-food kind): OFF drives allergy/nutrition decisions on volunteer-maintained, OCR-sourced, nightly-updated data that can be missing, wrong or stale. The pack already mandates a UI allergen disclaimer, write-moderation, delta refresh and cache-age display, so it is safe to self-host in a home/farm/village once the user keeps the server ventilated, uses standard mains installation, and never relies on an OFF lookup to make an allergy or medical decision. No licensed-person step is required.

Evidence

The strongest findings from Applied Commons research on this project:

  • Per-region coverage is measured by slicing the dump on countries_tags (countries where product is marked sold); OFF's official completeness is limited to legally-required fields (ingredients, nutrition, category) tracked as -completed/-to-be-completed states plus a per-product completeness float; allergens are not in that metric (derived from ingredients).
  • OFF generates the full database export (MongoDB, CSV, JSONL, Parquet) nightly; the full Food CSV is documented at ~0.9 GB compressed / ~9 GB uncompressed, and the Parquet export measured 7.88 GB.
  • OFF's first-party generate_dump_for_offline_apps.py defines the minimal offline subset as exactly 7 columns: code, product_name, quantity, brands, nutriscore_grade, nova_group, environmental_score_grade (the three score columns only for the OFF flavor).
  • In-market product counts (measured 2026-10-05): France 1,272,425; United States 980,911; Germany 429,310; Spain 372,185; Italy 271,165; United Kingdom 196,121; Canada 127,901; Netherlands 111,661; Australia 82,096; global total ~4,794,547.
  • OFF explicitly discourages API scraping for analytical use and rate-limits it (I hit intermittent 503s); the sanctioned path is nightly bulk exports (CSV ~0.9GB gz/9GB raw, JSONL ~43GB raw, HuggingFace Parquet), all free under ODbL with attribution/share-alike obligations; re-runs are idempotent since dumps are full snapshots.
  • A local/offline cache is OFF's officially recommended and ODbL-compliant pattern for offline use; there is no public real-time update stream (internal REDIS only), so periodic batch sync is the intended design.
  • Documented sync caveat: because the delta files are mongoexport output, they cannot represent deleted products, so a fully current offline deployment must periodically re-import the full MongoDB dump to purge deletions.
  • Robotoff's core QA mechanism is confidence-gated human-in-the-loop: predictions become 'insights' that are auto-applied when highly confident, otherwise sent to human annotators via the 'Hunger Games' platform; a scheduler marks high-confidence insights for automatic application and pushes them to the database. Insights span category, weight, brand, packager codes, expiration date, some labels, abusive/rotated pictures, and nutrition values.
