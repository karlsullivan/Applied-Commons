Alternative ESP8266/ESP32 firmware (GPL-3.0, 24,797 stars, pushed 2026-10-04) with web-UI config, OTA updates, automation rules and entirely local control — the common firmware for DIY temperature, humidity and relay-based fan/valve controllers.

Testing

CheckHowPass if
Temperature sensor accuracy (prerequisite for holding the 18-26 C comfort band at occupant height)Place the sensor (DS18B20 default, or DHT22) in an ice-water bath (0 C) or beside a calibrated reference thermometer, and read tele/<topic>/SENSOR via MQTT or the webUI; repeat at a second point inside range (e.g. ~25 C).Reading within +/-0.5 C of the reference (DS18B20 datasheet spec for -10 to +85 C).
Setpoint hold inside the comfort band (brief req: 18-26 C operative temperature, occupant height)ThermostatModeSet 1; TempTargetSet 20; run for at least two PI cycles (default TimePiCycleSet 30 min); log tele/<topic>/SENSOR and CtrDutyCycleRead; compare the trace against the official worked forced-air example (night 18 C, morning ramp to 22.5 C, evening 23.5 C) showing Ramp-Up then PI phases.Temperature settles at 20 +/- 1 C (inside the 18-26 C band), duty cycle decays toward 0 as the setpoint is reached, and oscillation around the setpoint stays within the default 0.1 C hysteresis band.
Frost protection (cold-exposure exposure in the brief's climate constraints)Keep default TempFrostProtectSet 4.0; drive the measured temperature below 4.0 C (local sensor in a cold space, or TempMeasuredSet during bench test) and observe the heating relay; then allow the temperature to recover above the threshold.Heating output turns ON at or below 4.0 C and turns OFF once measured temperature is back above the threshold.
Failsafe on sensor loss (prevents latched-on heating)Run with a healthy sensor, then unplug the sensor (or drop its MQTT feed); wait out TimeSensLostSet (default 30 min); check StatusSNS Thermostat sensor state and the relay state.Sensor is marked lost (0.0 C / 'not alive' in telemetry) and the heating output failsafes to OFF with no indefinite latched-on heating - issue #16985 documents exactly this failing in v12.2.0 (heater hunting 0 C and staying on), so the deployed firmware release must be checked against that report.
Power-restart and power-failure recovery (no unintended actuation after brownouts)With PowerOnState 3 (default) trigger a warm restart (webUI button or MQTT restart) and observe the relay; then cut and restore mains power (cold start) with PowerOnState 0 and 3 each, and check the relay.Warm restart: relay state unchanged, no off-on flick; cold start: relay matches the PowerOnState setting exactly (0 = OFF after power failure, 3 = last saved state). Note SetOption63 disables the startup GPIO scan where it reads relay state incorrectly.
Offline / local-only operation (brief constraint: patchy connectivity, no cloud)Set SensorInputSet 1 (local sensor); stop the MQTT broker and cut internet; change the setpoint via the webUI console or serial and watch the control loop over >= 1 hour.The Ramp-Up/PI loop keeps heating from the local sensor with no network at all (PID docs state the loop survives network detachment); telemetry and remote control resume on reconnect.
Manual bypass / wall-thermostat override (closest built-in emergency control)Send INPUTSWITCHUSE 1; close the input switch and verify the output follows it (manual mode); leave the input open for longer than TimeManualToAutoSet (default 60 min).Output mirrors the input while the input is active, and control returns to automatic after the input is inactive for the configured window. On devices whose button always reads active (documented: Sonoff 4CH PRO R2) INPUTSWITCHUSE must be 0 or the output latches on in permanent manual mode.
Multi-zone independence (multi-controller build)On a build compiled with THERMOSTAT_CONTROLLER_OUTPUTS > 1 (documented as tested on Sonoff 4CH PRO R2), assign different setpoints to two controllers and toggle one.Each relay tracks only its own setpoint; actuating or failing one zone does not drive the other outputs.
Configuration and repair fully local (brief: usable offline, repairable open source)Perform a complete configuration (Wi-Fi, MQTT host/user/topic, module template, thermostat parameters) via the webUI Console or a 115200 baud serial terminal with no internet access; then erase and re-flash the firmware over serial to prove repairability.Full device configuration and a full firmware re-flash are achievable offline; the device reboots into the flashed Tasmota and re-accepts the saved Backlog configuration.
OTA upgrade integrityPoint OtaUrl at the official release server (ota.tasmota.com or the tasmota32 equivalent), send Upgrade 1, and compare config and relay state after reboot.Device reboots into the new firmware with settings retained (warm-restart behavior per PowerOnState docs); verify the thermostat boot-reconfiguration rule (below) re-applies driver parameters after the reboot.

Failure modes

FailureEffectMitigation
Sensor failure or drop-out (DHT22 signal wire pulled, DS18B20 disconnected, feed device down)Tasmota keeps publishing telemetry with 'nan' (last_changed still updates, so HA does not mark it stale) or the driver sets measured temperature to 0 C after the sensor-lost timeout; the PI controller then hunts the setpoint and the heater latches ON indefinitely - continuous energy draw and overheating (HA generic-thermostat thread; Tasmota issue #16985 on v12.2.0).Verify the deployed release failsafes the output to OFF on sensor loss (test item 4); on the Home-Assistant side use expire_after plus a value template that treats nan as unknown and an automation that cuts the heat (both documented in the HA thread); shorten TimeSensLostSet from the 30-min default for faster reaction; add a redundant second sensor where the OpenHVACControl pattern (secondary-sensor check on primary failure) is needed - Tasmota has no built-in secondary handover.
Relay closes or flicks on boot/restart (ESP boot-time pin state)Unwanted actuation at every restart: garage door toggles, furnace/valve pulses, or an off-on flick even with PowerOnState 3. Documented for ESP32-C3 (e.g. GPIO12 is hardwired input-enabled with pull-up until software takes over - 'nothing Tasmota can change') and reported for ESP8266 in the field; only a subset of GPIOs hold their state across reboot.Choose the relay GPIO based on the board's external pull state (a design that holds the relay OFF with no signal is safe across resets); set PowerOnState 0 when a safe-off cold start is required; disable the startup relay-state scan with SetOption63 where it reads outputs incorrectly; on the hardware side add external pull resistors that hold the relay in the safe state.
INPUTSWITCHUSE 1 on devices whose input button always reports active (documented: Sonoff 4CH PRO R2)The thermostat driver treats the input as permanently active: the output turns ON continuously and the controller stays in manual mode forever.Set INPUTSWITCHUSE 0 on such hardware (explicit note in the official Thermostat docs); test the manual/auto handover after configuration.
Thermostat driver parameters are RAM-only and do not persist to flashEvery restart resets all PI/ramp-up/setpoint settings to the compile-time defaults (e.g. ThermostatMode back to OFF, target back to the default 18.0 C), so an unmonitored reboot silently disables control until re-configured.Install the documented boot rule that re-applies the configuration (ON Power#boot / ON mqtt#connected DO Backlog sensorinputset 1; controllermodeset ...; thermostatmodeset 1; temptargetset %mem1% ENDON), keeping values in Mem variables so they survive the reboot.
DHT22 wired to GPIO2 (e.g. Wemos DHT Shield D4 pin)Sensor reading is not available after a soft reboot - the thermostat silently loses its local sensor every reboot.Wire the AM2301/DHT22 data line to any other GPIO (explicit note in the official AM2301 docs: 'Do not use GPIO2 as reading will not be available after a soft reboot').
Controller mistuning: Ramp-Up overshoot or PI oscillation around the setpointTemperature overshoots the setpoint (Ramp-Up is a predictor, not a limiter - docs state it 'might produce some overshoot') or the relay chatters, wasting energy and stressing actuators.Tune PropBand, TimeHystSet, TempAntiWindupResetSet and TimeMinActionSet per the official tuning guidance (worst-case manual tune for min action); force pure PI with ControllerModeSet 1 if the hybrid overshoots; the Ziegler-Nichols PI autotune exists behind USE_PI_AUTOTUNING but upstream labels it untested, so do not rely on it for acceptance.
Valve actuator seizure after long time in one positionA zone silently stops heating/cooling because the mechanical valve is stuck - no error is raised by the firmware.Use the documented weekly forced-actuation rule (Rules#Timer + forceactuate event with EnableOutputSet 0; Power 1; ~600 s hold) so slow actuators (wax cartridges ~2 min full stroke) cycle regularly; verify the actuator actually moves against the CtrDutyCycleRead trace.
Competing control messages (rules, Node-RED flows, HA automations) racing the thermostat loopConcurrent messages interfere with control logic and the relay 'flashes' (documented from a field furnace build where a naive control loop caused havoc).Keep control in the firmware driver (MQTT setpoint in, relay out) rather than parallel automations; if external logic is required, serialize it (one message at a time / semaphore pattern used in the dullier.eu build) and gate it on the same trigger period.
MQTT broker or Wi-Fi lossRemote control and telemetry are lost; with SensorInputSet 0 (MQTT temperature input) the thermostat loses its only temperature source and the output decision degrades to the sensor-lost path.Run with SensorInputSet 1 so the local sensor keeps the loop alive offline (verified in acceptance item 6); monitor reachability via tele/<topic>/LWT (documented in the openHAB DHT22 build); keep the device reachable over serial for recovery.
Grid brownouts / power fluctuationsRepeated power cycles can trigger Tasmota's Power Cycle Recovery, resetting the device to firmware defaults (losing all configuration, including thermostat safety settings).SetOption65 1 to disable Power Cycle Recovery on unstable grids (documented); optionally feed the controller from a UPS, and use the boot-rule re-configuration as a backstop.

Known gaps

What the original design does not document:

  • Tasmota has no BOM of its own - it is firmware; the BOM is whatever ESP device it is flashed onto, and no official hardware, supplier or price is documented for a 'one unit' thermostat
  • No priced bill for the standard thermostat build exists upstream - the only prices are third-party (stuffblog, 2023, EUR street); no supplier/distributor links are provided by the project
  • The Voltlog open-hardware board has a complete KiCad schematic + PCB but NO priced BOM with part numbers, suppliers or quantities of passives - components must be read off the schematic
  • Power-supply spec is undocumented/optional: stuffblog lists a 5V 15W DIN PSU with no part number or price, and the relay module's supply is not otherwise specified
  • No emergency manual-mode BOM: unlike OpenHVACControl, Tasmota has no built-in emergency manual mode; the wall-thermostat bypass (INPUTSWITCHUSE 1) is the closest but requires an existing wall thermostat that is not in the DIY bill
  • No mains-safety/isolation BOM for a 240VAC-powered build: the Voltlog board has 1A and 0.5A fuses, but a DIY relay build driving a mains load has no documented isolation, transformer, creepage or enclosure guidance in a BOM form
  • No bill line for the MQTT broker / host service - it is free software (Mosquitto) assumed to run on a device the builder already owns
  • No connector/wiring spec for tying the sensor+relay to a specific local no-grid load (e.g. LPG burner solenoid, fan, heater element) is documented
  • nbkomputer sensor price comparison page was bot-walled at retrieval, so per-sensor street prices from that source could not be verified (datasheets used instead for sensor specs)
  • Tasmota thermostat/PID is a COMPILE-TIME feature: not present in precompiled binaries - a custom build (add USE_THERMOSTAT / USE_PID to user_config_override.h and compile via PlatformIO) is required; no prebuilt 'thermostat' .bin is shipped.
  • voltlog/Valve-Actuator has no 3D/CAD enclosure - only 2D schematic + KiCad PCB source; no exported Gerber/drill files are committed (must be generated from the .kicad_pcb), and no bill-of-materials (BOM) file is in the repo.
  • voltlog/Valve-Actuator carries no explicit component part numbers / purchase list for the rev D SMD board (DFM SMD variants) - component sourcing must be inferred from the schematic.
  • Tasmota documents no step-by-step thermostat commissioning / acceptance-test procedure; the closest test path is tools/qemu (software-in-the-loop), not a hardware acceptance test.
  • allen-shelton/esp8266-fan-controller has no LICENSE file - source licence is unstated.
  • tasmota/docs has no LICENSE file - documentation licence is unstated.
  • OpenHVACControl hardware / wiring / installation documentation lives in a separate GitHub wiki (github.com/lbrombach/OpenHVACControl/wiki) that is not part of the indexed repository tree and was not included file-by-file.
  • No project documents a grid-independent power supply (battery/UPS) for the ESP32/ESP8266 controller - all designs assume AC/USB 5V power at the site.
  • Upstream documents no test suite or acceptance procedure for the thermostat driver - no pass/fail test script, no conformance checklist; the only performance evidence is one worked forced-air heating example chart and compile-time defaults.
  • No measured loop accuracy is published (e.g. setpoint hold within +/-X C over time); only the raw sensor spec (DS18B20 +/-0.5 C) is available, so acceptance targets for band-holding must be set by the deployer.
  • Cooling mode is explicitly 'not properly tested' upstream (ClimateModeSet 1) - no cooling acceptance data exists; the need brief's tropical-heat use case is therefore unverified by the project.
  • PI autotune (Ziegler-Nichols) is marked untested upstream; it cannot be part of acceptance testing.
  • The sensor-loss failsafe is not documented as a guaranteed safety behavior, and issue #16985 shows it failing (heater latched on) in v12.2.0; the fix status of that issue could not be verified (GitHub API rate-limited during this task), so the deployed release must be tested against it.
  • The StateEmergencySet command and ThermostatEmergencyShutdown() exist in xdrv_39_thermostat.ino source but are not described in the public Thermostat documentation page retrieved - the emergency shutdown's trigger semantics are undocumented.
  • No built-in emergency manual mode and no built-in secondary-sensor handover: OpenHVACControl documents both (toggle-switch emergency operation; secondary sensor checked on primary failure); Tasmota's closest equivalents are the INPUTSWITCHUSE 1 wall-thermostat bypass (itself pitfall-prone on some hardware) and third-party Berry builds (e.g. Beormund's multi-zone controller adds explicit manual-override modes: Advance/All Day/Const On/Const Off/Boost).
  • No IAQ capability (PM2.5/CO sensing or limiting) in Tasmota - the brief's requirement to meet WHO indoor-air-quality emission targets is untestable on this stack; the thermostat controls temperature only.
  • No published deployment in the brief's target context (informal settlements, off-grid, low-income households, hand-tool buildability): every retrieved field build is a grid-connected Western home (UK furnace, Romanian floor heating, US garage door), so the cost/tenure/no-grid requirements of the brief are not exercised by any upstream evidence.
  • Relay-on-boot behavior is only documented through user Q&A (discussion #17157, Reddit) and is board/pin/design-dependent; there is no systematic guarantee or pin table stating which relay GPIOs will not actuate on boot.

Safety

Controls needed plus a qualified person for all mains work. The Voltlog board puts 110-240 VAC on the PCB and the manufacturer defers installation to a professional; the DIY relay build switches a mains furnace circuit with an unverified contact rating and no independent safety cut-off. Safe with the controls in place and mains steps delegated to a licensed electrician.

Evidence

The strongest findings from Applied Commons research on this project:

  • Tasmota's README states the exact warnings in question: a 'DANGER OF ELECTROCUTION' section (if the device connects to mains, improper installation risks electrocution; call an electrician, in some countries a licensed electrician is legally required; never serial-flash while connected to mains) and a full disclaimer that the project takes no responsibility or liability for the software or for installations/advice. The license is GPL-3.0-only, which imposes no restriction on private use or installation.
  • Tasmota's PowerOnState parameter defines relay state at initial power-up: 0=OFF, 1=ON, 2=TOGGLE, 3=last saved state (default), 4=ON and lock, 5=delayed ON. It does NOT apply to warm restarts. PowerOnState 0 is the firmware-level mechanism for a fail-safe (relay off) default after a mains power loss.
  • The thermostat driver is fully implemented and already contains heating AND cooling, frost protection, and auto/manual switching. Cooling is first-class in the code: enum ClimateModes {CLIMATE_HEATING, CLIMATE_COOLING}; the CmndClimateModeSet command; and the PI error and all Ramp-Up/state logic are explicitly branched for cooling (e.g. 'Invert error for cooling' in ThermostatCalculatePI). It is excluded from every precompiled binary solely by one commented-out #define USE_THERMOSTAT in tasmota/my_user_config.h (line 1194).
  • Tasmota Thermostat driver PI defaults are explicitly scoped to 'a typical floor heating application for mid-sized rooms (< 20m2) with one heating circuit', and the Ziegler-Nichols closed-loop PI autotune is shipped but documented as 'untested and will be further developed soon'.
  • By default (PowerOnState 3) a Tasmota heating controller restores its last relay state on power restoration, so a heater that was ON when power failed comes back ON uncontrolled until software intervenes - the unsafe default for a residential heating circuit.
  • OpenHVACControl documents its contrast point explicitly: 'Emergency operation mode. In event of controller or relay module failure, user can use toggle switches to open zones manually and operate as a single-zone system using an off-the-shelf thermostat', and its zone logic falls back to a secondary temperature sensor if the primary fails. Its wiki control-sequence docs show the main control loop, heat-priority arbitration, and a ~1 minute cool-down delay before closing dampers.
  • Frost protection is implemented and on by default: temp_frost_protect defaults to THERMOSTAT_TEMP_FROST_PROTECT (40 = 4.0 C) and acts as a hard lower bound — a setpoint below the frost-protection temperature is rejected (CmndTempTargetSet and ThermostatTimerArm both require tempVal >= temp_frost_protect), and it is tunable at runtime via TempFrostProtectSet. Auto/manual is also implemented: ThermostatMode has OFF/AUTOMATIC/MANUAL states, the input switch forces manual when InputSwitchUse=1, and manual returns to automatic after TimeManualToAuto (default 60 min).
  • The official Thermostat documentation explicitly warns the safety-critical caveats: 'This feature is not included in precompiled binaries'; the controller default is the Hybrid (Ramp-Up + PI) strategy; and, under 'Future improvements > Cooling', 'Due to lack of cooling setup at the time of the development of the driver, this feature has however not been properly tested. Testers for cooling are therefore welcomed.' It also states the PI autotune is 'untested'. So the cooling half of the requested turnkey spec is the untested part, even though the code path exists.
