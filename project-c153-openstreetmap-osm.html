Community-built open world map database covering roads, trails, water points and buildings, with an explicit emphasis on local knowledge (aerial imagery, GPS, low-tech field maps); operated by the OpenStreetMap Foundation, data under ODbL — exactly the open, locally-owned licence the brief requires; the volunteer-scale backbone every other candidate builds on. Very mature (founded 2004) and continuously maintained; this is the enabler itself rather than a tool.

Assembly

Tools: git, Docker Engine + Docker Compose (docker-compose-plugin), bash, curl / web browser (verification), Osmosis (optional, only if loading existing OSM data into the API database)
Skills: Basic Linux command line, Docker and docker compose (images, volumes, ports, healthchecks), PostgreSQL basics (databases, users, connectivity), Ruby on Rails app lifecycle (bundle, rake db tasks, dev server)
Time: Plan 0.5-1 day for a small or single-country deployment: the first docker compose build compiles the Ruby and Node dependencies and can take 30-90 minutes on a fast machine, the test suite takes a few minutes, and the rest of the setup is minutes. A full-planet data import is the long pole: osm2pgsql reports roughly 5.5-9 hours (non-slim) to 6-10 hours (updatable/slim) for the planet PBF, and Nominatim reports about 2.5 days on a well-configured machine or 4-5 days on traditional SSDs.

  1. Bill of materials (hardware, hosting and services, with costs) HOST: one Linux host running Docker (Debian/Ubuntu) or Docker Desktop on macOS/Windows; 64-bit CPU; 4-6 GB RAM and ~50 GB disk is enough for a small (city/state) extract, scaling to 120-128 GB RAM and 700 GB-1.5 TB NVMe for a full-planet updatable database. DISK: NVMe is strongly recommended over spinning disk for any data import. DATA: OSM PBF extracts from Geofabrik (free) for a region/country, or the weekly planet (~89 GB PBF, free) from planet.openstreetmap.org; planet data is ODbL licensed. SOFTWARE (all free/open-source): openstreetmap-website repo (GPL-2.0), Ruby 3.3, PostgreSQL 17 with PostGIS 3 (bundled in the provided database image), and osm2pgsql (latest 2.3.1) if you also import data for tile rendering. EXTERNAL SERVICES (free public endpoints, optional to self-host): map tiles (default is the public tile.openstreetmap.org CDN, per the DOCKER.md note that local tiles are NOT served from your database), Nominatim geocoding (nominatim.openstreetmap.org), Overpass (overpass-api.de), and routing (routing.openstreetmap.de / valhalla1.openstreetmap.de / graphhopper.com). If you self-host Nominatim it needs a minimum of 2 GB RAM (128 GB+ for a full planet) and at least 1 TB disk for a full-planet install.
    Caution: Confirm the disk is NVMe/SSD and has ample free space BEFORE starting an import; an out-of-disk or out-of-RAM import corrupts progress and wastes hours. If you use the public tile/geocoding endpoints rather than your own, comply with those providers' usage policies/ToS.
  2. Design files (source repositories, data downloads, configuration) SOURCE REPOSITORY: github.com (the Rails app; includes web site, API, browse pages, GPX). Key files: Dockerfile (root, Ruby 3.3-trixie web image), docker-compose.yml, docker/postgres/Dockerfile (postgres:17 + postgresql-17-postgis-3), docker/postgres/openstreetmap-postgres-init.sh, config/docker.database.yml, config/example.storage.yml, config/settings.yml. DATA DOWNLOADS: a PBF extract from Geofabrik or the planet PBF from planet.openstreetmap.org (only needed if you load existing data). CONFIGURATION: docker-compose.yml (services, ports, volumes, healthcheck), config/docker.database.yml, config/storage.yml, config/settings.yml and optional config/settings.local.yml. No proprietary or paid design files are required.
    Caution: Work on the upstream master or a pinned release tag you have actually retrieved, so the files you deploy match the files you read. Do not commit secrets into config/settings.local.yml.
  3. Install Docker (if not already present) On Linux install Docker Engine plus the docker-compose-plugin; on macOS/Windows use Docker Desktop. On Windows additionally enable git symlinks (core.symlinks true / Developer Mode) because this repo uses symbolic links.
    Caution: Use the official Docker install docs for your distro; a broken Docker install is the most common cause of the compose build failing later.
  4. Clone the openstreetmap-website repository Run: git clone github.com, then cd openstreetmap-website. All subsequent commands are run from the repository root.
    Caution: Verify the clone contains docker-compose.yml, Dockerfile and the config/ directory; on Windows make sure symlinks were not skipped during the clone.
  5. Copy the compose-tailored configuration files Run: cp config/docker.database.yml config/database.yml (points the app at host 'db', database 'openstreetmap', user/password 'openstreetmap'); cp config/example.storage.yml config/storage.yml; and create an empty config/settings.local.yml (a documented workaround, issues/2185).
    Caution: config/database.yml is git-ignored local config, so copying over it is safe. If you later change credentials, update docker.database.yml, the postgres init script and settings together or they will mismatch.
  6. Build the two Docker images From the repo root run: docker compose build. This builds the web image (root Dockerfile: ruby:3.3-trixie, installs system libs, bundle install, bin/yarn install) and the db image (docker/postgres/Dockerfile: FROM postgres:17, apt-installs postgresql-17-postgis-3, and installs the OSM-specific superuser 'openstreetmap' via the init script). The first build compiles all Ruby and Node dependencies and can take a long time.
    Caution: Be patient on the first build; do not kill it. If it fails, read the specific layer's output (bundle install or yarn install are the usual culprits) before retrying.
  7. Start the containers Run: docker compose up -d. This starts the db service (postgres:17+PostGIS, healthcheck pg_isready, data persisted in the db-data volume, host port 54321 mapped to 5432) and the web service (rails server on port 3000, depends_on db being healthy, tmp/ and storage/ persisted in named volumes). Inspect with docker compose logs -f web or -f db.
    Caution: Confirm the db container passes its pg_isready healthcheck before the web app will connect; the compose 'depends_on: condition: service_healthy' enforces this but a failed healthcheck shows up as a web connection error, not a clean message.
  8. Create the Rails databases Open a shell in the web container with: docker compose run --rm web bash, then run: bundle exec rails db:create. From this point on, run all further Rails commands inside this container shell.
    Caution: Stay inside the web container shell for every subsequent step, per DOCKER.md; running Rails commands on the host against a different database is the most common source of confusing errors.
  9. Validate the installation (test procedure) Still inside the web container: run the test suite with bundle exec rails test:all (takes a few minutes; a clean run with no errors means the install is successful, and the known spurious 'Attribute lat redefined' parser warnings can be ignored). Then start the built-in dev server with bundle exec rails server and open localhost:3000 in a browser: the site should load and the map should render. Check the API responds, e.g. GET localhost:3000 returns the API. The map tiles shown are the production tiles served from the public tile service over the internet, NOT generated from your local database (upstream DOCKER.md states this explicitly).
    Caution: Do not rely on a blank map to judge success; the map is populated from the external tile service by default. If the homepage loads but the map is blank, that is the expected tile-service behaviour, not a deployment failure.
  10. Populate data and create a user (optional but makes it a real working instance) To start editing, create users with: bundle exec rails dev:populate (creates 'admin' with administrator privileges and 'mapper' with normal privileges; both password 'password' per CONFIGURE.md, 'feel free to change it'). If you create users manually via the web UI instead, you must activate them (user.activate!) in the Rails console before they can sign in. If you did not use dev:populate, register the two built-in OAuth apps (iD and the website, for Notes) with: bundle exec rails oauth:register_apps["<user display name>"] - it saves the keys to config/settings.local.yml. Optionally, load EXISTING map data into the API/browse database with the Osmosis --write-apidb task, e.g.: osmosis --read-pbf greater-london-latest.osm.pbf --write-apidb host="<db host>" database="openstreetmap" user="openstreetmap" password="<db password>" validateSchemaVersion="no" (CONFIGURE.md shows host="localhost" and an empty password for its local example).
    Caution: dev:populate creates users with the well-known default password 'password' and an administrator account; change these immediately and never expose such an instance to the internet unchanged. Loading an apidb database with Osmosis is about twenty times slower than loading the same data with osm2pgsql into a rendering database, so a large extract can take many hours - use a small extract for the first run. Per CONFIGURE.md, to EDIT data loaded via Osmosis you need a 'yet-to-be-written script' (issue #282), so a loaded-but-not-yet-editable dataset is an expected, documented limitation, not a failure.
  11. Production hardening (before any non-local use) Upstream warns not to run rails server in production; the recommended approach is Phusion Passenger behind a web server. Precompile assets and i18n with: RAILS_ENV=production bundle exec i18n export; bundle exec rails assets:precompile. Ensure the web-server user and the rails user can read/write/create in tmp/. Consider CGIMap in place of the included map call, which is slow and memory-hungry.
    Caution: Do NOT serve a production instance with the development container's trust auth (POSTGRES_HOST_AUTH_METHOD=*** or the default db password; put TLS (reverse proxy) in front and move credentials out of the committed config. The compose file is explicitly a development/test setup.

Failure modes

FailureEffectMitigation
Out-of-memory during osm2pgsql importImport of a large extract or planet crashes or is extremely slow when RAM is under-specified (planet needs 64-128 GB; a slim import needs ~80 GB just to map the flat-node file).Size hardware to the extract per osm2pgsql Appendix E; prefer a regional extract over planet on a small machine; run a tuned PostgreSQL.
Stale / out-of-date local dataSettlements, water points or roads change but the local DB does not reflect it, so the sustainability requirement (R7) fails silently.Apply .osc.gz deltas on a schedule, verify the last-changeset timestamp, and re-import from a fresh base periodically.
Double-count from a non-idempotent updateRe-applying a delta or re-running the import duplicates rows, inflating counts (silent wrong data).Track applied changeset ranges, use version-based optimistic locking, and assert count stability after an idempotent re-apply.
Corrupted or checksum-mismatched downloadA corrupted PBF/planet imports garbage or fails outright.Verify md5/sha against the publisher's published hash before import; re-download on mismatch.
Rate-limit / bandwidth block on bulk download or API useBulk download or heavy API use gets blocked (HTTP 509 / 429, 'You have downloaded too much data'), stalling the pipeline.Pull bulk data from Geofabrik/BBBike/planet mirrors, respect rate limits, and run write/sync tests against the dev API.
Offline field edits lost when there is no connectivityCaptured points/ways never sync and are lost, so the last-mile data (R5) is missing.Use editor offline mode that queues edits and uploads on reconnect; verify the local edit queue before discarding; confirm the round-trip into the local DB.
Version conflict (HTTP 409) on uploadConcurrent edits cause the upload to fail.Refresh the element version before upload and retry; run test uploads against the dev API.
Licensing / attribution drift in derivativesAn exported map/dataset loses ODbL attribution or mixes in proprietary imagery, violating the 'open, locally owned' requirement (R6).Carry ODbL attribution in all exports and respect the imagery blacklist.
Target area still unmapped / no hazard layer (R2)The unmapped villages have no data, and OSM has no native hazard-exposure or vulnerability layer, so the risk-knowledge pillar is not served by OSM alone.Route mapping to the volunteer-scale (HOT Tasking Manager) workflow and derive hazard layers from a separate dataset; treat R2 as a gap, not a pass.

Known gaps

What the original design does not document:

  • Hardware unit prices (CPU/RAM/NVMe/server): spec is documented from the osm2pgsql sizing docs but no per-unit price was retrievable from a vendor or cloud per-spec table, so unit_cost is null
  • Field phone hardware price: only the ODK Collect app + minimum specs (Android 10+, 4 GB RAM) were sourced; a specific low-cost phone model/price was not
  • Local bandwidth/connectivity cost: no regional mobile-broadband or district-office internet price was retrievable, so the connectivity line is the $4/month cloud alternative only
  • OsmAnd 'offline editing' quote could not be verbatim-attached due to page markup; the offline-edit capability is stated on the page but not evidence-locked
  • Open-source licensing for the software stack: the retrieved osm2pgsql requirements doc states only version requirements (PostgreSQL 11+, PostGIS 2.5+, 64-bit), not that PostgreSQL/PostGIS/osm2pgsql are free or open-source. 'Free open-source' for all three is widely-known general knowledge (each is a public OSS project), not a claim from a retrieved page; none is paid, so unit_cost=0 stands
  • Optional hazard-exposure / WASH point layers (from the need brief) are not part of an OSM core deployment and would be additional data/services, out of scope for this OSM BOM
  • Full source trees are not indexed file-by-file (e.g. the entire iD/ or JOSM/ source); the design section lists the build-relevant config, style, and data files that a deployment consumes. The complete per-repo source trees are reachable at the pinned commits listed in build.repositories.
  • osmosis (openstreetmap/osmosis) has no LICENSE file in the repo root and its README states no license; recorded as 'unknown'. The upstream project is historically GPL, but that is not asserted here because the pinned commit does not state it.
  • The three sample OSM data downloads in the build-pack brief (demo.openstreetmap.org/planet.osm.pbf, geofabrik south-america bermuda, and a 0/0/0 tile) were unreachable from the build environment (DNS resolution failed / 404 / TLS hostname mismatch). A verified, reachable replacement data source is indexed instead: Geofabrik 'Monaco' extract (monaco-261124.osm.pbf, ~0.69 MB, HTTP 200/206), licensed ODbL. The full planet.osm.pbf (~70-120 GB) and a global 0/0/0 tile were NOT fetched or indexed because they exceed a practical build-pack payload and were not reachable as specified.
  • openstreetmap-carto style: project.mml and the style/*.mss CartoCSS are indexed as the style definition; the rendered font glyphs and raster basemaps it references at build time are external assets not committed to the repo, and are therefore not in this index.
  • openstreetmap-website: config/settings.yml, config/puma.rb, and config/docker.database.yml are the deploy-relevant runtime config; full per-environment settings under config/settings/ are not enumerated file-by-file.
  • The shipped Docker path (DOCKER.md) is explicitly for development and testing; there is no single, complete production deployment recipe in the repo. Production guidance is scattered across INSTALL.md and CONFIGURE.md (switch to Phusion Passenger, CGIMap, assets:precompile, tmp/ permissions) and is left to the operator to assemble.
  • The compose deployment does not provide map tiles from the local database; tiles come from the public tile.openstreetmap.org CDN and search/routing from public Nominatim/Overpass/routing endpoints. A fully self-contained tile pipeline (osm2pgsql import + a tile server such as Martin/mod_tile/pg_tileserv, per the OSM wiki) is a separate, heavier stack that the website repo does not document as part of its install.
  • No hardware sizing is given for loading website/API data via Osmosis (only the osm2pgsql sizing appendix and the Nominatim install guide give RAM/disk figures, and those are for rendering/geocoding imports, not for the Osmosis apidb load).
  • The default config uses a fixed db superuser/password 'openstreetmap' and postgres POSTGRES_HOST_AUTH_METHOD=*** upstream does not document the production credential/TLS hardening beyond general warnings.
  • Upstream does not document how to keep a loaded data set current over time (repeated Osmosis apidb updates / osmosis replication for the website DB) in the website repo; the osm2pgsql docs cover replication for rendering databases only.
  • Editing data loaded via the Osmosis --write-apidb path is not usable as documented: CONFIGURE.md points to a 'yet-to-be-written script' (issue #282) for making the loaded data editable, so the website docs do not currently provide a complete path to a fully editable, data-loaded instance through Osmosis alone.
  • No published end-to-end 'verify a running instance' acceptance-test procedure: osm2pgsql documents import requirements/sizing and replication, but not a step-by-step acceptance suite (row-count checks, tile-serving verification, offline round-trip).
  • No native hazard-exposure / vulnerability layer (R2): OSM's data model has buildings, roads and land use but no hazard exposure or vulnerability; it must be derived by another party.
  • No published tolerance for offline-capture coordinate accuracy (how accurate a field-captured point must be to pass).
  • No published sustainable running-cost figure for a district/country-scale local deployment (only import hardware/sizing is documented, not operational cost or re-run schedule).
  • OSM Stats publishes global figures (10M users, 10B nodes, ~4M changes/day) but not per-region data-quality benchmarks (e.g. % of villages with building coverage) usable as a test target.
  • No single authoritative document for the offline capture->upload error-handling path across editors (Vespucci, OsmAnd and Organic Maps each document only their own app).

Safety

Software deployment on COTS hardware. No physical build hazard (mains/gas/pressure/structural/medical use-on-patient all N/A). Five real hazards, all closable by an ops person: (1) network exposure of the default dev stack — trust Postgres on 54321 + OSM edit API on 0.0.0.0:3000 — is the single biggest risk; (2) weak default credentials shipped in the pinned repo; (3) field GPS-trace privacy for trial mappers; (4) ODbL/GPL attribution not covered; (5) rural-server operational hardening (power/cooling/connectivity) not covered. No qualified-person step for physical work.

HazardSeverityControls

Operational dependency in low-resource settings: the server is 24/7 and needs reliable internet for (a) phone sync (ODK Collect / OsmAnd upload), (b) OSM updates (the pack uses a manual weekly-update path via Overpass/planet diff), and (c) remote maintenance. Evidence

The strongest findings from Applied Commons research on this project:

  • Official osm2pgsql v2 manual (System Requirements): RAM rule of thumb is at least as much main memory as the PBF file; planet needs >=64 GB (128 GB better); osm2pgsql will not work with less than 2 GB RAM; only 64-bit systems supported; PostgreSQL 9.6+ and PostGIS 2.5+ required; SSD (NVMe if possible) strongly encouraged.
  • Live Geofabrik PBF sizes (download.geofabrik.de, retrieved 2026-11-24): Monaco 691 KB, Andorra 3.3 MB, Faroe Islands 7.4 MB, Kosovo 29.4 MB, Albania 51 MB, Iceland 61 MB, Georgia 98.1 MB, Croatia 192 MB, Belarus 335 MB, Spain 1.4 GB, Poland 2.0 GB, Italy 2.1 GB, Germany 4.5 GB, France 4.8 GB, Africa 7.4 GB, whole Europe 33.0 GB. Geofabrik PBFs are explicitly 'suitable for Osmium, Osmosis, imposm, osm2pgsql, mkgmap' and refreshed daily, so a country extract imports directly into osm2pgsql without the planet file.
  • The OSM data model has no native language cap: feature names are key/value tags of the form name:<ISO 639 code> (ISO 639-1 alpha2, falling back to 639-2 then 639-3), with an optional ISO 15924 script suffix (name:code-Script), so any language or script can be represented; the wiki explicitly notes ISO codes 'define' many languages 'inaccurately or uncoded' and tagging deviates where needed.
  • Official osm2pgsql Sizing appendix (osm2pgsql 1.7.0, PostgreSQL 14, Ryzen 9 3900/128GB/NVMe, Oct 2022 data, RAM = osm2pgsql process only): non-updatable imports: Switzerland 0.4 GB PBF -> 1-4 min, DB 2-3 GB, RAM ~3 GB; Germany 4 GB PBF -> 18-39 min, DB 20-30 GB, RAM ~10 GB; Europe 27 GB -> 130-240 min, DB 140-180 GB, RAM ~60 GB; planet 70 GB -> 5.5-9 h, DB 330-407 GB, RAM ~120 GB. Updateable (slim+flat-nodes) final DBs are larger: Switzerland 4-5 GB, Germany 40-48 GB, Europe 260-310 GB, planet 590-730 GB.
  • OsmAnd, the main offline OSM editor, localizes its UI through hosted Weblate (hosted.weblate.org/projects/osmand), tracks 109 locale variants (measured live from the Weblate API on 2026-11-24, incl. ar, bn, fa, hi, sw, th), and offers any language with >10% translation in the display menu, marked 'incomplete' until ~80%; 3-letter ISO 639-2 codes have historically failed to display in Android menus.
  • OsmAnd supports offline OSM editing via its OpenStreetMap editing plugin: with 'Offline editing' enabled, changes (POI create/modify, OSM notes, GPX tracks) are saved locally on the device and uploaded on request - i.e. mapping works with no connectivity and syncs later.
  • The OSM wiki's offline-contributing page lists the editors that support offline editing (JOSM, Merkaartor, Vespucci, StreetComplete) and names Field Papers as the paper-based field-survey aid, with annotated maps photographed and uploaded back - the canonical paper channel.
  • Field Papers (a Walking Papers continuation built for OpenStreetMap) creates printable multi-page atlases that require no GPS and no desktop GIS; field notes are photographed back ('snapshots') and transcribed to points/areas, giving a pure paper + phone-camera loop usable in areas with no reliable phones or connectivity.
