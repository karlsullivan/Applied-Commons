Open-source (KoboForm/KoboToolbox, AGPL-3.0) data-collection, management and visualization platform used by 32,000+ organizations across 220+ countries, purpose-built for low-resource and challenging field settings with fully user-owned data and access control. Runs offline in the field and self-hosts data in-country, meeting the local data-sovereignty and maintainability constraints. Maturity: very high and very actively maintained.

Assembly

Tools: git, Python 3.12+ (runs kobo-install run.py), Docker Engine + Docker Compose v2 (Compose V1 has been EOL since July 2023 and is not supported), SSH + bash on the host, DNS control for the public domain (A records for kf/kc/ee subdomains), host firewall (e.g. ufw/iptables), any SMTP server for activation email (e.g. a free Gmail account with an app password, per builder transcript)
Skills: Linux system administration (SSH, package management, user and group management, firewall rules), Docker and Docker Compose (images, networks, env files, logs), DNS and HTTPS (subdomains, Let's Encrypt certificate issuance, port 80/443 exposure), KoboToolbox deployment specifics (kobo-install setup wizard, kobo-docker front-end/back-end split, envfiles), Backups and restore (PostgreSQL, MongoDB, Valkey, media) and service restart-on-boot
Time: About 1-2 hours for a person comfortable with Docker on a 4-core/8GB+ server with a working public domain: a few minutes of prerequisites and setup Q&A, then the first boot, which pulls all images and runs migrations and can take well over 30 minutes (the installer offers 'Wait for another 600 seconds?' prompts; on slow machines you may answer Yes one or twice).

  1. Provision the host and OS (the bill of materials) One Linux server, Ubuntu 22.04 or 24.04 (the versions kobo-install documents as tested), with 4+ cores, 8GB+ RAM and 80GB+ SSD (sizing rationale: kobo-install auto-computes PostgreSQL and uWSGI sizing from detected CPU/RAM, allocating 75% of the machine for production; maintainer community advice is 4GB RAM at a bare minimum and the smallest installation Kobo itself manages is quad-core + 16GB; the only concrete builder data point retrieved is a 1-core/2GB/50GB VPS in 2019, which predates the current PostGIS/MongoDB/Valkey images). It needs a public static IP, an A record for the public domain plus its kf/kc/ee subdomains, and TCP 80 and 443 reachable from the internet. Cost references actually retrieved: $10/month for that 2019 2GB Linode; a self-hosted Intel N100 mini PC (reviewed at under US$200) drawing 8-12 W at the wall idling, i.e. roughly $14-21/year of electricity at $0.20/kWh (MiniLabHQ). Optional: AWS S3 for media/backup off-site storage (only needed if you enable it); SMTP can be a free personal account.
    Caution: The 2.026.43 release ships as a git tag on master (there is no release/2.026.43 branch); the installer checks out the matching kobo-docker tag 2.026.43 automatically (Config.KOBO_DOCKER_BRANCH). The release/* branches lag behind - release/2.026.12 still pins PostGIS 14 / MongoDB 5 / Redis 7.2 - so don't mix a release branch with the 2.026.43 tag. Database ports 5432, 6379-6380 and 27017 are not exposed by kobo-docker by default; if you expose them (split front-end/back-end), a firewall is mandatory and they must never be public.
  2. Install prerequisites Install Docker Engine and Docker Compose v2 (the builder transcript installed docker-ce + docker-compose via apt/pip; current kobo-install requires Compose V2 - V1 reached EOL in July 2023 and is explicitly unsupported), plus Python 3.12+ for run.py and git. Open ports 80/443 in the host firewall.
    Caution: If a firewall is in place and port 80 (and 443 when using the Let's Encrypt proxy) is not open publicly, kobo-install cannot work (explicit warning in the readme).
  3. Create a service user and fetch the code Create a dedicated non-root user (e.g. kobo), add it to the docker group, then git clone github.com, check out the release tag 2.026.43 (matches the kobo-docker 2.026.43 release published 2026-11-23), and cd into kobo-install. kobo-install clones kobo-docker into ../kobo-docker itself during setup; KPI source files are only cloned in development mode.
    Caution: Adding a user to the docker group effectively grants root privileges (Docker docs, cited in the builder thread) - use a dedicated account and do not run the stack as root.
  4. Run the setup wizard to generate the configuration Run python3 run.py; first execution launches setup. Choose Production and (for a first server install) answer: public domain name (subdomains keep kf/kc/ee and internal names are derived), support email address (used as the from-address, for Let's Encrypt, and on the maintenance page), HTTPS via Let's Encrypt (default; kobo-install installs the nginx-certbot reverse proxy), SMTP server/port/user/password (a free Gmail app password works, per the builder transcript), and the superuser credentials. Everything else - install directory, primary network interface and IP, PostgreSQL/uWSGI sizing (75% of machine for production), ports - is configured automatically.
    Caution: Nothing is written to disk until the end of setup (Ctrl+C aborts cleanly), so wrong answers are cheap to redo. Choose a strong superuser password and set a Redis password (strongly recommended in the readme). If you use your own reverse proxy, pick Custom setup and uncheck the HTTPS section.
  5. Launch the containers and wait for the environment to be ready On completing the Q&A, run.py pulls and starts both compose stacks: back-end (postgis/postgis:18-3.6, mongo:8.0, valkey/valkey:9.1 main + cache) and front-end (kobotoolbox/kpi:2.026.43, kobotoolbox/enketo-express-extra-widgets:7.6.3, nginx:1.31, certbot), then prints 'Waiting for environment to be ready'. First boot is long (image pulls plus database migrations); the installer asks 'Wait for another 600 seconds?' - on slow machines answer Yes once or twice. Success is signalled by a box printing the Ready URL, user and password, as in the builder transcript.
    Caution: If it stalls, run python3 run.py --logs (or docker ps / compose logs) in another terminal; known first-boot failures in the builder thread are a stale nginx-certbot checkout (fix: run.py --stop, rm -rf ../nginx-certbot, run.py --setup) and bad SMTP values. Containers use restart: always with multi-minute stop grace periods, so a crashed container self-heals after migrations settle.
  6. Test: verify the running instance 1) curl -I or a browser hit to kf.<domain>; (KPI/KoBoForm login), kc.<domain>; (KoBoCAT) and ee.<domain>; (Enketo) - all three must serve valid Let's Encrypt pages (certificate issuance is itself a test that DNS and ports 80/443 were correct). 2) Log in with the superuser and register a second account: receiving the activation email proves SMTP end-to-end. 3) Create a survey/form in KoBoForm and publish it to Enketo; 4) submit a test response from the Enketo web form (and, for field use, from KoboCollect on a phone); 5) confirm the submission appears in the form's data table and in the KoBoCAT/KPI API.
    Caution: A 500 error on new-user registration is the documented symptom of bad SMTP settings - fix the SMTP section and re-run setup before blaming the app. Do not skip the SMTP check: account activation and password reset silently depend on it.
  7. Make it durable: backups, restart-on-boot, and update path Enable periodic backups by uncommenting the *_BACKUP_SCHEDULE variables in the envfiles (PostgreSQL, MongoDB, Valkey, KoBoCAT media land in ./backups/ on disk; with AWS S3 configured they go to the bucket) and verify a restore manually (kobo-docker ships backup-to-disk.bash and documents mongorestore/pg_restore restore commands). Ensure the stack comes back after a host reboot: the kobo-docker containers carry restart: always, but the builder transcript's working recipe for the full kobo-install + nginx-certbot stack is a /etc/cron.d entry '@reboot <user> cd <path-to-kobo-install> && /usr/bin/python run.py' with a trailing blank line. For future upgrades: python3 run.py --update <branch-or-tag> on a release branch, with a full backup first.
    Caution: Back up before every upgrade - especially if the instance predates the September 2026 Valkey cutover: once Valkey has saved, the old Redis process can no longer read the data files, so the pre-upgrade Redis backup is the only way back. Never expose the backups directory publicly.

Known gaps

What the original design does not document:

  • No published hardware minimum in the kobo-docker or kobo-install READMEs: the 4 GB RAM bare minimum and the quad-core/16 GB reference appear only in core-team forum replies (2021); the official 'Installing KoBoToolbox on Your Own Servers' support page could not be machine-extracted (JS rendering) in this run.
  • No published disk/storage minimum; 50 GB SSD is the only documented working figure (2019 VPS transcript), and actual disk grows with media uploads, exports and databases.
  • No published power-draw figure and no tested off-grid/solar configuration; the off-grid sizing here is inferred from independent N100-class measurements, not upstream data.
  • No swap recommendation in current docs; 8 GB swap on a 2 GB RAM box appears only in the 2019 install transcript.
  • No tested low-cost field-device list and no field-day battery data for KoboCollect; feature-phone support is absent (Android-only client).
  • No documented SMS/voice advisory-delivery path: the RapidPro bridge is out-of-tree and not part of the core Kobo deployment.
  • No per-VM sizing table: uWSGI and PostgreSQL are sized automatically from detected CPU/RAM (75% of the machine in production) rather than documented per-component numbers.
  • No fixed minimum hardware spec (RAM/CPU/disk) is published; kobo-install derives PostgreSQL and uWSGI sizing from the host's detected CPUs and RAM at install time rather than documenting a target number.
  • No hosting or service cost figures are documented anywhere upstream; infrastructure cost depends entirely on the deployer's chosen host and cloud provider, so no BOM dollar total can be quoted from the sources.
  • enketo-express-extra-widgets, kobo-in-a-box, geocoder and docs carry no SPDX license file (upstream does not state one for these), so their licence is recorded as 'unknown'.
  • The docker-compose frontend pins KPI and Enketo by release tag (kobotoolbox/kpi:2.026.43, kobotoolbox/enketo-express-extra-widgets:7.6.3), not by image digest, so a build is not bit-for-bit reproducible from the compose file alone.
  • kobo-helm-chart values.yaml requires the operator to set kpi.version and enketo.version (no defaults), so exact application image pinning is left to the deployment rather than fixed in the chart.
  • kobocat is archived and merged into kpi (release 2.024.19); pre-2.020.18 installs shared a single Postgres database and need a documented migration to separate KPI/KoBoCAT databases that upstream only links to a community post, not a file in the repos.
  • No official documented minimum RAM/CPU/storage for current releases: the support-docs hardware page (support.kobotoolbox.org/kobo_your_servers.html) now meta-redirects to the docs index (verified by fetching it); the only sizing figures anywhere are maintainer community advice from 2021 (4GB RAM bare minimum; Kobo's own smallest managed install is quad-core + 16GB) and a 2019 builder datapoint (1-core/2GB/50GB VPS + 8GB swap) - both predate the current PostGIS 18 / MongoDB 8 / Valkey 9 images, so real minimums for a 2.026.x install are inference, not documentation.
  • Storage sizing is undocumented: media uploads and database growth have no stated ceiling or recommended disk size (the 50GB figure is a builder's choice, not a requirement).
  • Restart-on-boot is not documented in either README; the working @reboot crontab recipe comes from a community reply in the builder thread, and containers alone (restart: always) may not re-attach the nginx-certbot/Let's Encrypt layer after a bare reboot.
  • No time-to-deploy estimate is published anywhere upstream (first-boot image-pull/migration duration varies with network).
  • Hosting cost is never documented by the project; the only price retrieved is the 2019 builder's $10/month 2GB VPS, which is under-provisioned for current images, so real-world cloud costs for 4-core/8GB instances must come from provider price lists.
  • The installer's long-wait prompts ('Wait for another 600 seconds?') are documented for macOS slowness but there is no Linux guidance on how long a normal first boot takes or what indicates a genuine hang vs. a slow pull.
  • Branch/tag topology is under-documented: the 2.026.43 GitHub release is a tag on master and the installer checks out a same-named kobo-docker ref (Config.KOBO_DOCKER_BRANCH='2.026.43'), but kobo-docker has no 2.026.43 branch and its newest release/* branch (release/2.026.12) pins an older data layer (PostGIS 14 / MongoDB 5 / Redis 7.2) than master (PostGIS 18 / MongoDB 8 / Valkey 9.1). The readme's generic 'use a release branch for production' advice does not state which branch/tag to pin for a given version, so a builder who picks a release branch for 2.026.43 will get an inconsistent or…
  • Kobo publishes no power-draw figure for a running instance and no tested off-grid/solar configuration - the ~10-15 W average used for sizing is inferred from N100-class mini-PC measurements, not a Kobo measurement
  • Kobo publishes no official load-testing standard or benchmark numbers; the 1,000,000-submission load figures come from a community report, not an upstream test suite
  • No published field-day battery data or tested-device list for low-cost (<US$30-150) Android phones - only the getodk tested-device list exists, and sub-US$30 device viability is unverified
  • The documented hardware minimum (4 GB RAM / 20 GB storage) is well below Kobo's own smallest managed configuration (quad-core / 16 GB RAM) - a gap between the stated floor and the practical recommendation that is not reconciled upstream
  • No documented RTO/RPO or disaster-recovery objective; backups (disk/S3) are provided but no restore-time or recovery-point target is published
  • Backend redundancy is not implemented (single point of failure) - no documented HA beyond the optional PostgreSQL replica
  • Feature-phone / SMS / voice collection is architecturally out of scope for KoboToolbox itself and requires the separate RapidPro platform - a boundary, not a Kobo capability, so no in-Kobo test exists for it

Safety

No physical hazard in the KoboToolbox software deployment or the off-the-shelf Android field phones; the build pack's test.safety already covers the (data-only) security concerns. All physical hazards are in the optional, locally-sourced off-grid power kit (solar panel, 12 V battery, 12 V-to-AC inverter, DC wiring), which the pack does not document or control. Safe to build only with the listed controls applied to that kit.

HazardSeverityControls
The 12 V-to-AC inverter outputs mains voltage (~230/110 V AC) to power the N100 mini PC and any connected devices. Touching a live or poorly insulated AC output, a fault to the metal case, or a missing earth is an electrocution risk, and a low-quality locally-sourced inverter can deliver unsafe output to the PC.highBuy an inverter with IEC 62109-1/2 (or IEC 61000-6-x EMC) certification, not a generic unbranded unit.; Earth the inverter frame and all exposed metalwork per IEC 60364-5-54 with a proper earth electrode.; Install a correctly rated RCD/GFCI (30 mA) on the AC output and use insulated, correctly sized mains wiring.; Route AC wiring away from the battery/bench; never splice mains leads by hand; keep terminals covered when de-energized.; Label the inverter AC output and install a visible isolator/disconnector on the AC side.
If the 12 V battery is a lithium (Li-ion / LiFePO4) pack, a poor-quality or damaged pack can vent, ignite or go into thermal runaway under overcharge, short circuit, puncture, crush or overheating - a fire that is hard to extinguish and that can release toxic fumes indoors.highSpecify a lithium pack certified to IEC 62133-2 with its own charge controller / protection (BMS) and correct charge voltage.; Use a charge controller matched to the pack chemistry (LiFePO4 vs NMC have different charge profiles); never overcharge.; Mount the pack in a ventilated, non-combustible enclosure away from the inverter and solar panel; do not install in a bedroom or enclosed wardrobe.; Protect against short circuit (fuses, insulated busbars, no bare metal on the case) and against physical damage.; Provide a way to isolate and safely store the pack; add a smoke detector in the same room.
If the 12 V battery is a valve-regulated lead-acid (VRLA) unit, it can vent hydrogen (explosive above ~4% in air) and release lead-acid electrolyte on overcharge, damage or end-of-life failure; it is also heavy and a lead-contamination risk if the casing cracks.mediumSpecify a VRLA stationary battery certified to IEC 60896-22 with the correct float/charge voltage for its chemistry.; Install in a well-ventilated space (or a vented enclosure) to keep hydrogen below the LEL; never in a sealed cupboard.; Use a compatible charge controller to avoid overcharge (the main cause of hydrogen venting and dry-out).; Handle with care to avoid casing cracks (lead/acid); provide spill containment; keep away from the inverter's heat.; Plan safe disposal / recycling of the lead-acid battery at end of life.
The inverter (the kit's main heat source) and a charging battery both generate heat; in a hot, enclosed, unventilated home or a tropical/arid climate the enclosure can overheat, accelerating battery failure or igniting nearby combustibles. A poorly sized inverter running continuously at its limit adds the risk.mediumMount the inverter in line with its ventilation requirements (clear air gaps on the vented faces); never wrap or shelf it in an airtight box.; Separate the inverter and the battery from combustibles (curtains, bedding, stored paper/wood) by the distance the equipment requires.; Size the inverter and wiring for the peak ~30 W load with margin so the inverter does not run continuously at its thermal limit.; Provide ambient-temperature derating / a fan for hot climates and check the pack's maximum operating temperature (LiFePO4 > Li-ion for heat tolerance).; Do not stack equipment so the top unit blocks the bottom unit's exhaust.
The solar panel is typically roof- or pole-mounted to face the sun: fixing it to a lightweight roof, a pole without a foundation, or an insecure rafter can let the panel come loose in wind (collapse / falling-object hazard), and working at height to install it is a fall hazard. Lifting a panel overhead in a village setting without help can injure the installer.mediumUse a PV module certified to IEC 61730-1/-2 and mount it on a structure designed for its wind load, weight and orientation in that climate.; For roof mounting, check the roof can take the dead + wind load and use a rafter/fixing (not just sheeting); for pole mounting, use a properly embedded or ballasted foundation.; Two-person lift for the panel; use a stable ladder or platform for height work, never stand on the roof ridge or on the panel itself.; Tie off or use a spotter when working at height; do not install in high wind or rain.; Keep the mounting hardware stainless or corrosion-resistant in tropical/arid humidity and re-torque at first inspection.
The DC side (solar panel to battery to inverter) runs at 12 V but with high current (a 30 W load is ~2.5 A at 12 V; a 100 W panel can push 5-8 A; charging currents are higher). Undersized or corroded DC cables, loose terminals, or reversed polarity cause voltage drop, overheating, arcing and fires at the connection points.mediumSize DC cables for the maximum charging current (not just the load current) and keep runs short; use tinned or corrosion-resistant conductors in humid climates.; Fuse the battery output and the panel output at the correct rating; use a properly rated DC-rated switch/disconnector for service.; Use crimped or bolted DC connectors rated for the current - no hand-twisted or solder-only joints; polarity-check before energizing.; Keep DC wiring away from AC wiring and from heat sources; label the + and - at each connection.; Inspect connections periodically for corrosion and re-torque.

Evidence

The strongest findings from Applied Commons research on this project:

  • KoboCollect is an Android-only companion app (phones and tablets) for the KoboToolbox platform.
  • KoboCollect cannot collect end-to-end via SMS or IVR: native SMS submission was disabled in Collect in October 2018 when Google Play restricted the SEND_SMS permission used for automated background submission (off from v1.20); workarounds are the last SMS-capable build (v1.19 APK) or manually launching the default SMS app, neither a supported scalable channel.
  • The current self-hosted KoboToolbox stack does not include Elasticsearch: per the kobo-docker README and its container diagram, the backend is PostgreSQL (with PostGIS), MongoDB, and two Redis instances (redis_main, redis_cache), now running Valkey 9.1 in current releases; the frontend is NGINX, KPI, Enketo Express, and Celery workers, plus a maintenance-page container. The question's Elasticsearch component describes an older architecture.
  • Current releases are gated behind a chain of mandatory, dated, manual database migrations: the kobo-docker README states 'Running current releases of KoboToolbox requires you to upgrade...' four times, each linking to a separate stop-the-server procedure (March 2019; between March 2019 and 2.022.44/November 17 2022; from July 7 2026 for MongoDB 8; and from September 22 2026 for the Redis-to-Valkey switchover), and kobo-install hard-fails the upgrade otherwise: 'If you do not, kobo-install will not be able to start.'
  • Kobo publishes no official CPU/RAM minimum in the current kobo-docker or kobo-install READMEs; the only 'requirements' listed are installer dependencies (Linux, Python, Docker, Compose, ports 80/443).
  • The base kobo-docker deployment runs 12 containers: 8 front-end (kpi, enketo_express, nginx, plus 5 Celery services worker/worker_low_priority/worker_long_running_tasks/worker_kobocat/beat) and 4 back-end (postgres with PostGIS, mongo, redis_main, redis_cache), plus a maintenance page.
  • The current KoboCollect version requires Android 8.0 (Oreo) or later; an earlier build is available for older devices.
  • SMS and IVR data collection is achievable via the separate RapidPro platform, whose Twilio and Verboice channels support SMS, voice/IVR, and mixing SMS and voice in a single flow.
