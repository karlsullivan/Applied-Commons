Configuration system for ESP32/ESP8266/BK72xx/RP2040 (11,783 stars, pushed 2026-10-05) that lets makers define sensors, fans, heaters, dehumidifiers and climate control in YAML and drive them from a home-automation system — the firmware layer for low-cost buildable climate/humidity hardware.

Known gaps

What the original design does not document:

  • ESPHome is firmware/software with no physical device and no bill-of-materials file: the esphome/esphome repo and the device-builder component catalog (climate.thermostat.json) document YAML/config and form fields only, not parts, quantities, or prices. Every BOM item here is therefore sourced from third-party build guides (botmonster, esp32.co.uk, acceleratenetzero, bhupiister, hackaday.io), not from esphome/esphome itself.
  • No supplier/storefront URLs are given by any retrieved source; 'where you found one' is limited to the 52pi EP-0099 I2C-relay wiki and the named converter models (HLK-PM01/LM2596). Specific datasheets, vendor part numbers, and per-region pricing are not documented.
  • No per-part price for: the 24V-to-5V buck converter, the OLED display, the pull-up resistors, the safety/fusing/isolation set, or the heating load. Only the controller core (ESP32/BME280/relay/enclosure) has concrete US$ figures.
  • ESPHome is a networked device: no retrieved source documents a fully standalone/offline BOM. It requires local Wi-Fi and a self-hosted Home Assistant (or MQTT broker) instance, which conflicts with the off-grid and patchy-connectivity constraints in the need brief.
  • The device is a DIY 24V-HVAC / resistive-load controller, not a safety-certified HVAC thermostat; safety (fusing, thermal cutoff, isolation, default-off) is builder-implemented and is not specified or certified by upstream.
  • No currency other than USD is documented, and no pricing for the target regions (e.g. sub-Saharan Africa / locally hand-tool-sourced alternatives). The 'alternatives' fields list locally-sourceable substitutes but no local cost basis.
  • Quantities beyond one per module are not documented for multi-room / multi-sensor builds (bhupiister adds optional battery-powered slave ESP32s over ESPNOW; hackaday.io adds an ESP-01 per remote sensor). This BOM is for ONE controller unit.
  • No CAD model, PCB layout, or electrical schematic for the controller hardware: ESPHome is firmware-only and the hardware (ESP32/ESP8266/BK72xx/RP2040 dev board, relay module, temperature/humidity sensor) is user-selected; upstream ships no reference PCB, board outline, enclosure CAD, or full pin-to-pin wiring schematic (only wiring/pinout diagrams for specific IR controllers, e.g. the CN105 and Haier images).
  • No canonical hardware bill of materials with part numbers, costs, or a fixed pin map is published in any of the esphome repos; the only in-repo 'builds' are the YAML test configs under tests/components/ (thermostat/common.yaml, pid/common.yaml), which reference generic test boards rather than a specific purchasable BOM.
  • The Device Builder definition catalog (components.index.json, boards.index.json, automations.index.json and per-component JSON) is generated/synced from the ESPHome source by a GitHub workflow, not hand-curated per device, so there is no single authoritative hand-written device definition to build from.
  • No standalone (no-Home-Assistant) or no-grid-power / offline / low-bandwidth deployment path is documented: the install and getting-started docs assume a USB cable for the first flash, local Wi-Fi, and a Home Assistant (or MQTT) instance; the need-brief's constraints (no grid power, patchy connectivity, no cloud) are outside what the project documents.
  • Licensing is not uniform across the stack: the core firmware is dual-licensed (C/C++ under GPL-3.0-only, Python and everything else under MIT, per LICENSE; GitHub API reports NOASSERTION), the Device Builder and Desktop repos are Apache-2.0, but the esphome.io documentation is CC BY-NC-SA 4.0 (non-commercial), so the docs cannot be reused in a commercial build without a separate licence.
  • ESPHome documents component configuration but no acceptance-test procedure or pass/fail test plan for a finished thermostat (no bench checklist, no steady-state deviation targets); the tests above are assembled from component docs, reference builds and forum reports - upstream only provides config validation (esphome config) and CI test configs
  • No electrical-safety standard mapping (UL/EN/IEC) for the loads the relays switch - certification is the builder's responsibility; the only guidance found is community advice to use UL-listed/CE-marked relay modules
  • The closest published thermostat test regime (NREL/LBNL/EPA BOPTEST 'Benchmarking Smart Thermostats') targets commercial cloud thermostats in a cloud-hosted test-case service; no published test standard covers DIY ESPHome-controlled loads
  • No automated, reproducible test harness for a running instance in the referenced repos; verification is manual (observe HA entities, logs, OTA round-trip)
  • The standalone ESPNOW build (bhupiister/DIY-Thermostat) is explicitly 'Work In Progress' - 'YAML files, if uploaded on this repo are work in progress. I will notify of stable release after testing'; its tested status is unverified
  • No long-term reliability / 10-year durability data for relay boards or continuous-duty ESP operation; guidance is component selection only
  • Offline/low-bandwidth provisioning and updating (need-brief connectivity constraint) is undocumented beyond 'HA may be off' independence - e.g. building without internet access, updating over low-bandwidth mobile
  • The 18-26 C comfort band at occupant height is not demonstrated by any retrieved source; the only measured field study (Pritoni et al 2016) measures energy (0-9% cooling, 5-8% heating savings in normal operation) and reference builds use 7-32 C bounds
  • Humidity/dehumidification control is configurable (humidity_sensor, dry_action, humidity_hysteresis default 1%) but no retrieved source documents a tested working build or acceptance target for it

Safety

Safe with the pack's listed fail-safes (fail-off, ALWAYS_OFF restore, 30C offline trip, interlocks, 300s min run/off, bounded setpoints, manual override) PROVIDED the mains-side heater path and the permanent 24VAC wiring are done by a licensed/qualified person, the relay contact current is verified against the actual heater load (10A max), the buck converter is specified (>=500mA, isolated, 24VAC input) and the enclosure/wiring is treated as a permanent installation under the local electrical code (IEC 60364 / NEC Article 347-348 / EN 60730 for the appliance-control side).

HazardSeverityControls
Mains (120/230VAC) switching via the 4-channel relay module when the unit drives a resistive heater; Songle SRD-05VDC-SL-C contacts are 10A max at 250VAC, and the pack BOM's '30V AC' spec understates the module and could mislead a builder into assuming a low-voltage part. Evidence

The strongest findings from Applied Commons research on this project:

  • ESPHome's thermostat is a climate: platform (source at esphome/components/thermostat/); it is a bang-bang controller that only triggers user-defined automations (idle_action, heat_action, cool_action, fan/swing/humidity actions) when a sensor crosses target_temperature_low/high. It has no knowledge of the load it is switching.
  • Reading the thermostat source (climate.py, thermostat_climate.cpp, thermostat_climate.h) and grepping for safety/interlock/overheat/over-current/fuse/fail-safe yields zero hits; the only 'interlock' match is the unrelated DIFFUSE fan mode. The thermostat component ships NO built-in safety interlock, over-temperature trip, over-current protection, or fail-safe logic.
  • The only interlock feature in ESPHome is the gpio switch interlock, and the docs explicitly warn it is software-only: 'a software bug (which can always happen) can still activate both switches at the same time. Similarly, at reset time (before any of ESPHome's code runs) the relay GPIO pins may have pull-ups active, so the relay may be active before ESPHome can manually deactivate them.' Hardware interlocks (e.g. SPDT-type relays) are 'highly recommended'.
  • The new ESPHome Device Builder is a from-scratch web app that replaces the legacy in-tree dashboard: the 2026.5.0 release shipped a 'public beta' with 'a real configuration editor, a firmware job queue, ... out-of-sync detection', and the 2026.6.0 release notes state it 'reached 1.0.0 this release and replaces the legacy in-tree dashboard' and is 'the dashboard bundled by default in the official Home Assistant ESPHome add-on'.
  • The 2026.6.0 release notes explicitly describe the Device Builder as a 'Visual component and automation builder alongside a CodeMirror YAML editor', with a 'Component catalog with dependency resolution and a per-board pin info viewer' — i.e. a genuine visual builder, not a plain text editor over a .yaml file (which is what the legacy dashboard was).
  • The Device Builder backend (esphome/device-builder) ships per-component visual-form definitions under definitions/components/, and the catalog index contains 33 climate platforms — climate.thermostat (Thermostat Climate Controller), climate.bang_bang, climate.pid, climate.template, plus ~29 brand IR/UART climate platforms (midea, gree, daikin, haier, tuya, ...). Each definition I fetched (thermostat, bang_bang, template, pid) carries full typed config_entries with labels, descriptions, units (°C/°F/K) and per-field help links, i.e. form fields renderable in the GUI.
  • ESPHome has three in-tree climate control platforms: bang_bang (pure on/off + hysteresis), thermostat (v1.15+, 'essentially two bang-bang controllers in one'), and pid (modulating float-output control with a Ziegler-Nichols autotuner). The bang_bang and thermostat controllers are exactly bang-bang with hysteresis, as the question assumes; pid is the PID alternative built in.
  • The default hysteresis in ESPHome's bang_bang controller is 0.5 C: around a 20 C target_temperature_low, heat_action fires at 19.5 C and idle_action at 20.5 C. The thermostat platform's per-action hysteresis (cool_deadband, cool_overrun, heat_deadband, heat_overrun) each also default to 0.5 C. This configured band is the only 'stability' number that exists in the product — it is a design parameter, not a measured figure.
