Open-source (ISC) extended fork of the iD OpenStreetMap editor maintained by Meta with AI-generated suggestion layers for roads, buildings, sidewalks, address points and trees plus a catalog of authoritative open data to validate, with per-object human review before upload. Provides the AI-assisted, human-in-the-loop building/street extraction needed to close the ~170,000 unmapped-village gap at volunteer scale; multilingual, web-based.

Assembly

Tools: Node.js >=18.18 (ESM; I verified on v26.8.2), npm 11 (npm install; npm-run-all drives run-s/run-p scripts), git (clone) — or a plain source tarball download, static-server (bundled dep; npm run start serves port 8080), esbuild (bundling), dotenvx (env), svg-sprite (icon sprites), A browser for the human-in-the-loop verification step, Any static file host for production (nginx / Caddy / Cloudflare Pages / GitHub Pages)
Skills: Node.js / npm project build and running a dev server, Serving a static web app (reverse proxy / static host) for production, OpenStreetMap OAuth2 editor client setup (client_id/client_secret + in-browser login), Open geospatial data: OSM API 0.6, Overture Maps (STAC/PMTiles), Meta ML-roads PMTiles
Time: About 10–20 minutes on a modern workstation: a few minutes to install Node + clone, ~1–3 min for `npm install`, ~1 min for `npm run all`, and a minute to start the server and confirm the page loads. A production static-host deploy adds 10–30 minutes depending on the host.

  1. Install the build toolchain Install Node.js >=18.18 (package.json engines) plus npm. The .env sets NODE_OPTIONS=$(node scripts/node_options.js) to size the heap for the build, so Node's standard memory flags apply. Verify with node --version (>=18.18) and npm --version. I verified the whole flow on Node v26.8.2 / npm 11.
    Caution: Use the pinned node >=18.18 lower bound; the project is ESM ("type":"module"), so an old CommonJS-only runtime will fail on import statements.
  2. Get the source Clone git clone github.com and cd Rapid, or download the main branch tarball (36.9 MB) and extract. Default branch is main; the repo is 1906 files. This is the only 'design file' you need to fetch — all npm dependencies and build-time data are pulled/derived from it.
    Caution: Pin to a release tag rather than tracking main if you need reproducible builds; main is an active branch (last push 2026-05-28).
  3. Install dependencies Run npm install. This installs the build toolchain (esbuild, dotenvx, static-server, gaze, svg-sprite) and the @rapid-sdk/* editor modules plus test tooling (karma, playwright, c8). Produces node_modules (~118 MB). It reads .env automatically via dotenvx.
    Caution: Allow a few hundred MB of disk for node_modules; the build also needs ~118 MB for dist/. If npm install is blocked by a network/registry policy, use an internal npm mirror.
  4. Build the app Run npm run all, which is run-s clean build dist: (1) clean stale dist artifacts, (2) build in parallel — CSS (scripts/build_css.js), the modern dev bundle (dist/rapid.js), and the data files (scripts/build_data.js writes dist/data/: imagery.json ~8 MB with 1211 imagery providers, l10n translations, languages/locales, presets, QA data, etc.), (3) dist — the minified production bundles dist/rapid.min.js (2.8 MB) and legacy bundle dist/rapid.legacy.min.js, plus all SVG icon sprites (FA, Maki, Temaki, Roentgen, Mapillary, community, rapid). I measured ~48 s on 6 cores; output dist/ is ~118 MB.
    Caution: The build is network-touching (downloads caniuse-lite/browserslist data); if offline, pre-warm the npm cache. It does not modify the OS — output is confined to dist/.
  5. Run a local instance Run npm run start (alias npm run quickstart), which re-runs the build then starts the static server (npm start:server → dotenvx node scripts/server.js). scripts/server.js uses the static-server package with rootPath=process.cwd() (the repo root) on port 8080 and followSymlink=true, and it watches css/**/*.css to rebuild CSS on change. The console prints 'Listening on 8080'. Open 127.0.0.1:8080 — the root index.html loads dist/rapid.js (dev bundle) with assetPath='dist/'.
    Caution: Port 8080 is hardcoded in scripts/server.js; change it there if it collides. The server is a plain file server with no auth — bind it to localhost (127.0.0.1) for a dev instance, not a public interface, since anyone who can reach it can load the app (edits still require a separate OSM login).
  6. Deploy to production (static host) Run npm run dist to produce the production bundle, then deploy the dist/ directory to any static host and serve dist/index.html at the site root. dist/index.html is the production-style page: it loads the minified bundle (rapid.min.js), sets assetPath='' (assets at site root), and points at the live OSM endpoints. This is how rapideditor.org/edit is served (Meta hosts it at rapideditor.org). Upstream does not ship an nginx/Dockerfile/CI deploy recipe, so this step is filled from the repo's own dist/index.html + standard static-site practice (flagged as a fill in gaps).
    Caution: Set HTTP headers (immutable caching for hashed/min assets, short-cache for index.html), enforce HTTPS, and keep the host to static files only — the app itself is stateless; all state is on the OSM API.
  7. Configure OSM editing credentials Editing/saving requires an OpenStreetMap OAuth2 client. The repo's index.html already embeds working public client_id/client_secret for two apiConnections: the live API (url openstreetmap.org, apiUrl api.openstreetmap.org) and a dev instance (api06.dev.openstreetmap.org). A private deployment should register its own OSM OAuth2 client at openstreetmap.org (or the dev equivalent) and swap in its client_id/client_secret in the served index.html. Mappers then sign in in-browser; no server-side secret is needed because it is a client-side (public) credential shipped in the JS bundle.
    Caution: The embedded client_id/client_secret are intentionally public client-side credentials (they are in the open-source bundle every browser already receives) — treat them as non-secret. Do not treat a client_id as a password; the real authentication is the user's OSM OAuth login.
  8. (Optional) Refresh the imagery catalog before building Run npm run imagery (scripts/update_imagery.js) to pull the latest community imagery catalog before npm run all, so dist/data/imagery.json is current. This is the documented way to update the 1211-provider imagery list.
    Caution: This rewrites data/imagery.json — commit or back it up before the build so the catalog change is reviewable.

Known gaps

What the original design does not document:

  • No cost breakdown for the rapideditor.org hosting stack (S3 spend, TLS, or any CDN in front of rapideditor.org) is documented in the repo; deploy.yml only shows the s3://world.ai.rapid bucket layout and the OIDC role in us-west-2.
  • Overture pmtiles URLs are resolved at runtime from the STAC catalog (stac.overturemaps.org/catalog.json); the release and per-theme .pmtiles URLs are not pinned in the repo, so the exact archives consumed change over time.
  • global_ml_roads.pmtiles (17.16 GB) has no checksum, version tag, or generation date in the repo; its provenance is only the MapWithAI license PDF linked from MapWithAIService.js.
  • Dataset services (MapWithAIService, OvertureService, EsriService, VectorTileService) register their sources at runtime via getAvailableDatasets() / STAC discovery, so the full set of per-dataset data URLs is not statically enumerable from the repo tree.
  • RELEASING.md and pages.yml describe GitHub Pages hosting for the dist/examples integration demo, but the relationship between Pages and the S3/rapideditor.org production host is not documented.
  • No infrastructure-as-code (Terraform/CloudFormation) for the S3 bucket is present; the bucket (world.ai.rapid) and deploy role ARN are referenced only as secrets in deploy.yml.
  • No production deployment recipe: upstream only documents the local npm run start. There is no documented procedure, Dockerfile, nginx/Caddy config, or CI deploy job for serving the built dist/ to the public — the production step above is filled from the repo's dist/index.html + standard static-site practice (a fill, per instructions).
  • No documented way to obtain your own OSM OAuth2 client credentials for a private deployment; the repo ships working public client_id/client_secret in index.html but never explains how to register your own.
  • AI data layers are baked to external URLs and not documented for self-hosting: Meta's ML-roads (rapideditor.org/country_exports/global_ml_roads.pmtiles) and Overture Maps (stac.overturemaps.org/catalog.json → per-theme PMTiles) are fetched at runtime from third parties. There is no documented fallback or mirror if those hosts are unreachable, and no guidance on re-hosting/re-licensing that data (Overture is CC-BY 4.0; Meta ML roads is under Meta's MapWithAI license, rapideditor.org/doc/license/MapWithAILicense.pdf).
  • No documented build resource requirements: the repo states only node >=18.18. I measured them (node_modules ~118 MB, dist/ ~118 MB, build ~48 s on 6 cores / ~11 GB RAM available) but upstream does not publish minimum RAM/disk/cores.
  • Mapillary full imagery requires a graph.mapillary.com access token (MapillaryService.js reads one) but upstream does not document how to provision that key for a local run; the editor still works for OSM + Overture + Meta-ML-roads without it.
  • No 'verify a running instance' documentation or acceptance checklist exists - CONTRIBUTING.md covers only the PR checklist (test suite passes, lint, CLA)
  • No end-to-end test of the AI data chains (ML roads PMTiles / Overture buildings): no test asserts reachability, freshness or content correctness of either layer
  • No offline test and no offline mode: the repo tree contains no service worker, IndexedDB usage or web manifest, so need-brief req 5 (offline-capable) cannot be tested
  • No accuracy metrics (precision/recall) for AI suggestions in the repository - only external publications exist (RoadTracer, arXiv 2107.12283; GlobalML Building Footprints README)
  • No declared upper Node bound: engines says >=18.18, but the unit suite fails on Node 26; CI tests only 18/20/22 and the incompatibility is undocumented
  • karma.conf.cjs LCOV report path typo: 'lcovonly: coverage/lcof.info' (should be lcov.info) - the LCOV report is written to a misspelled file and no tooling consumes it
  • Pixi renderer tests are excluded and assertion-free, documented only by a code comment in karma.conf.cjs, not in any doc
  • No test enforces the MapWithAI attribution condition (source=digitalglobe / source=maxar tags or changeset credit)
  • No performance/load budget in main CI: the Playwright benchmarks (chromium/firefox/webkit, tokyo_canned_data.zip) run only on the 'benchmarking' branch
  • No documented maintenance owner or handover: the OSM wiki marks the project 'Unmaintained' with no successor, leaving test triage ownerless

Safety

Pure-software unit with no physical build phase: no electrical, battery, gas-combustion, pressure, heat-fire, structural, water-food, chemical, mechanical, biological-medical, or radio hazards exist to control. The build is a Node.js static web app (RapiD, ISC, pinned to the 2.5.7 commit) served to browsers; installation is a static-host deploy. Residual hazards are cyber/data: XSS history (fixed in the pinned commit), AI-suggested geometry entering the shared OSM dataset, third-party data-host and unmaintained-upstream fragility, and participant privacy via OSM OAuth and third-party fetches. Safe to build and use with the listed controls; no step requires a licensed or qualified person - the required skills (npm build, static hosting, OSM OAuth client setup) are documented in the pack.

Evidence

The strongest findings from Applied Commons research on this project:

  • The April 2026 commit is real and is a pivot from server-side conflation to client-side tile conflation: commit f91f240fe37240df020dbb2e2283d448137053dc (Jennings Anderson, 2026-04-15, PR #1782) added PMTilesService.js, rewrote MapWithAIService.js to fetch the PMTiles archive client-side, and removed the mapwith.ai endpoint services; it was shipped in release 2.5.7 whose CHANGELOG entry reads 'Remove dependency on conflation through mapwith.ai';. (Note: the PR title mentions a 'MetaService', but no MetaService.js exists in the tree at that commit - the roads logic lives in MapWithAIService.js; the 'Meta' layer is the dataset id fbRoads / service id mapwithai.)
  • Serving the AI layers from locally hosted tiles is directly supported by the format and by RapiD's own dependency. The roads layer is a single self-contained PMTiles v3 file, global_ml_roads.pmtiles, measured at 17,160,384,286 bytes (~16.8 GiB), served over Amazon S3/CloudFront with HTTP range requests (accept-ranges: bytes; last-modified 2026-03-24); the buildings layer resolves through Overture's STAC catalog to tiles.overturemaps.org/<release>/buildings.pmtiles (2026-11-18.0 measured at 181,379,551,760 bytes, ~168 GiB, range 206). PMTiles is designed to be read from flat storage (S3 or local disk) via range requests with no tile-server process, so an operator can host a copy of either archive on their own storage/CDN and point the editor at it; RapiD's 'Custom Data' panel already accepts any .pmtiles or MVT vector-tile URL for this purpose.
  • The question's 'March-December 2025 inactivity' premise is partly inaccurate: the GitHub API shows exactly 8 commits on main between 2025-03-18 and 2025-12-09 (2025-06-12 to 2025-07-23: the v2.5.5 release plus security/privacy fixes). The real dead period is roughly August 2025 to February 2026, followed by a brief resumption (v2.5.6 on 2026-02-03, v2.5.7 on 2026-04-15). Open-issue count matches the question: 312 issues + 27 PRs = 339 open.
  • True offline (no network) is possible at the library level but is not wired up in RapiD as of this review. RapiD's dependency, the pmtiles npm library v4.3.0, accepts either a URL string (wrapping a FetchSource that issues HTTP fetches) or a local File/Blob via its FileSource class, whose getBytes() reads file.slice(offset,offset+length).arrayBuffer() with zero network calls; it also registers a pmtiles:// MapLibre protocol. However the RapiD source tree contains no service worker, no IndexedDB/CacheStorage persistence, and no online/offline handling (searched: serviceworker/sw.js/workbox/navigator.onLine/IndexedDB/CacheStorage/localStorage/dexie - 0 hits), and VectorTileService.js builds the archive from a remote URL template with only an in-memory zoom cache that is discarded on reload. So 'serve from local files offline' is one small app feature away (download the archive, then construct PMTiles from a Blob/FileSource) but is not shipped.
  • Self-hosting a buildings (and, via Overture's transportation theme, roads) acceleration layer that does not depend on Meta is already real and already bundled in RapiD: the buildings datasets are served from the Overture Maps Foundation (a Linux Foundation project) through OvertureService.js, which walks the Overture STAC catalog and loads the per-release buildings.pmtiles. Overture publishes each monthly release as open GeoParquet on S3/Azure plus PMTiles; its docs state the published PMTiles are 'for data inspection only' and point to the open overture-tiles repository (and docs examples) as the recipe for building your own tiles from the open GeoParquet - a natural, documented path to locally hosted, region-scoped tile archives.
  • Licensing of the Meta roads layer (relevant to hosting a local copy): the 2019 'Map With AI' license PDF (rapideditor.org/doc/license/MapWithAILicense.pdf, last-modified 2019-12-02) states the predicted 'Services Data' (roads/pathways/buildings) is provided under MIT and that if the data carries 'digitalglobe' tags the resulting OSM edit must keep the attribution (source=digitalglobe, or source=maxar); RapiD's core.yaml labels the Rapid features' license as 'Facebook's Map With AI License'. The RapiD client code itself is ISC-licensed (package.json license: ISC). So self-hosting the archive for internal use is fine, but redistribution is governed by that license/attribution rather than public-domain terms.
  • Google's technical report (arXiv 2107.12283) describes a U-Net building-detection pipeline trained on 100k satellite images / 1.75M manually labelled building instances across Africa (mixup +0.12 mAP, soft-KL self-training +0.06 mAP), which produced the 516M-footprint Open Buildings Africa dataset.
  • The three footprint products define coverage and accuracy differently (Microsoft: precision/recall/IoU/FPR on its own eval set; Google: per-cell precision thresholds, no single number; Esri: building count only), so their statistics are not directly comparable as printed. No single authoritative Sub-Saharan-Africa footprint count exists across them.
