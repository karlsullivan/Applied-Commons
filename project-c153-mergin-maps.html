Mobile field-data collection with instant two-way sync to QGIS using open GeoDiff formats: open a QGIS project on a phone/tablet, digitize and edit features in the field, merge changes automatically back to the project, and share/publish by URL; explicitly designed to work offline on mobile. Bridges the last mile between desktop GIS (QGIS) and in-the-field community data entry. Who it helps: GIS teams, NGOs and local surveyors mapping on a phone without specialist staff or always-on bandwidth. Maturity: commercially backed open-source project, GPL-2.0 (mobile client) with open GeoDiff library (MIT), ~394 GitHub stars, active (pushed on the retrieval date).

Assembly

Tools: Docker + Docker Compose (latest, per official Docker install guide for the distro), git (clone MerginMaps/server), Linux CLI: curl, openssl (for SECRET_KEY/salts generation), coreutils, AWS CLI or console (worked example: EC2 instance + gp3 volume; region of choice), QGIS desktop (any current release; minimum version not pinned by upstream - see gaps), Mergin Maps QGIS plugin (from QGIS plugin manager), Mergin Maps mobile app (Android 9+ / iOS 16+ via app stores; Windows 10/11 build from MerginMaps/mobile releases)
Skills: Docker Compose fundamentals (stacks, env files, volumes, ports), Linux sysadmin: firewall rules (open 8080, 443), directory ownership/permissions (projects dir must be writable by container users 901/101), TLS certificate installation, Basic PostgreSQL operational awareness (data dir persistence, changing default password), QGIS plugin installation and Mergin Maps project configuration, Mobile app store installation and sign-in, (optional) AWS EC2/EBS instance and volume creation
Time: 2-4 h for a first deployment including end-to-end sync verification (1-2 h to provision host + install Docker + clone/configure, 30-60 min to bring up + init + fix env issues, 30-60 min for client install + round-trip sync test); subsequent upgrades (image tag bump + re-up + flask server check) ~15-30 min

  1. Provision the host Linux host with Docker support, 8 GB RAM / 2 vCPUs (docs: 'similar to AWS t3a.large'; 4 vCPUs for >25 people who sync often), persistent disk sized by project size x expected version count, plus low latency/high bandwidth because syncs can move hundreds of MB. Worked example: aws ec2 run-instances --instance-type t3a.large with a >=100 GB gp3 data volume. us-east-1 on-demand cost (AWS pricing index published 2026-11-14): $0.0752/hr instance + $0.08/GB-month = ~$63/mo for 100 GB, before data transfer/NAT.
    Caution: Pick an isolated VPC/security group; keep SSH (22) out of the public internet (use a bastion or SSM) and expose only 8080/443 to the clients.
  2. Install Docker and Docker Compose Follow the official Docker install guide for your distribution; verify with docker compose version and add the service user to the docker group.
    Caution: Use the distro's reviewed package or Docker's official script from get.docker.com; verify the docker compose plugin version before deploying.
  3. Open firewall ports Open only 8080 (HTTP) by default; open 443 additionally when you enable SSL. All other containers talk on the internal 'mergin' Docker network.
    Caution: Do not expose 5432 (PostgreSQL), 6379 (Redis) or 8082 - the compose file never maps them to the host, but a misconfigured host firewall that forwards them defeats that.
  4. Clone the deployment files git clone the MerginMaps/server repository and cd into deployment/community.
    Caution: Pin the clone to a tag/commit you verified rather than tracking master, so an upstream push cannot silently change the compose file under a running deployment.
  5. Configure the environment file cp .env.template .prod.env, then set every 'fixme' variable: MERGIN_BASE_URL (your public https URL - used verbatim in email links), CONTACT_EMAIL (admin email), SECRET_KEY and SECURITY_BEARER_SALT / SECURITY_EMAIL_SALT / SECURITY_PASSWORD_SALT / SECURITY_UNLOCK_SALT (distinct long random strings, e.g. openssl rand -hex 32), DB_PASSWORD (must equal POSTGRES_PASSWORD in docker-compose.yml). Configure MAIL_DEFAULT_SENDER + MAIL_SERVER/PORT/USERNAME/PASSWORD if you will send mail; keep MAIL_SUPPRESS_SEND=0. Full variable reference is in the docs 'Configure environment' page.
    Caution: The compose file ships POSTGRES_PASSWORD=*** with a '!TODO change this' note - changing only one side leaves the DB unreachable; change both together. Keep .prod.env chmod 600; it holds secrets.
  6. Prepare data directories mkdir mergin_db (PostgreSQL data dir); run ../common/set_permissions.sh on the projects dir and optionally diagnostic_logs (diagnostic logs are client uploads kept on the host; remove the mount in compose if you do not want to retain them).
    Caution: These dirs are your durable state - put them on the persistent volume, back them up separately, and never delete mergin_db to 'reset' a problem (data loss).
  7. Add TLS in front (recommended) The repo ships deployment/common/ssl-proxy.conf (expects certs under ./certs/, redirects HTTP->HTTPS). Mount it on the proxy service in place of ../common/nginx.conf, map host 443, install fullchain.pem/privkey.pem, open 443 in the firewall, and set MERGIN_BASE_URL to the https URL before first init.
    Caution: Do not ship the default self-signed or test certificates to production clients; mobile browsers reject them and field staff will report 'cannot connect' rather than a TLS error. Obtain a real cert (e.g. Let's Encrypt) - upstream does not document the issuance step, only the nginx template.
  8. Start the stack docker compose -f docker-compose.yml up -d, then docker compose ps. The CE pin as of retrieval: backend+celery images lutraconsulting/merginmaps-backend:2025.7.3, frontend lutraconsulting/merginmaps-frontend:2025.7.3, postgres:14, redis:6.2.17, proxy nginxinc/nginx-unprivileged:1.27.
    Caution: Check docker compose ps for restart loops before proceeding; if the server container cannot reach db/redis it will crash-loop, and flask init will fail confusingly.
  9. Initialise the database and admin user docker exec merginmaps-server flask init - initialises the DB, creates the super-user and generates its password, and reports missing/wrong variables (e.g. unset MERGIN_BASE_URL, disabled mail). Safe to re-run if the first attempt failed (DB and super-user are not re-initialised). Add further users with: docker exec merginmaps-server flask user create <username> <password> --is-admin --email <email>.
    Caution: Store the generated admin password in a secret store immediately - it is printed to the console once and there is no recovery path other than DB access.
  10. Verify the deployment docker exec merginmaps-server flask server check (reports edition, version, database, /data permissions, celery, missing env vars), then docker exec merginmaps-server flask server send-check-email --email you@... If it prints 'Sending emails is disabled. Please set MAIL_SUPPRESS_SEND=False...' that is the docs' own expected output when mail is not configured - fix the MAIL_* variables and re-run.
    Caution: Treat any 'missing' or 'wrong' flag in the check output as a blocker for hand-over, not a warning to defer.
  11. Verify from the QGIS side In QGIS: Plugins -> Manage and Install Plugins, install 'Mergin Maps', open Configure Mergin Maps QGIS plugin, enter server URL + credentials, click Test Connection. Test Connection is the proof that proxy+server+db+celery are reachable from a real desktop client.
    Caution: Upstream does not pin the minimum QGIS version for the plugin - confirm your QGIS version against the plugin's release notes before field rollout (gap).
  12. Verify from the mobile side and run the round-trip acceptance test Install the Mergin Maps app (Android 9+ / iOS 16+ from the app stores; Windows 10/11 build from the MerginMaps/mobile repo), sign in to your server. Then: create a project in QGIS, push to the server, open it in the mobile app, digitize a feature while offline, let auto-sync merge it back, reload the project in QGIS and confirm the feature is present. This QGIS -> server -> mobile -> sync-back cycle matches the plugin README's documented quick-start workflow and is the acceptance test for the assembly.
    Caution: Test the offline path explicitly (airplane mode / no signal) before signing off - offline capture plus auto-merge on reconnect is the core field requirement, and a server reachable only over 4G will mask whether offline sync actually works.
  13. Upgrade path (repeat for each CE release) Bump the pinned image tags in deployment/community/docker-compose.yml to the next CE release, docker compose up -d, re-run flask server check. Update the QGIS plugin independently from QGIS's plugin manager. Self-hosted CE/EE releases were paused mid-2026 for the Sync API migration (community post, Aug 2026; next release planned late Oct/early Nov 2026; normal cadence CE 2x/year), so re-check the release post and the compose pin before a production cutover.
    Caution: Do not mix the new Sync API server with an old mobile app or old QGIS plugin - the pause exists precisely because cross-component compatibility breaks mid-migration; upgrade all three components together.

Known gaps

What the original design does not document:

  • No concrete storage minimum — upstream documents only the rule of thumb 'project size * number of versions'.
  • No certificate/TLS setup procedure for the CE nginx proxy (docs only recommend opening port 443 if SSL is enabled).
  • No backup/restore procedure documented for the CE deployment (env template references a MAINTENANCE_FILE 'locking file when backups are created', but no backup guide was retrievable).
  • SaaS per-tier pricing not public on the retrieved pricing page (plan price table is client-side rendered and did not extract).
  • Enterprise Edition image costs and access process are not public — private Docker Hub requiring a contract from sales.
  • No quantitative network bandwidth/latency minimums — only 'a low-latency, high-bandwidth environment is preferred'.
  • No SMTP provider recommendation or documented cost for email delivery.
  • No machine-detectable (SPDX) licence at the server repository level; the dual AGPL-3.0 / MerginMaps Commercial licence is only stated in the docs and the LICENSES directory.
  • No dollar cost figures anywhere in the retrieved docs: hosting pricing is left to the operator, and the EE (private Docker Hub) licence requires a sales contract with no public price.
  • Disk sizing is a rule of thumb only ('project size x number of versions'); no published benchmarks for sync throughput, concurrent users, or storage growth.
  • Retrieved install docs cover no backup/restore, disaster recovery, or multi-node/scaling configuration for the CE stack.
  • No guidance for low-power or low-bandwidth hosting (the deployment assumes a dedicated 8 GB/2 vCPU class host and low-latency high-bandwidth links), which is the operating context the need brief targets.
  • The mobile app is distributed via app stores rather than as a source-pinned binary; no signed release artifacts are indexed per commit.
  • Minimum QGIS version for the Mergin Maps plugin is not pinned in the official install doc - confirm against the plugin's release notes before field rollout (not documented upstream).
  • TLS certificate issuance (e.g. Let's Encrypt / certbot steps) is not documented - upstream only ships the ssl-proxy.conf nginx template; cert acquisition is left to the operator.
  • Backup/restore procedure for mergin_db and the projects volume is not covered in this section (the MAINTENANCE_FILE backup-locking env var is mentioned, but no restore steps); define one before relying on the instance.
  • External PostgreSQL is mentioned in the environment-variables doc ('Database settings') but the CE install procedure assumes the in-compose postgres:14; off-host DB setup is not walked through.
  • Data transfer, NAT gateway and cross-AZ costs are not itemised in the EC2 pricing index used for the ~$63/mo us-east-1 estimate; add a data-transfer budget line per region before committing.
  • The current CE release line (2025.7.3 compose pin; paused releases per the August 2026 community post) comes from a community forum post, not an official release-notes page - re-verify against the official channel at cutover.
  • No published end-to-end test suite or CI for the CE self-hosted deployment; only the flask server check smoke commands exist, with no automated sync round-trip acceptance harness
  • No documented load/performance benchmark for concurrent mobile syncers (how many simultaneous field devices the 2 vCPU / 8 GB sizing supports)
  • No documented backup/restore test procedure to verify a running instance recovers after a failure (notable given the disaster-response use case)
  • No published testing standard (e.g., an OGC conformance test) referenced for the GeoDiff sync protocol
  • No quantified hardware/hosting cost in dollars upstream; only component sizing (8 GB RAM / 2 vCPU) and the free-CE vs cloud-tier price points
  • No documented migration test path from the pinned 2025.7.3 build to the new sync API while releases are paused
  • No one-click conflict-merge tooling documented; conflict resolution is manual/semi-auto JSON inspection only

Safety

Software build: no physical-hardware hazards (no user assembly, mains work, gas, pressure, or medical use). The significant risks are server hardening (default credentials, plaintext transport, self-registration) and the privacy of location-referenced community WASH data (URL publishing, offline data on unmanaged devices). Every hazard below is fixable by documented configuration before exposure, so the build is safe only once those controls are applied. Categories with no applicability to a software build (gas-combustion, pressure, heat-fire, structural, chemical, mechanical, water-food, biological-medical) are noted as not applicable.

Evidence

The strongest findings from Applied Commons research on this project:

  • Mobile app minimum OS: Android 9 (and iOS 16) — this is the ONLY documented mobile floor.
  • Vendor-recommended minimum server hardware for a 'typical deployment': 8 GB RAM and 2 vCPUS, described as 'similar to AWS t3a.large' instances.
  • Self-hosted server reference footprint is a single multi-container (docker compose) node: PostgreSQL, Redis, Celery-Beat, Celery-Worker, Server, Web, NGINX; only port 8080 (and 443 for SSL) exposed. PostgreSQL can be externalized.
  • POWER FOOTPRINT IS NOT DOCUMENTED: no vendor source publishes a wattage / power-consumption figure for the CE server. The only hardware proxy is the AWS t3a.large compute reference (2 vCPU / 8 GB), implying a single small VM-class host, but no power spec is given and none should be invented.
  • NEW SYNC API status: the vendor has paused self-hosted server releases 'to avoid compatibility issues' while migrating the mobile app, QGIS plugin, dev tools and server to a new Sync API that adds 'simultaneous sync' behaviour; next EE/CE release planned late Oct/early Nov 2026. The current shipped release 2026.10.1 (2026-10-29) lists 'multiple performance enhancements and fixes for the sync mechanism' but no revised hardware sizing.
  • geodiff resolves concurrent edits by 'rebasing': on the second user's sync its changes are temporarily undone, the first user's changes applied, and the second user's changes re-applied rebased on top; non-conflicting edits merge automatically.
  • For a same-feature/same-attribute edit, resolution is last-sync-wins (the editor who syncs last is kept); the losing edit is written to a separate uploaded JSON conflict file listing the original value and both modified versions, so no data is lost.
  • Automatic merging is not supported (so a conflict / whole-file 'conflicting copy' is always produced) when data is in a non-GeoPackage format such as shapefiles, or when the database/table schema is changed while some devices still hold the older schema.
