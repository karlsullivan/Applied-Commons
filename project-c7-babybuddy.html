Self-hosted, open-source (BSD-2-Clause, ~2.9k stars, active 2026) web app that helps caregivers track infant sleep, feedings and diaper changes and learn/predict a baby's needs. Self-hosted = low-cost, locally buildable/maintainable; helps parents and new caregivers improve infant and their own sleep routines.

Evidence

The strongest findings from Applied Commons research on this project:

  • Premise confirmed from primary sources: babybuddy advertises itself to help caregivers learn about and predict baby's needs, but the codebase has no predictive model or any ML/forecasting dependency. requirements.txt is a pinned Django/djangorestframework/Plotly/Postgres stack with zero scikit-learn, numpy, pandas, torch, tensorflow, xgboost, prophet or statsmodels entries; core/models.py is pure event recording. The prediction in the marketing is a user-facing promise, not an implemented capability.
  • Default login is admin/admin, auto-created by Baby Buddy's custom manage.py migrate command whenever no superuser exists (confirmed in source: babybuddy/management/commands/migrate.py). The deployment docs say 'log in and change the default password immediately' but there is no first-run password wizard or prompt; a June 2026 external security report (issue #1075) was answered by the maintainer as an acceptable risk for home-LAN deployments, not a defect to fix.
  • The ESPHome bottle scale is human-gated: the user presses a Full button before the feed and an Empty button after; an HA automation then waits 60s (documented as 'to prevent multiple recordings as you are juggling bottles and babies') plus a 180s re-press guard, and calls babybuddy.add_feeding with type=Formula, method=Bottle, amount=(last_full_weight - last_empty_weight), and start/end from the button timestamps. It cannot log breastfeeds or solids (type/method are hardcoded).
  • The official babybuddy-mcp server (babybuddy/babybuddy-mcp) exposes grouped CRUD tools (list/create/update/delete across feedings, sleep, diaper, pumping, tummy, timers, measurements, medications, notes); its client exposes only api_get/api_post/api_patch/api_delete variants. It replaces manual typing with natural-language transcription into the same records; it adds no sensor data and no conflict handling.
  • BabyBuddy performs no reconciliation of conflicting or duplicate sensor-vs-human entries. The REST API (Django REST Framework) does only 'regular sanity checks' on writes; the scale's automation posts unconditionally with notes 'From Bottle Scale' (a label, not a dedupe key); the MCP and HA integration layers are thin CRUD wrappers. The only duplicate guardrail in the system is timer consumption: a POST that references a running timer uses the timer's start/end and stops it, so one timer cannot be double-logged. A scale entry and a manually typed entry for the same feed are stored as two separate records; the human must detect and merge/delete via UI, API PATCH/DELETE, or MCP update/delete.
  • There is no one-command backup/restore: the official docs contain no backup/restore page (verified against the full docs navigation in mkdocs.yml), and the repo has no backup management command. The only documented data-protection paths are (a) copying the /config volume and (b) Django-admin import/export of individual entry types to CSV/XLSX (docs page 'Import/Export'), which the docs themselves note gives 'not detailed information about the required data and formats'.
  • The training data is already in babybuddy, which is the key finding: no new sensor is required. core/models.py already logs Sleep (child, start, end, duration, nap flag) and Feeding (child, start, end, duration, type, method, amount) events per Child, plus DiaperChange, Weight, Temperature, TummyTime, and Child.birth_date (for age/chronological features). A sleep-feed-wake episode sequence with inter-event intervals, age, and circadian features is directly derivable from these tables. Real-world logs will be sparse and irregularly sampled, so a model for time series with missing data (e.g. low-rank matrix factorization, the approach in arXiv:1904.04780) is the right starting point.
  • The ESP32 keypad (jeroenterheerdt/Baby-Buddy-Keypad) and its ESP8266 ancestor (sfgabe Baby_Buddy_Keypad) are single-button entry paths for discrete events (diaper wet/solid, sleep start/end, feeding start/end, tummy time); they remove the phone from the loop but measure no amount. The battery/deepsleep ESP32 variant supports single-click only.
