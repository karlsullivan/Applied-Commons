Whole-building energy simulation program (1,583 stars, pushed 2026-10-02; originally under U.S. DOE/NREL) used by engineers, architects and researchers to model building energy and water use and HVAC performance — the reference open tool for predicting building thermal comfort and energy use.

Evidence

The strongest findings from Applied Commons research on this project:

  • EP-Launch is a launcher/workflow-manager GUI, not an input-authoring or model-validation tool: it browses to a folder with an IDF, selects a (user-extensible Python) workflow, runs EnergyPlus, and refreshes results via cache JSON files. It presupposes the user already has a correct IDF, so it does not reduce input-error rate for non-specialists, only run/logistics friction.
  • OpenStudio's reverse translation (IDF to OSM) is deliberately partial: per an OpenStudio developer (2014), 'Geometry and space-type definitions will usually be translated faithfully, but HVAC systems generally aren't. The resulting OSM will NOT produce the results you expect'; confirmed in 2017 as 'OpenStudio cannot read EnergyPlus HVAC... writing IDF easy, but reading it difficult'. The GUI path is therefore an authoring-from-scratch path (OSM -> forward translation to IDF), not a general drop-in wrapper for existing IDFs.
  • A single EnergyPlus simulation is single-threaded (does not use OpenMP / multiple cores for one run); a 4-core CPU gives no speedup for a single model but lets you run multiple independent models in parallel (one per core).
  • Minimal validated workflow for a simple (residential) EnergyPlus retrofit = OpenStudio-HPXML: one HPXML file as the building description, validated by an EnergyPlus Schematron so required inputs are machine-enforced; geometry by area+orientation (no 3D), solar shading via overhangs/neighbor buildings; run via run_simulation.rb (BuildResidentialHPXML -> HPXMLtoOpenStudio -> ReportSimulationOutput/ReportUtilityBills); end-to-end 3-10 seconds.
  • Run time scales approximately linearly with sub-hourly timestep resolution: in LBNL parametric runs the 15-minute loads timestep (4/hour) was ~4x slower than the 60-minute timestep (1/hour) (large office 77 s vs 18.4 s; secondary school 657 s vs 158 s; hospital 499 s vs 138 s). LBNL attributes this to 'the reduction of number of time steps per hour from 4 to 1'.
  • IDF-Editor, the bundled 'spreadsheet-like' input GUI, is fragile at version boundaries: it fails with 'too many fields' on OpenStudio-produced IDFs and even on DOE's own ASHRAE 90.1 prototype/outpatient healthcare models; the documented fix is manually editing the Energy+.idd schema file to add missing field declarations - i.e., the GUI's failure mode pushes the non-specialist into expert-level text editing of a schema file.
  • Documented non-specialist error classes from community Q&A (2014-2026): (a) cross-version hard stops - an EnergyPlus 9.5 IDF hitting a 22.2 toolchain with 'must be changed... with the IDFVersionUpdater', where the user could not find the tool; (b) IDF-Editor/.idd field-count mismatches; (c) silent partial imports of reference-building IDFs ('409 objects could not be translated'; 'Only geometry, constructions, loads, thermal zones, and schedules are supported') that a non-specialist cannot judge for validity. The dominant error class is inter-tool and inter-version boundary friction, not physics or HVAC design errors.
  • No public head-to-head quantitative benchmark of time-to-first-reliable-result or error rate (GUIs vs raw IDF, non-specialist) was found in official docs, arXiv, or community forums; the arXiv EnergyPlus literature is about ML/surrogate/control layers built on EnergyPlus, not input-creation ergonomics. Third-party comparison (2026-06) states qualitatively that the IDF format 'has a steep learning curve' and characterizes EnergyPlus's GUI as 'None (text-based IDF)'. No numbers were fabricated to fill this gap.
