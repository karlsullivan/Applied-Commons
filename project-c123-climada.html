Free, open-source (GPL-3.0, 479 stars) software framework for climate risk assessment and adaptation-option appraisal (CLIMADA-project, ETH Zurich). Quantifies hazard impact and compares adaptation measures, supporting the brief's documented benefit-cost (BCR) requirement for coastal and climate adaptation. Climate-independent software, runs year-round in cold or warm regions.

Assembly

Tools: Workstation: any modern Linux (x86-64/ARM64), macOS, or Windows machine with a terminal and an internet connection — no dedicated hardware, GPU, or server needed (CLIMADA is a Python library, not a service) — free (your existing machine), Miniforge (bundles the mamba package manager, recommended over conda for faster solving) — free, open-source, conda-forge channel — free, Python 3.11 (supported; 3.11–3.13 allowed) — free, pulled by conda, CLIMADA core package `climada` (v6.2.0 on PyPI/conda-forge; requires-python >=3.11,<3.14) — free, GPL-3.0, CLIMADA Petals package `climada-petals` (optional; adds data-generation modules such as TC_Surge, WildFire) — free, GPL-3.0, JupyterLab (optional, for the tutorials) — free, Pixi (optional, faster conda-based resolver; the documented fallback if mamba cannot solve climada-petals on Windows) — free, CLIMADA Data API (https://climada.ethz.ch/data-api/v2/) for hazard/exposure data — free, public REST, no account, Git (only for the optional install-from-source path) — free
Skills: Using a command-line/terminal (copy-paste of the documented commands), Conda/Mamba environment management (create, activate, install), Python basics: importing climada and running the shipped test module, CLIMADA domain API: Hazard, Exposures/Entity, ImpactFuncSet, ImpactCalc, Measure and CostBenefit (for the benefit-cost-ratio 'test'), Optional: reading Jupyter notebooks; Git clone/checkout for the from-source install
Time: Roughly 30–60 minutes for a first-time install-and-verify on a workstation with a normal connection: a few minutes to install Miniforge, 5–15 minutes to create and resolve the conda-forge CLIMADA environment (the dependency set is large), and the first verification run is slow because it builds the local data tree under your home directory; budget longer for the optional Petals install (very slow to resolve on Windows) and for large live-data downloads from the Data API.

  1. Install an environment manager (Miniforge/Mamba) if you don't already have one. On macOS/Linux: curl -L -O "github.com -m).sh" then bash Miniforge3-$(uname)-$(uname -m).sh; accept the license, confirm the default location, and type 'yes' to update the shell profile. On Windows: run the Miniforge installer from the GitHub release page. If you get 'command not found: mamba', open a new terminal; if prompted, run mamba init.
    Caution: Put CLIMADA's workspace in a normal subdirectory of your home/user directory and do NOT use a directory synchronized by OneDrive/iCloud/Polybox (the docs warn this breaks the install). Answering 'yes' to the shell-profile prompt is expected; it is not a risky action.
  2. Create a conda environment with CLIMADA from conda-forge. mamba create -n climada_env -c conda-forge climada. This installs the current stable CLIMADA (v6.2.0) and its full dependency set (gdal, cartopy, numba, geopandas, xarray, scipy, netcdf4, pandas 2.2, etc. per env_climada.yml). CLIMADA's dependencies are complex and 'cannot be installed with pip alone' — follow the conda path, do not try a bare pip install climada for a first deploy.
    Caution: Use mamba rather than conda: upstream reports conda often cannot solve an environment that mamba solves in seconds. The create step downloads a large dependency tree — this is a network + disk operation, not a system modification.
  3. Activate the environment. mamba activate climada_env. The prompt should show (climada_env).
    Caution: None — this only switches the active environment for the current shell.
  4. Verify the installation with the shipped test (this also 'boots' CLIMADA and builds its data tree). python -m unittest climada.engine.test.test_impact. The first run takes a while because it generates a directory tree under your home directory — per climada.conf the local_data system dir is the climada/data folder in your home and the demo dir is climada/demo/data in your home. In the end you should see 'Ok' — that is the pass criterion. This is the same check the upstream CI runs on a 3.11/3.12/3.13 x ubuntu/windows/macos matrix (with a python -c "import climada" pre-check), so passing it means the deployment matches the project's own build gate.
    Caution: The first run is slow and writes a data tree under your home directory; this is expected and is not a sign of failure. No destructive action.
  5. Optional: install CLIMADA Petals (data-generation modules) into the same environment. mamba install -n climada_env -c conda-forge climada-petals. Petals is not standalone — it requires CLIMADA Core, which is already in the environment.
    Caution: On Windows, resolving climada-petals with Conda/Mamba can take a very long time; the documented reliable fallback is Pixi. Budget extra time; do not interpret a long hang as a broken install before trying the Pixi fallback.
  6. Optional: add a code editor (JupyterLab) to run the tutorials. mamba install -n climada_env -c conda-forge jupyterlab, then mamba activate climada_env and jupyter-lab — it opens in your default browser.
    Caution: JupyterLab binds a local port; by default it listens on localhost. If you ever expose it to a network, add authentication — the docs do not cover this, so treat a non-localhost bind as something you must harden yourself.
  7. Alternative (developers only): install from source instead of conda-forge. If you already did the simple install, first remove that env (mamba env remove -n climada_env) or use a new name. Then: git clone github.com, cd climada_python, git checkout develop; mamba create -n climada_env "python=3.11.*"; mamba env update -n climada_env -f requirements/env_climada.yml; mamba activate climada_env; python -m pip install -e ./ (editable). Verify with the same python -m unittest climada.engine.test.test_impact.
    Caution: Do not mix the conda-forge and from-source installs in one environment — remove or rename first. The -e editable flag links to your local source, so source edits take effect without reinstall; dependency changes still require re-running the env-update step. On Linux you may need apt install git (sudo).
  8. Provision data for a real (non-demo) run. Only the tropical-cyclone demo hazard+exposure ship in the package; other hazards/exposures come from the Data API. In Python: from climada.util import Client; c = Client() then c.get_hazard(...) / c.get_litpop(...) / c.get_exposures(...) — data downloads and caches locally under the system dir (climada.conf: cache_enabled=true, cache_dir {local_data.system}/.apicache, cache_db .downloads.db). Supported hazard types: river_flood, tropical_cyclone, storm_europe, relative_cropyield, wildfire, earthquake, flood, hail, aqueduct_coastal_flood; supported exposures: litpop, crop_production, ssp_population, crops. To refresh the shipped system/demo data: python -c "import climada; climada.setup_climada_data(reload=True)".
    Caution: This pulls multi-megabyte-to-gigabyte datasets from climada.ethz.ch; confirm you have enough free disk before large runs (upstream does not publish size figures — see gaps). Network is required for anything beyond the TC demo.
  9. Test a running instance: run a live impact and benefit-cost-ratio calculation. Follow the 10-minute quickstart or a live BCR. Quickstart (offline demo): from climada.hazard import Hazard; haz = Hazard.from_hdf5(HAZ_DEMO_H5); from climada.entity import Exposures; exp = Exposures.from_hdf5(EXP_DEMO_H5); build an ImpactFuncSet, then from climada.engine import ImpactCalc; imp = ImpactCalc(exp, impf_set, haz).impact(save_mat=True). Live BCR (the brief's core use case): fetch a real hazard and exposure via the Client, wrap adaptation options in Measure/Entity, then from climada.engine import CostBenefit; cb = CostBenefit(...); cb.calc(hazard, entity, haz_future, ent_future, future_year=...) (haz_future and ent_future are single Hazard/Entity objects, or None for a present-only run) to get each measure's cost, averted-damage benefit, and benefit/cost ratio with present and future scenarios.
    Caution: CostBenefit.calc requires the user to supply measure costs and discount rates — no cost model ships in the package, so the BCR is only as good as the inputs you provide (flag this, don't treat a number as a published figure). Setting assign_centroids=False is a big speed saving if centroids are already assigned; the default assign_centroids=True is an expensive operation on large grids. Run on the 10-minute notebook's ~2500-centroid TC demo before scaling to a full national/global grid.

Known gaps

What the original design does not document:

  • No upstream-published minimum hardware spec (CPU cores / RAM / disk) for a single working unit; the compute-host item is an estimate from dataset sizes, not a documented requirement.
  • No published price for the compute host or internet service, so total_cost cannot be computed from upstream figures (only the free software/data/service components are priced, at $0).
  • Data API v2 docs (as retrieved) show no authentication/keys, but rate limits, quotas, availability SLAs, and data retention/versioning/expiry policies are not documented - an institutional or long-running deployment should confirm these directly with ETH/IAC.
  • Exact dataset sizes beyond LitPop (global ~0.7 GB) and one global TC scenario (~2.0 GB) are not enumerated per country/hazard in the retrieved listings, so disk planning is approximate.
  • The conda-forge binary build pins python 3.11 and exact dep versions (climada 6.2.0) while the main-branch pyproject lists a looser dev range (>=3.10,<3.13); a from-source build may need a slightly different toolchain than the binary packages.
  • No hardware/hosting spec: minimum CPU/RAM/disk, GPU use, or cloud-service recommendation is not documented anywhere in the docs or repos; all sizing in this pack is an estimate.
  • Flagship coastal-flood data not published: 'aqueduct_coastal_flood' (global probabilistic coastal flood maps ~1 km, 2/5/10/25/50/100/250/500-yr) and the 'ssp_population' exposure are named as supported in climada.conf and have data-type metadata on the API, but appear in 0 of the 8,667 live datasets, so a coastal-flood build cannot pull them as documented.
  • No coastal-flood / sea-level tutorial: doc-tree hazard tutorials cover Hail, StormEurope and TropicalCyclone only; coastal method must be assembled from Petals TC_Surge/coast modules plus the data types.
  • Two repos have no LICENSE file: climada_papers and learn-climada report no detected SPDX licence; code repos are clearly GPL-3.0 but publication/teaching content licensing is undocumented.
  • Version drift: readthedocs 'latest' shows 6.2.1-dev while the published release and the inspected commit are 6.2.0; no doc pin clarifies which docs version matches a given release.
  • Offline operation only partial: only the tropical-cyclone demo hazard+exposure ship in the package; all other hazards require the network Data API, but the deployment docs do not call out which hazards are offline-capable.
  • Dataset listing pagination is undocumented in the OpenAPI spec: the default listing is capped and requires ?limit= (used up to 50000) to retrieve all 8,667 datasets.
  • No minimum RAM or CPU specification anywhere in the docs — upstream never states the hardware floor, only that it runs on Python 3.11–3.13.
  • No disk-space requirement for the local climada data tree or for Data-API dataset downloads (setup_climada_data and Client caches) — you must size disk yourself.
  • No offline/air-gapped install procedure: only the tropical-cyclone demo hazard+exposure ship in the package; every other hazard/exposure requires network access to the ETH Data API, and there is no documented bundle-for-offline path.
  • No service/container deployment model: CLIMADA is a conda-environment Python library, not a running service, so 'deploy' and 'test a running instance' must be mapped to a local venv + verification script (this pack infers that mapping; upstream does not document it).
  • No Data-API SLA, rate-limit, or quota documentation — nothing states availability guarantees or throttling for heavy/production data pulls.
  • No multi-user / shared-server concurrency guidance (e.g., many analysts against one install or one cache dir).
  • No bundled cost model for CostBenefit: measure costs and discount rates are user-supplied, so benefit-cost outputs are not self-contained and must be treated as inputs-dependent.
  • No documented guidance on runtime/cost of large-grid runs (e.g., assign_centroids cost on national/global exposures) — only that it is 'expensive'.
  • Upstream publishes no fixed baseline data checksum/hash for a reproducible end-to-end BCR, so there are no upstream 'expected value' targets; the running-instance check was validated against the bundled demo's own computed values instead.
  • No hardware sizing / RAM guidance for high-resolution (site-specific) runs - OOM risk is only documented in the issue tracker.
  • No offline mode for non-demo hazards: only the tropical-cyclone demo hazard + exposure ship in-package; every other hazard type needs the ETH Data API (network).
  • The cost_ben_ratio attribute is named as if it were cost/benefit but the tutorial's printed 'Benefit/Cost' column is its reciprocal - this definitional trap is not called out in the docs and must be inverted before comparing to the brief's benefit-cost ratio (2-10).
  • The published make install/unit/integ_test standards were not executed in this run (they need the repo checkout and, for integ, open internet); the running-instance verification was done on the installed package's bundled demo instead.

Safety

Pure software deployment (conda/mamba install + open-data download + Python scripts). No physical build hazard in any category: electrical, battery, gas-combustion, pressure, heat-fire, structural, water-food, chemical, mechanical, biological-medical, or radio are all absent because the pack contains no physical component and does not modify the host machine. The only real risk is decision-support: CLIMADA outputs are modelled estimates that depend on user-supplied cost/discount inputs, so a BCR should not be treated as a published guarantee. All non-physical operational caveats are already documented in the pack's own test.safety, assembly, and failure_modes sections.

Evidence

The strongest findings from Applied Commons research on this project:

  • CLIMADA's core tropical-cyclone hazard (climada_python) models WIND only (Holland 2008 / Emanuel parametric wind fields from IBTrACS tracks); it has no physical storm-surge component. The 2019 GMD platform paper lists coupled rainfall+surge modelling as explicit future work.
  • Storm surge in CLIMADA is an optional add-on in the separate climada_petals package with two implementations: TCSurgeBathtub, a crude linear wind-to-surge proxy (surge[m] = 0.1023*(v-26.82)+1.8288, Xu 2010/SLOSH-based, 0.2 m/km inland decay per Pielke 1997), and TCSurgeGeoClaw, a full 2D shallow-water flow solver (up to ~270 m resolution, HPC-scale, Linux/Mac only).
  • Wind-based TC economic-damage calibration (Eberenz et al. 2021, NHESS; 473 EM-DAT matched events, 1980-2017, 53 countries): the uncalibrated default impact function biases damage by up to a factor of 36 (N-W Pacific overestimation) and factor 5 (S Indian Ocean underestimation); regional calibration brings total damage ratios to ~1 per region, but single-event damage ratios still span several orders of magnitude (post-calibration RMSF ~6-36). The authors conclude the setup is 'not suitable to represent single TC events adequately.'
  • Only tropical cyclone is runnable fully offline from bundled data. The climada 6.2.0 wheel ships the TC demo hazard (tc_fl_1990_2004.h5, Florida, IBTrACS 1990-2004, ~2500 centroids) and demo exposure (exp_demo_today.h5), and the 10-minute tutorial (TC hazard + demo exposure + Emanuel-USA impact function + ImpactCalc) completes an end-to-end impact/averted-damage calculation with no network. The wheel bundles these files and setup_climada_data() copies them into the local CLIMADA data directory at import time, so 'offline' holds from a fresh install.
  • CLIMADA outputs a directly usable per-measure benefit-cost ratio: CostBenefit.calc() returns per-measure cost, averted-damage benefit, and Benefit/Cost ratio (plus a per-measure dict, present and future scenarios, discount rates, and a combined-measures view).
  • CLIMADA contains NO physical mangrove/marsh attenuation or averted-damage function. Zero code hits for mangrove/marsh/vegetation across the full file trees of climada_python, climada_petals and climada_papers. The 'Mangrove' in the MeasureSet tutorial is a placeholder adaptation measure with an arbitrary flat hazard-intensity impact (e.g. -10), not a physical averted-damage model.
  • The GeoClaw flow solver that CLIMADA's TCSurgeGeoClaw wraps was validated (Vogt et al. 2024, Communications Earth & Environment) against satellite-based floodplain observations for a global set of 71 storms; the models overall have 'only moderate skill in reproducing the observed floodplains.' GeoClaw outperforms the two static (incl. wind->inundation/bathtub-style) approaches but over-predicts inundation (true-negative-rate 93% vs 97-99% for the static models), and a full-scale ocean model (GTSMM) reproduces tide-gauge hydrographs better than GeoClaw.
  • Because CLIMADA's TC damage is driven by wind speed only, surge- and rain-driven damage is absorbed implicitly into the calibrated wind-based impact function and is poorly represented for surge-dominated, low-wind events. The Philippines case study in Eberenz et al. 2021 shows Tropical Storm Ketsana (2009, flood/surge-driven, low wind) with an event-damage ratio of 0.002 (simulated damage >2 orders of magnitude below reported) and Typhoon Haiyan at 0.17.
