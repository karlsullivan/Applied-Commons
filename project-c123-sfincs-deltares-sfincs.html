GPL-3.0, super-fast 2D/3D numerical model of dynamic compound flooding in coastal systems (Deltares): couples storm surge, waves and pluvial/fluvial flooding for designing and evaluating nature-based coastal defence against sea-level rise. 98 stars, very active (pushed 2026-11-12).

Assembly

Tools: Docker Desktop (or Apptainer on an HPC cluster) to run the SFINCS engine, Miniforge (mamba) or Miniconda with Python >= 3.11 for the HydroMT-SFINCS builder, JupyterLab (or VS Code) for the example notebooks, git to clone the hydromt_sfincs repository, Optional, only when compiling the engine from source: Visual Studio Community 2026 + Intel oneAPI 2026.1 Fortran (IFX), building source/sfincs.sln
Skills: Conda/mamba environment management (separate env per project), Docker image pinning and volume mounting, including the Windows Git Bash path-conversion pitfall (MSYS_NO_PATHCONV=1), Python + YAML for HydroMT build configs (sfincs_build.yml) and data catalog files, NetCDF post-processing (xarray/xugrid) with NaN-aware reads, required since SFINCS v2.5.0, Fortran toolchain setup (only if compiling SFINCS from source)
Time: First-time setup is download-bound (~220 MB Docker image or 80.8 MB zip, plus a conda-forge environment) and takes under an hour on a decent connection; building and running the bundled example then takes minutes (the enso-floods-peru builder measured 9 s for the 50 m Piave compound example, 2 days of simulated time). Plan ~2-4 h end-to-end for a new user including reading the notebooks and first-run troubleshooting. This is an estimate: upstream publishes no timing or hardware benchmarks.

  1. Install and start prerequisites Two prerequisites per the project's own docs: (a) Docker Desktop installed and running (Windows/macOS/Linux) to run the SFINCS engine via container, or Apptainer on an HPC cluster; (b) for the Python model builder, Miniforge (mamba) or Miniconda with Python >= 3.11, as recommended by the HydroMT-SFINCS installation guide (mamba can be added to an existing install with: conda install mamba -n base -c conda-forge).
    Caution: Verify the Docker daemon is actually running before starting: the enso-floods-peru builder reports a 'failed to connect to the docker API ... dockerDesktopLinuxEngine' error when Docker Desktop is closed.
  2. Obtain the SFINCS engine via Docker (recommended path) Run 'docker pull deltares/sfincs-cpu' (~220 MB CPU image, workdir /data, command sfincs). For reproducible deployments pin a verified release tag instead of the floating :latest - e.g. 'docker pull deltares/sfincs-cpu:sfincs-v2.5.0-Hautacam' (tag pushed 2026-11-02; the :latest tag was re-pushed 2026-11-06). For clusters, the SFINCS manual documents Apptainer: 'apptainer exec -B $(PWD):/mnt/data --nv docker://deltares/sfincs-cpu', or pre-build an image with 'apptainer build sfincs-cpu.sif docker://deltares/sfincs-cpu:latest'.
    Caution: Pin the tag: :latest can change silently under a running deployment, and v2.5.0 contains a breaking output-format change (see run/verify step) that would alter post-processing of any model built against it.
  3. Obtain the SFINCS engine via the Deltares download portal (Windows executable alternative) Register a free account and log in to download.deltares.nl (login is mandatory), then download SFINCS_2026_02_release.zip (80.8 MB). Keep sfincs.exe at a stable location; the Windows run method is a batch file in the model folder that calls the executable by full path: call "c:\path\to\sfincs.exe" > sfincs_log.txt. The GitHub releases do not ship Windows binaries - the portal is the only exe distribution channel documented.
    Caution: Keep the executable path absolute and unchanged: the batch file and any run_sfincs(model_root, sfincs_exe=...) call hard-reference it, and moving it silently breaks every run.
  4. Install the HydroMT-SFINCS model builder Create the project's pinned environment: 'mamba env create -f raw.githubusercontent.com;. The file defines env 'hydromt-sfincs' from conda-forge with python 3.11, hydromt-sfincs=2.0.0, jupyterlab, cartopy, datashader, descartes, ffmpeg, numba_celltree>=0.4.2 (quadtree workflows). Alternative for an existing env: 'mamba install -c conda-forge hydromt_sfincs'. Note hydromt-sfincs 2.0.0 is the current PyPI release and it moved to a component-based API (sf.grid.create() etc.); the old setup_* methods are gone.
    Caution: Use a dedicated environment: the installation guide warns that if an env with the name hydromt-sfincs already exists, either remove it (conda env remove -n hydromt-sfincs) or give the new env a name with -n <name>, otherwise the create silently targets the wrong environment.
  5. Obtain the example model and data Clone the builder repository to get the notebooks and sample model: 'git clone github.com;, then 'conda activate hydromt-sfincs', 'cd hydromt-sfincs/examples', 'jupyter lab'. The examples build a sample compound-flood model (Piave river, Italy) from the bundled hydromt-artifacts data catalog; custom data catalogs are added via the -d flag on the build command or via global.data_libs in the build config. The builder also supports running the examples directly on Binder (no local install) for a read-through.
    Caution: Do not plan around the 'deltares_data' catalog for external users: the data catalog guide documents it as requiring a Deltares P: drive mount, which external users do not have - use the artifacts catalog or supply your own data yaml.
  6. Build a SFINCS model Run the 'Build from CLI' example notebook, or from the terminal: 'hydromt build sfincs path/to/built_model -i sfincs_build.yml -d data_sources.yml -vv'. The build yaml lists ordered component calls (config time range tref/tstart/tstop, grid creation with resolution/crs/rotation, elevation from the data catalog, active-cell mask from a zmin threshold, boundary types such as waterlevel with zmax), and step order is significant per the user guide. The Python-script alternative is the SfincsModel API, e.g. sf.data_catalog.get_rasterdataset('gebco', geom=sf.region, buffer=5) for in-memory data.
    Caution: Write builds against the v2.0.0 component API: scripts written against the removed v1.x setup_* methods will fail on the current hydromt-sfincs, and the v2.0.0 API note in the manual's getting-started page is the only migration signpost - check the migration guide before porting an old script.
  7. Run the model From the folder containing sfincs.inp: 'docker run --rm -v /full/path/to/model:/data deltares/sfincs-cpu' (the manual's own form is 'docker run -v C:/Users/.../SFINCS:/data deltares/sfincs-cpu' with an explicit note that a full, not relative, path must be supplied). The --rm flag, the '> sfincs_log.txt 2>&1' output capture, and the 'MSYS_NO_PATHCONV=1' prefix for Windows Git Bash come from the enso-floods-peru builder report, not the upstream manual. From Python instead: from hydromt_sfincs.run import run_sfincs; run_sfincs(model_root=model_root, sfincs_exe=sfincs_exe) - it captures stdout/stderr into sfincs_log.txt itself.
    Caution: The volume mount must be a full path: the manual warns relative paths fail, and on Git Bash an unconverted /data becomes a Windows path (C:/data), so the container sees an empty directory and the run either fails or runs on wrong inputs - the builder lists this as an observed error, not a theoretical one.
  8. Verify the running instance (the test) Read the log - sfincs_log.txt when run via run_sfincs or Docker with redirection, sfincs.log written directly by the binary: the last lines should contain 'Simulation finished'. A successful run writes two NetCDF files into the model folder: sfincs_map.nc (gridded water level zs, max water level zsmax, wave height hm0) and sfincs_his.nc (time series at observation points: water level, wave height, direction). Reference check available from a builder report: the enso-floods-peru Phase-0 test (23-oct-2026) ran the 50 m Piave example (251x108 cells, 2 days) in 9 s and obtained output identical to the Deltares reference - 7,034 wet cells, 0.0000 m difference, CSI 1.000. Peer-reviewed context: SFINCS has been validated against historical river floods at global scale (HESS 2026) and its subgrid corrections are documented in a SFINCS 2.1.1 case study (GMD 2025).
    Caution: Handle outputs NaN-aware from v2.5.0 onward: the v2.5.0 release notes state map, maximum and his output now write the fill value (read as NaN) wherever a cell/station is dry, there are no waves, or a quantity is undefined - comparing v2.5.0 NetCDFs against v2.4.x references or plotting them without NaN handling gives wrong (all-zero or all-NaN) results. Deprecated input keywords (e.g. dtout -> dtmapout) still work but log warnings.

Known gaps

What the original design does not document:

  • Minimum hardware specifications (CPU count, RAM, OS version) are not published; only an example run showing 12 threads / ~22.5 s is given, so hardware must be self-sized.
  • No bill-of-materials or cost table exists upstream; all software/data are free (freeware / GPL-3.0 / open-source) and no prices are stated, so every unit_cost is null.
  • No storage-size recommendation for a working deployment is documented.
  • Boundary/forcing data (wind, atmospheric pressure, precipitation, tide, river discharge) are described only as model input files, not as named freely-downloadable datasets; sourcing real forcing requires external providers not named by upstream.
  • The full Deltares data catalog (global products) requires Deltares P-drive access and is not publicly documented; only the bundled Piave/Northern-Italy example extract is public.
  • Deltares Support Packages and training are described as paid but no prices, tiers or durations are published.
  • Vegetation design provenance is split: the reef/mangrove wave-attenuation solver was developed in the SFINCS_veg fork's non-default feature branches (315-veggie-effect-on-mean-flow, 292-renewed-branch-vegetation-effects, 331-adapt-wave-force-limiter) and merged into upstream SFINCS main; the fork's default branch (v2.3.3) does not contain the merged vegetation code, so there is no single documented default-branch location for the vegetation design.
  • No worked vegetation input file (veg.toml lookup table or veg .inp) is committed in the SFINCS repository (verified: zero .toml and no veg .inp in the tree); the vegetation input format is specified only in the sfincs_vegetation.f90 source header and docs/parameters.rst, not by a runnable example.
  • The pre-compiled Windows binary is behind a registration portal (download.deltares.nl), not a direct open download link; GitHub releases carry 0 binary assets, so the only directly downloadable open binary is the Docker image deltares/sfincs-cpu (~220 MB).
  • Model input data (bathymetry, DEM, rainfall, river discharge, tides, wind, waves) is not stored in any of the four repositories - it is pulled at build time from the external HydroMT data catalog; the enso case study notes Deltares' own catalog points to an internal disk and required a custom catalog, so data sources are external and not version-pinned in the repos.
  • The GPU build path (NVIDIA HPC SDK, deltares/sfincs-gpu image) is mentioned in source/README.md and docs/singularity.rst but has no pinned source commit or reproducible build recipe in the indexed files.
  • The four default-branch heads are not a version-locked, tested-together set: the enso case pins hydromt_sfincs 1.2 (win-64 pixi/conda-forge) while the SFINCS v2.4.0 release notes recommend HydroMT-SFINCS v2.0.0, so a working deployment requires choosing a compatible pair.
  • Upstream publishes no minimum hardware requirements (CPU cores, RAM, disk) and no compute-time benchmarks for coastal-scale compound-flood grids; the only runtime figure found is the builder's 9 s 50 m example, so deployment sizing for real sites is left entirely to the user.
  • No HPC deployment is documented: no SLURM/queue submission scripts and no per-job resource requests - the manual shows only a single Apptainer command on 'clusters that support Apptainer', and a dedicated Linux build is offered by contacting Deltares rather than documented.
  • The v2.5.0 release notes fix GPU code paths (Neumann/downstream boundary conditions, SnapWave coupling on GPU), implying GPU builds exist, but no public GPU image or download was found in the sources retrieved - the only public Docker repo verified is deltares/sfincs-cpu (CPU).
  • The manual's Docker example omits output capture (no --rm, no stdout/stderr redirection to a log file); those details are documented only in the enso-floods-peru builder report, not upstream.
  • The 'deltares_data' data catalog is tied to a Deltares P: drive mount (unavailable to external users), and the data catalog guide shows no worked example of defining large-scale coastal inputs (bathymetry, storm-surge or tide-gauge forcing); the worked examples use the small Piave (Italy) sample data, so a full coastal deployment requires writing custom catalog yamls without a documented template.
  • docs/validation.rst and docs/numerical_implementation.rst in the public repo are heading-only stubs - test cases are named (Bates, dam break, Carrier & Greenspan, runup, Jacksonville) but no reference values, tolerances or expected outputs are published
  • The kernel's internal 'quality control testbed' (v2.0, 'doubled in number of tests' per the v2.4.0 changelog, 'further improved and extended' per v2.5.0) is not published: no test directory exists in the repo and no benchmark results are released
  • No public CI for the Fortran kernel - .github/workflows contains only Sigrid code-quality and a PR checklist; the only automated test suite published is the Python frontend (pytest, GitHub Actions)
  • No golden/reference outputs ship with the examples, so a finished deployment cannot be diffed against a known-good result
  • Wave boundary forcing via bwvfile/bhsfile/btpfile/cstfile is explicitly unfinished (marked 'work in progress', 'should not be used')
  • SnapWave vegetation wave-attenuation (the feature most relevant to the need brief's NBD requirement) is prototype status with no published field validation or recommended drag calibration for SFINCS specifically
  • No documented post-construction validation loop for deployed defences - the 'measurably reduces surge' claim in the need brief is only demonstrable by third-party practice (e.g. enso-floods-peru's Sentinel-1/Landsat CSI loop), not by an upstream SFINCS procedure
  • Published mass-conservation or runtime budget for the example models is not documented, so efficiency acceptance ('super-fast') has no reference target in the public docs

Evidence

The strongest findings from Applied Commons research on this project:

  • Minimum mandatory SFINCS input = elevation (DEM+bathymetry), active-cell mask, and the indexfile; roughness, infiltration, subgrid tables, observation points and all forcing files are optional and have defaults.
  • Upstream Deltares/SFINCS 'main' now includes a dedicated native vegetation module that did not exist in May 2026 (the prior attempt's 'no native vegetation module' finding is now outdated). It was added in the v2.4.0 Galibier release / 2026.01 (2026-06-15), per the changelog: 'Added vegetation effects in the integrated SnapWave solver'. The module is source/src/sfincs_vegetation.f90 (reads the veggiefile/veggietype_toml, populates stem height, diameter, stems/m^2 and bulk drag coefficient per cell) plus source/src/snapwave/snapwave_vegetation.f90 (XBeach-adapted vegetation wave-attenuation and wave-force routines).
  • Peak water level, pluvial/compound flood (Hurricane Harvey, Houston, TX, 25 m grid, 21 USGS water-level stations + 115 high-water-mark locations, original setup Sebastian et al. 2021): regular SFINCS NSE 0.349, MAE 1.68 m, RMSE 2.14 m, bias -0.55 m, HWM MAE 0.73 m; SFINCS with subgrid corrections NSE 0.581, MAE 1.29 m, RMSE 1.58 m; average simulated flood-depth error across the study area 73 cm. A regular 100 m grid collapses (NSE -1.988, bias +2.49 m) - subgrid corrections are load-bearing for coarse-grid accuracy.
  • Storm-surge/tide forcing needs no raw tide-gauge network: a global tide+surge model product (gtsmv3_eu_era5) is the documented default, with tide-gauge CSV or a synthetic sine tide as alternatives; the HydroMT call is a single water_level.create(...).
  • Build path is a single reproducible .yml recipe via hydromt build sfincs (CLI, no Python needed) or a short Python script; all example notebooks run online (Binder) or locally.
  • The native vegetation coupling is into the SnapWave wave solver only. It parameterises vegetation as a wave drag (incident-wave attenuation) plus an added wave force (x/y) — i.e. it damps and refracts waves, not open-water flow. It is NOT a drag term on the SFINCS core shallow-water momentum equations. Core-flow vegetation is still represented only through Manning roughness (uniform / land-sea / per-cell manningfile) and Curve-Number infiltration (sfacinf); the 'Drag coefficients' block (cdnrb/cdwnd/cdval) is wind drag, not vegetation. So the documented attenuation pathway for vegetation is wave attenuation, not subgrid flow drag.
  • The vtmvanzelst/SFINCS_veg fork (fork of Deltares/SFINCS, created 2026-05-27, 0 stars, single push) adds NO vegetation module of its own. A recursive tree diff against the parent shows the fork's only additions are one figure (docs/figures/MapChart_Map.png) and one snapwave file (snapwave_date.f90); no vegetation source is added. It was created ~10 days before the upstream feature landed, so it is a pre-feature snapshot, not the provenance of SFINCS's vegetation capability.
  • River flood extent (global, 499 historical events, SFINCS vs satellite-derived Cloud-to-Street extents): global mean CSI 0.39, hit rate 0.58, false-alarm ratio 0.49, systematic over-prediction bias E=1.24; CSI 0.42 for basins >1000 km2 upstream area, 0.29 for basins <50 km2 (under-prediction, E=0.61). Forcing with observed USGS river discharge (10 US events) raised CSI from 0.39 to 0.67; switching from ~30 m FABDEM to ~1 m 3DEP DEM raised CSI from 0.37 to 0.57 (six US events). Extent accuracy is input-limited, not solver-limited.
