Open-source (ODK Central server, Apache-2.0; ODK Collect Android app) offline-first mobile data-collection platform: field workers fill out forms on low-end Android devices with zero connectivity and sync opportunistically to a self-hosted, locally owned server. Used to collect billions of data points in challenging environments for health, agriculture, humanitarian and monitoring-and-evaluation work. Maturity: very high, active, and widely deployed in low-connectivity settings.

Assembly

Tools: SSH access to the server (root login, password from provider email), Docker Engine v23.x + Docker Compose v2.16.x or greater (server containerization), git (clone central repo + submodules), ufw (system firewall, disabled per ODK docs), nano or equivalent editor (.env, config templates), Domain registrar or free FreeDNS + DNS A-record management, Let's Encrypt (automatic, via SYSADMIN_EMAIL for cert alerts), Web browser (admin panel, health check), Spreadsheet / XLSForm authoring (form design), Android smartphone (ODK Collect app), Optional: PostgreSQL server + psql (init/migration scripts for central-sync), Optional: cron (scheduled central-sync runs)
Skills: Linux server administration on Ubuntu LTS (files, users, swap, fstab), Docker and Docker Compose operations (build, up, ps, exec), DNS / domain name configuration, Basic XLSForm form design (question types, audit row, Entity List declaration), Basic Android app configuration (QR scan, form download, offline workflow), Basic PostgreSQL administration (databases, roles, running .sql scripts) - optional sync step, Basic scheduling (cron) - optional sync step
Time: ~4-6 hours for a skilled administrator to deploy and verify one unit (server provision, domain, long docker compose build, first admin, project/form/App User setup, phone setup and offline test); add ~1-2 hours if the optional central-sync upstream PostgreSQL step is deployed.

  1. 1. Provision the Linux server Create a DigitalOcean Droplet (or equivalent) from the Docker marketplace image (version does not matter), 2 GB RAM (1 GB + 2 GB swap is the documented floor for light loads); pick region for data residency and user proximity. Cost ~$10/month per the official benchmark config ($10/month, 2 GB, 2018: ~41.2 submissions/s with 500 concurrent devices on a 250-question form); AWS alternative t2.micro 1 GB + 1 GB swap + 15 GB disk minimum.
    Caution: Choose the region deliberately if data-location requirements apply.
  2. 2. Register a domain name and point it at the server Commercial registrar (often as little as $3/year) or free FreeDNS with a fixed suffix (e.g. name.dynet.com); create a DNS A record at the registrar/DNS pointing to the server IP. Domain is mandatory: Central will not work with just an IP, and no subdirectory hosting is supported.
    Caution: None physical; FreeDNS names should be less popular to reduce Let's Encrypt certificate issues.
  3. 3. Log in and change the root password SSH in with root plus the emailed password (or Launch Console); change the password on first login (you are prompted, or run passwd).
    Caution: Change it immediately 'so that people snooping your email do not gain access'.
  4. 4. Verify Docker versions Run docker --version && docker compose version; require Docker Engine v23.x and Docker Compose v2.16.x or greater; install Docker Engine (not Desktop) for Ubuntu from the official apt repo if older.
    Caution: None.
  5. 5. Disable the system firewall Run ufw disable; web-form features need the host reachable from inside each Docker container. The docs call custom iptables/ufw configuration difficult and not recommended for most people; an upstream network firewall is the alternative.
    Caution: The docs note most Linux distros ship with the firewall disabled; if you keep a firewall, verify by curling the Central site over its public domain from inside one of the containers.
  6. 6. Download the Central software Run umask 022; git clone github.com on the server.
    Caution: None.
  7. 7. Fetch submodules cd central, then git submodule update --init to get the latest server components; the install docs call this out as required after cloning.
    Caution: None.
  8. 8. Configure the .env file cp .env.template .env, then edit with nano: set DOMAIN (bare domain, no http/https scheme) and SYSADMIN_EMAIL (Let's Encrypt uses it only for certificate alerts); leave the rest as-is unless integrating into a custom security/network environment.
    Caution: Do not change the file name; keep the file private (it carries deployment settings).
  9. 9. Mark the database upgrade touch ./files/allow-postgres14-upgrade - mostly useful for upgrades but currently necessary for fresh installs per the docs.
    Caution: None.
  10. 10. Build the containers docker compose build; it takes a long time and pauses silently at times; expect 'Successfully built' text when done.
    Caution: None.
  11. 11. Start the server and check health docker compose up -d (first start takes a while to set itself up), then docker compose ps: the central-nginx-1 row must read Up or Up(healthy); Up(health:starting) means wait a few minutes; anything else is a failure. Visit the domain in a browser - DNS may take minutes, hours, or a day to resolve.
    Caution: None; treat a non-healthy status as a stop point and diagnose before continuing.
  12. 12. Create the first administrator account cd central; docker compose exec service odk-cmd --email YOU@ADDRESS.com user-create (set a password when prompted), then user-promote with the same flags; log into the Central website. user-set-password resets a lost password. A custom mail server is recommended so account-creation and password-reset emails are delivered.
    Caution: Use a strong unique password for the admin account; it governs the whole server.
  13. 13. Set up backups and monitoring Enable host-level backups (e.g. DigitalOcean backups) plus Central's built-in backup system; set up monitoring with a Disk Utilization alert at ~90% (plus CPU/memory if comfortable).
    Caution: Running out of disk as media attachments pile up is the most common operations issue and can crash the server; upgrade storage before this happens.
  14. 14. Create the project and App User in Central In the Central web UI create a Project (a workspace for users/permissions/forms), create an App User for the field device, grant it access to the consignment forms, and generate the App User settings QR code. App Users connect from Collect and are limited to their project, unlike Web Users.
    Caution: Treat the App User QR code like a credential: if the device is lost or the code may be shared, revoke the App User in Central and create a replacement, then re-test the device.
  15. 15. Author and publish the XLSForm for status updates Build the form as an XLSForm using standard question types: geopoint for location, image and signature questions, text/integer for quantities and status; add an audit row (type=audit, name=audit; at most one per form) with optional identify-user=true, track-changes=true, and location-priority/location-min-interval/location-max-age parameters for who/when/location logging; if the same consignment is tracked across visits, declare an Entity List so updates flow to follow-up forms (offline Entity create/update works with Central + Collect v2024.3.0+, with 'Offline update' labelling and up-to-5-day holding of out-of-order submissions; known limitation: all Entities are sent to every device on every update, a privacy concern the docs flag).
    Caution: Audit-log location tracking is an invasion of privacy; Collect must inform enumerators when a form enables it, and users can disable location providers or per-form tracking.
  16. 16. Install ODK Collect on the phone and connect it Install ODK Collect (Android 8.0+; minSdk 26 in the current gradle build config, docs state Android 5+ with 10+ recommended, 4 GB RAM recommended for complex forms). First launch: tap 'Configure with QR code' and scan the App User QR code, or 'Manually enter project details' with URL and credentials; multiple servers/users = multiple Projects.
    Caution: Check device storage for forms and expected media before fieldwork; keep the QR code private.
  17. 17. Download the form and run the offline test before deployment Open 'Get blank form' and download the consignment form; confirm title/version. Test with the exact device type and form version: airplane mode, complete a realistic interview (required questions, skip paths, constraints, repeats, GPS, media), save a draft and reopen it, finalize (the form lands in 'Ready to send'), reconnect, send, and confirm the submission appears in Central with App User identity, timeStart/timeEnd, geopoint, photo/signature, and an exportable audit CSV. Use a clearly labelled practice record and remove it afterwards; repeat the drill as part of enumerator training.
    Caution: Do not start fieldwork until a device-to-server test has passed with the same device type and form version.
  18. 18. (Optional) Deploy upstream/national sync with central-sync There is no built-in Central-to-Central sync. Deploy the Apache-2.0 central-sync Go binary: create one PostgreSQL database per project and run sql_init/01_init_structure.sql and 02_init_role_and_privileges.sql with a privileged role; place the binary next to .env (ODK_CENTRAL_URL/USER_EMAIL/USER_PASSWORD, PG_HOST/PORT/USER/PASSWORD/SSLMODE) and central_config.yaml (project_id, database_name, dataset and form mappings with table names, sync_mode append_only or upsert, optional sync_app_users/sync_attachments); schedule via cron or run manually; afterwards check central_metadata.sync_runs for the run record. It syncs entity lists, submissions (incl. repeat groups), and optionally App Users without storing tokens; run sql_migrations in version order when upgrading.
    Caution: Do not commit .env - it contains credentials and tokens may be cached locally; include the attachment directory in backups.
  19. 19. (Optional) Enable project-managed encryption In the Project's Settings, enable encryption: Central generates and stores the cryptographic keys, protected by a passphrase you provide (Central never stores the passphrase); all forms in the project are updated with encryption info and mobile devices must fetch the new versions before submitting successfully; on data download you are asked for the passphrase to decrypt on the fly. Recommended by ODK over self-supplied-key encryption for most cases.
    Caution: If you lose the passphrase there is no way to recover it or decrypt the data; store it in a password manager or physically secured. Encryption does not protect the web admin panel (use HTTPS) or blank form contents, and cannot be disabled once enabled.

Testing

CheckHowPass if
Central installation is healthy after deployment (BOM assembly step verified).After 'docker compose build && docker compose up -d' on the server, run 'docker compose ps' and read the Status column of the central-nginx-1 row; confirm the Central website loads in a browser at the domain, then create an admin via 'odk-cmd user-create' / 'user-promote'.central-nginx-1 reports 'Up' or 'Up(healthy)' (a lingering 'health:starting' or any other status means the install has gone wrong); domain resolves to the Central login page.
End-to-end field data round-trip works (need: offline-first capture, no paper transcription).In Central, create a Project, upload an XLSForm and publish it, create an App User and assign the form; in ODK Collect scan the App User QR code (Configure with QR code), choose Fill Blank Form, complete it and submit; then open the form's Submissions tab and download the CSV.The submission appears in Central with the correct values and the CSV export matches; the app user is fully isolated from management functions.
Zero-connectivity capture with opportunistic sync to a self-hosted, locally owned server (need: 2.2B offline; data sovereignty).With the device's network disabled, download blank forms, fill and save them on-device; re-enable connectivity (or move to a local LAN/Wi-Fi) and let Collect auto-sync; check Central for the new submissions. Corroborate against documented deployments.Forms can be saved offline without error, and filled forms reach Central when a connection is found; matches field reports (MSF South Sudan: 'offline-first workflows to ensure no data loss'; Last Mile Health Liberia: 'functions in a fully offline environment').
Server meets the documented concurrent-submission scale (need: low-cost hardware serving rural last-mile scale).Against ODK's published benchmark, load-test a 250-question form (no attachments) with many concurrent devices, then a 5000-question form, then 5 MB attachment submissions, and measure throughput and failure rate.~41.2 submissions/s for a 250-question form with 500 devices uploading at once; ~12 submissions/s for a 5000-question form with at most ~1 failed submission per 1000 (re-submittable without issue); ~1-2 submissions/s for 5 MB submissions at 50 devices.
Backup can be taken, verified, and restored (safety: data must survive server loss).Trigger a Direct Backup via the Central API, then verify the archive: pipe the file through 'openssl enc -d -chacha20-pbkdf2' and into 'pg_restore --file /dev/null'; separately perform a test restore to a scratch database.The first 5 bytes of the decrypted stream read 'PGDMP' (valid passphrase and valid archive) and pg_restore completes without 'input file does not appear to be a valid archive'; the test restore reproduces the data. Note a restore replaces ALL data and cannot target an older Central version.
Transport and access control meet the security baseline (need: health/personal data, local ownership).Run an external TLS scan on the domain; confirm the server requires HTTPS (no bare-IP / plain-HTTP access), that App Users are isolated from Web Users, and that System > Server Audit Logs records logins, form uploads, and submission downloads.Valid TLS certificate (ODK targets an A+ rating / TLS 1.3 on its own infrastructure), HTTPS enforced, app-user accounts fully isolated from management, and administrative actions present in the audit log.
Optional end-to-end encryption works for low-trust environments (need: sensitive health data).Enable project-managed (or self-supplied key) encryption, submit an encrypted form from Collect, then attempt to view the submission in the Central web UI and via the OData feed.Only metadata (submitter, submission date) is visible in the UI/OData; the actual submission data is shown or editable only after decryption with the appropriate key (Briefcase or direct API).
Forms with repeats and complex logic are robust in the field app (safety: no silent data errors).Test any form containing repeats in ODK Collect (not the web form preview) with 0, 1, and 2 repeat instances, and open complex forms on a 2 GB vs 4 GB RAM device.No 'XPath evaluation: type mismatch - This field is repeated' crash and no java.lang.OutOfMemoryError; repeated fields resolve correctly; 4 GB RAM devices open complex forms cleanly.
Location capture is reliable in field conditions (need: geotagged last-mile data).Outdoors with a clear view of the sky, answer a geopoint question on a GPS-capable device, optionally placing a background location question at the start of the form to warm the GPS; compare a known-good and a weak-sensor device at the same site.A high-accuracy location point is obtained in a reasonable time; failures are explained by expected limits (no GPS indoors / under dense canopy) rather than by app fault, and the device runs the latest Collect (pre-v1.28 raw-sensor Android bug fixed).
The upgrade path is validated before touching production (safety: no downgrade exists).Clone the production environment and perform the full upgrade there (git pull, submodule update, 'docker compose pull && docker compose build --pull', restart), reviewing upgrade notes for every version in between and running any version-specific maintenance; then confirm the running version.The clone comes up healthy and serves data with no loss; the production upgrade is then scheduled with a 2+ hour window and a fresh backup taken first; the version is readable via the ? icon or /version.txt.

Failure modes

FailureEffectMitigation
Out-of-memory crash when opening a form (java.lang.OutOfMemoryError).Collect crashes, typically on first open of a form with heavy logic, many repeats, or 60k+ choice-list/Entity/data-file elements, or on devices with 1 GB or less RAM.Restart the device / close other apps; simplify the form (trim choice lists, split logic into two forms, cap repeats); use 4 GB RAM devices for complex forms; share the form and device info on the forum if it persists.
XPath 'type mismatch - This field is repeated' crash.The app crashes when a repeated field is used as a single value; the web form preview silently hides this and always uses the first repeated value, so it is easy to ship a broken form.Always test forms with repeats in ODK Collect using 0, 1, and 2 instances; fix with indexed-repeat()/position(), move the reference inside the repeat, ensure lookup-key uniqueness, or aggregate with join()/count().
Submission timeout / failure under weak connectivity (field report: rural and urban upload timeouts).Filled forms do not reach the server and can sit on the device; at very large form sizes ODK's own benchmark shows roughly 1 failure per 1000 submissions.Verify connectivity and speed, firewall rules, server specifications, whether the device can reach Central from a browser, and whether submissions carry large attachments; rely on opportunistic re-submission (failed submissions can be re-sent without issue).
Direct Backup via API truncated or fails mid-download.You may have no recent backup exactly when one is needed; a truncated archive will fail to restore and a Direct Backup also omits S3-stored attachments and web-form link state.Configure automated backups with error handling and alerting (curl remove-on-error pattern), verify each archive with openssl + pg_restore ('PGDMP' check), and make a full system backup in addition to Direct Backups.
Server runs out of disk space from media attachments (most common operations issue).The server can crash and become unresponsive.Set a ~90% disk-utilization alert and monitor disk/CPU/memory; upgrade storage before it fills; offload files to S3-compatible storage to reduce database load.
GPS / location capture failure.No or inaccurate geopoint: GPS does not work indoors, is degraded by dense canopy or tall buildings, weak device sensors, or (in Collect before v1.28.0) an Android raw-location-sensor bug.Keep Collect current; restart the device; enable the highest-accuracy Android location settings with all sensors on; use a background location question to warm the GPS; get a clear view of the sky; prefer newer, higher-sensor devices.
SMS submission path is unreliable and is disabled in current Collect (docs page is titled 'Disabled'; removed in v1.20+ per ODK forum over the Google Play SEND_SMS restriction).There is no dependable feature-phone / no-data submission path in current Collect; SMS can drop messages, splits into multipart above 160 characters, and does not carry media.Do not rely on SMS for data; use opportunistic data or local-LAN sync, and for outbound voice on basic phones use an ecosystem add-on (e.g. InSTEDD Verboice) rather than an ODK SMS/voice path (ODK's own voice tool is unmaintained).
Data fabrication / tampering or shared credentials by collectors.Fake or altered submissions, or reduced data reliability when credentials are shared; data is stored in shared (readable) storage on the device.Per-collector isolated App Users with QR tokens, an admin password locking settings, device biometrics/passcode and screen lock, server audit logs, and program-level fidelity checks (e.g. device-lockdown kiosk software as used by Last Mile Health).
Self-signed / offline-LAN certificate friction between Collect and an intranet Central.Collect may refuse to connect to a local Central using a self-signed CA (community reports it working on Android 5 but failing on Android 7-8 without a modified build).Use a Let's Encrypt DNS-challenge certificate (e.g. via Nginx Proxy Manager) with SSL_TYPE=customssl on a free DuckDNS-style domain, or an easy-rsa private CA with a patched Collect; always provision a proper domain even for offline deployments.
Upgrade breakage (no downgrade path).A botched multi-version upgrade can leave the server unusable, and you cannot roll back to an older Central version.First try the upgrade on a clone of production to validate the steps; review upgrade notes for every version in between; plan a 2+ hour window (more for v2025.3/v2026.1) and run version-specific maintenance (e.g. v2025.4 Postgres REINDEX); take a fresh backup immediately before and after.
ODK Web Forms (Enketo) behaves differently from ODK Collect.A form that works in the web preview can fail or behave differently in Collect (and can hide the repeat-XPath error), so testing only in the browser gives false confidence.Test the form the way users will actually interact with it; consult the XLSForm template's compatibility notes; for enumerator-mediated or offline collection, validate in ODK Collect.

Known gaps

What the original design does not document:

  • No upstream BOM exists: ODK is software, and the project documents installation procedure (not hardware parts, deployment cost, or a materials list); this BOM is assembled from ODK install docs plus current third-party pricing pages.
  • Server-scale figure is dated: the '$10/month 2 GB VPS, 500 devices, ~41.2 submissions/s' benchmark is ODK's own 2018 vendor run quoted in the install docs; the current equivalent 2 GiB DigitalOcean Droplet is $12/month per a 2026-05-01 third-party pricing guide (not re-verified by ODK).
  • No battery-life or off-grid power documentation: no battery-days figure, no solar kit; the only published figure is an implementer-tested 2,500 mAh minimum (Standard Co), and ODK's security page names a Raspberry Pi as a low-end offline-server example without any power BOM.
  • SMS submission removed: disabled in Collect v1.20+ after Google Play restricted the SEND_SMS permission — there is no documented feature-phone data path in current Collect (older v1.19 APKs are the workaround the docs cite).
  • No outbound advisory/alert delivery: ODK is a collection platform; getodk/voice (ODK's own voice tool) is archived. Outbound voice requires ecosystem add-ons (Verboice + a VoIP line/phone line whose cost ODK does not document).
  • No device prices: ODK documents device requirements (Android 5+, RAM tiers, <3-year-old Android) but prices for any model; Standard Co's tested device list is the closest published hardware reference.
  • Managed-hosting prices (SurveyLoopr from $79/month) come from a third-party blog (prices checked 2026-08-20), not from ODK; ODK's own managed price is ODK Cloud $199/$499/month (getodk.org).
  • Email-service cost not documented (providers vary); Central's built-in mail server is free but ODK recommends a dedicated service for reliable delivery.
  • arXiv search for 'ODK Collect' returned 0 results (checked 2026-10-12), so there is no peer-reviewed literature layer behind this BOM; evidence rests on ODK docs, ODK forum, GitHub, and vendor pricing pages.
  • ODK documents no purpose-built last-mile logistics workflow (consignment tracking template/XLSForm) out of the box; it ships a generic form-capture layer, so the build must author the supply-chain form, App-User roles and Entity (longitudinal record) setup itself - no such turnkey config file is published.
  • No official built-in Central-to-Central (instance-to-instance) sync is documented; the documented upstream path is the third-party Apache-2.0 central-sync tool (PostgreSQL-to-PostgreSQL) or re-upload from Collect - a manual build-pack step, not an ODK feature.
  • ODK_Pi (the only off-grid single-board deployment in scope) targets the legacy ODK Briefcase/Aggregate stack, not ODK Central, and has no licence file; it is not compatible with the Central/Collect deployment indexed above without rework.
  • posm (Portable OpenStreetMap) is explicitly marked 'no longer being maintained' in its own README and carries no licence, so it cannot be relied on for an offline-map field asset.
  • No source documents a 1-hour onboarding for a 15-year-old on this exact consignment-tracking workflow; collect's documented floor is Android 8.0 (minSdk 26) low-end smartphone, not a feature phone, so 'basic phone' is only partly met.
  • No BOM/hardware cost for a last-mile field device (phone/tablet) is specified by ODK; the only concrete hardware figures are server-side (2 GB VM ~$10/mo or t2.micro) and the ODK_Pi ~GBP35 RPi - field-end device cost is out of scope for ODK's docs.
  • ODK documents no power/energy figure (watts, battery, solar sizing) for the server or field devices; the off-grid claim rests on the RPi's 'runs off pretty much any power source / low consumption' README statement, which is not quantified.
  • The xforms-spec repository (the normative form-format spec the whole ecosystem depends on) has no licence file in the repo, so compliance reuse cannot be confirmed from an SPDX identifier.
  • No official documentation of a one-hour onboarding path for a 15-year-old enumerator; the best retrieved training checklist (airplane-mode drill, three device states) is third-party (SurveyLoopr), not official ODK material.
  • No built-in Central-to-Central (national/upstream) sync is documented; upstream sync depends on the third-party Apache-2.0 central-sync repo, whose setup lives outside the ODK docs, or re-upload from Collect.
  • Hardware floor conflict: collect-intro docs say 'Android 5 or above' while the current build config's minSdk is 26 (Android 8.0); the docs trail the build, and no docs give battery-life figures for field use.
  • No official storage or sizing guidance beyond the 2018 2 GB/$10-month benchmark and an AWS note of 15 GB disk minimum.
  • No official documentation for running Central on Raspberry Pi or other minimal/off-grid hardware; the community ODK_Pi README documents a Raspberry Pi hub for ODK Briefcase (Aggregate-era), not Central.
  • ODK verifies each Central version only on DigitalOcean and states it generally cannot provide free support for deviating install paths; other providers (e.g. AWS) are community territory.
  • central-sync documents known first-public-version limitations: minimal PostgreSQL indexing, no log rotation/retention, and no App User form/role synchronization.
  • No deployer-runnable test standard or regression suite: upstream documents only a manual happy path (Getting Started) and troubleshooting; there is no published CI suite, smoke-test script, or acceptance harness a self-hosting org can run to certify an install.
  • The scale figures (~41.2 submissions/s at 500 devices for a 250-question form; ~12/s and 1-fail/1000 at 5000 questions; 1-2/s with 5 MB attachments) are ODK's own 2018 vendor benchmark on a specific DigitalOcean tier; there is no published current, independently reproducible load-test procedure.
  • No battery-life / off-grid power test: no published figure for a full day of field work on battery or for solar charging; the only device figures are implementer-tested minimums (e.g. 2,500 mAh), and ODK names a Raspberry Pi as a low-end offline-server example without a power BOM.
  • No official offline-LAN / intranet deployment test or guide: the working pattern (free DuckDNS-style domain + Nginx Proxy Manager + Let's Encrypt DNS challenge + customssl, or easy-rsa CA + modified Collect) is reconstructed from community forum threads, not vendor documentation.
  • SMS submission is disabled in current Collect (the docs page is titled 'Submitting filled forms via SMS (Disabled)'; per the ODK forum it was removed in v1.20+ over the Google Play SEND_SMS restriction), so the feature-phone / no-data path cannot be tested or is not documented for current versions.
  • No native outbound advisory / alert delivery exists to test: ODK is a collection platform, getodk/voice is unmaintained, and the webhook route is a third-party add-on (hotosm/central-webhook) whose author notes it has not been thoroughly tested.
  • No documented end-to-end encryption interop test procedure between ODK Aggregate and ODK Central (only a prose statement that the same encrypted forms work).
  • No device conformance list: ODK publishes OS/RAM tiers (Android 5+ floor, 10+ recommended, 4 GB RAM for complex forms) but not a verified list of specific device models.
  • No self-hosted reliability SLA or uptime/chaos test: the 99.9999% uptime figure and independent penetration tests apply to ODK Cloud only; self-hosted installs carry no published uptime guarantee.

Safety

Software/data-collection deployment with no physical-assembly hazards. Safe with the listed controls for: (1) Li-ion field-device batteries and off-grid charging (pack documents a 2,500 mAh minimum and flags off-grid power as a gap, no charging controls); (2) heat/fire from local server + device chargers in flammable rural housing (VPS path removes it); (3) protection of the health/personal data the pack's test criteria collect (self-host at-rest DB encryption is an ODK-Cloud-only feature, E2E encryption opt-in, on-device cleartext storage). A licensed electrician is needed only if a builder must install a new mains point. No gas, pressure, structural, water-food, chemical, or mechanical hazards exist in the BOM.

Evidence

The strongest findings from Applied Commons research on this project:

  • Official ODK documented minimum (docs.getodk.org/collect-intro/): the only hard requirement is Android 5 or above (Android 10+ recommended for security/performance). RAM is the spec that most affects performance and crash risk: for forms with complex logic, many repeat instances, or 60k+ elements in a choice/Entity list, ODK recommends aiming for >=4GB of RAM; devices with less 'will likely work even for complex forms but may feel slow and even occasionally crash.' The official docs contain no battery-life guidance.
  • The ODK troubleshooting docs (collect-troubleshooting) document the concrete crash mode on low-end hardware: 'Fatal Exception: java.lang.OutOfMemoryError' most often occurs when opening a form, is 'particularly likely' on devices with 1GB or less of RAM, and ODK again recommends >=4GB RAM for complex forms. This is the documented crash threshold for this workload.
  • ODK's device-level SMS was inbound-only (submitting filled forms) and was disabled in ODK Collect v1.20+ (2018) because Google Play restricted the SEND_SMS permission; ODK never built device-level outbound SMS messaging.
  • No publicly available measured battery-drain / battery-day figure (in W, mAh, %/hour, or hours-per-charge) for ODK Collect on a modern $100-150 low-end Android running GPS + photos + 100+ entries/day exists in ODK official docs, the ODK forum, vendor pages, the UNHCR 2025 field guide, arXiv, or Semantic Scholar as of this check. The question's premise is correct: no battery-day figures exist in the official docs.
  • Documented developer/vendor minimum (Standard Data, which 'develops for and tests on' a fixed device list): RAM 2GB minimum, storage 1GB minimum, Android 5.0 minimum, battery 2,500 mAh minimum. Tested/supported budget devices: BLU Tank Xtreme, BLU Life LX, Motorola Moto E 2nd Generation, BLU Advance 4.0M, ASUS ZenPad 8.0 Z380M (all $100-200 class). This is the most concrete documented 'minimum that works' spec found.
  • Strongest crash-reliability field evidence: a 300-device Kenyan field test (2019, American Red Cross) ran ODK Collect v1.24.1 on 1GB-RAM Tecno SA6S phones (~$100 class, 8GB storage, Android 7.0) targeting 20-40 interviews/day. On day one up to 25/300 (~8%) units hung (ANR, black screen); after resets/updates it improved to 2-7 units freezing per day. ODK developers (Grzesiek2010, LN) concluded the device 'has just 1GB RAM, it's very little' and that the forms were too complex for the hardware, and pointed to 4GB-class RAM and Collect v1.28+ — i.e. a 1GB-RAM $100-class device does NOT reliably survive full-day GPS+photo+many-entries usage without crashes.
  • Backups: ODK's docs call a backup strategy 'critical' and recommend a FULL system backup (Postgres DB + Enketo's Redis store and keys + files, or S3 storage if used) in a different physical location. A simpler 'Direct Backup via API' exists (passphrase-encrypted pgdump) but does not re-establish Web Form links, excludes S3-offloaded attachments, and 'may fail or the downloading may break halfway' - the docs explicitly warn that unattended automated backups need error handling and alerting so you don't discover missing backups 'just when you need them'. Restores cannot target an older Central version. For a no-vendor district, this means writing and monitoring backup automation yourself.
  • Form updates to offline devices need no special mechanism: ODK Central is pull-based. Collect with App Users automatically matches and downloads updated forms when it next successfully contacts the server (default behavior); devices can also manually browse/refresh and 'Get Selected'. With a daily 2G sync, a form published to Central reaches all 50 devices by their next daily sync (~1 day latency) and every device converges on the same version automatically. A form's media attachments are downloaded together with the blank form, so form media size is part of the sync bandwidth cost.
