This project is parked: Applied Commons has catalogued it but has not written a build pack for it.

Open-source, self-hostable e-commerce platform that connects farmers, producers, and food hubs (co-ops, online farmers markets) with buyers, removing the commercial-software barrier for local food sales. Helps small producers and community food hubs get a marketplace. Maturity: very high - active repo with 1.3k stars, 801 forks, 37k commits, latest commit within days of this run.

Evidence

The strongest findings from Applied Commons research on this project:

  • Release cadence is approximately weekly: 199 non-prerelease releases between v4.2.14 (2022-09-27) and v5.7.15 (2026-10-05) = 4.1 releases/month (0.95/week) over 48.3 months, measured from the GitHub releases API.
  • A documented, actively maintained single-machine deployment exists: the ofn-install repo (GitHub API shows last push 2026-10-09, i.e. maintained this week) provides Ansible playbooks (setup/provision/deploy plus backup/rollback/db_transfer) that install Nginx + rbenv/Ruby + PostgreSQL + Redis + Unicorn onto one Ubuntu VPS; the README says the playbooks were tested on Ubuntu 16.04/18.04/20.04 (64-bit) on AWS, DigitalOcean and Scaleway, and the wiki's recommended OS is Ubuntu 20. A local Vagrant test path is documented (vagrant up, then ansible-playbook site.yml, ~20 minutes).
  • The documented self-hosted upgrade path is ofn-install's Ansible deploy.yml: deploy a specific release git tag (the playbook refuses to deploy master to production), bundle install + yarn install, rake ofn:data:remove_transient_data, assets:precompile, rake db:migrate, then swap the current symlink and restart puma and sidekiq.
  • Runtime requirements jump across versions, so lag also forces runtime upgrades: Ruby 3.0.3 (v4.2.14) -> 3.1.4 (v5.3.0) -> 3.4.8 (v5.7.15); Rails 6.1 (v4.2.14) -> 7.1 (v5.3.0) -> 7.2 (v5.7.15). The deploy playbook installs the Ruby/Node version required by each release via rbenv/nodenv, so a lagging server gets a bigger combined code+runtime+DB change in one deploy.
  • OFN core developer luisramos0 publicly stated (2019, community forum) that PWA/service-worker offline capability is not available in the codebase: 'We are very far from this in ofn with the current rails+angular solution.' A PWA proposal (2016) aimed only at app-like UX, not offline support, and was closed as a wishlist thread without implementation.
  • OFN does not publish an explicit 'minimum server spec'. The closest official guidance is the ofn-install Performance wiki: 'A typical server starts with 2 GB of memory and our biggest servers have 8 GB', with a rule of thumb of one Unicorn web worker per 1 GB of RAM (~0.8 GB each), keeping ~1 GB spare plus swap for asset precompilation and debugging.
  • Lag cost scales steeply and is measurable: an instance one year behind (v5.3.0 -> v5.7.15) must apply 32 new database migrations; four years behind (v4.2.14 -> v5.7.15) must apply 163, many destructive (dropping tables, removing columns, rewriting/deleting data) - measured by diffing db/migrate/ file sets across the release tags.
  • Migrations have been broken enough to be removed from the default migration path: 13 foreign-key migrations sit quarantined in db/bad_migrations/ (never executed by db:migrate), added in commit dc411eb42b 'Remove migrations with bad ids' (Jan 2024) together with a migration that rewrites their recorded IDs in the schema_migrations table.
