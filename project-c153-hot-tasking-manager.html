Free, open-source (Digital Public Good) web tool built for the Humanitarian OpenStreetMap Team to divide an area into assignable mapping tasks with QA/review workflow, showing which areas need mapping; self-hostable with an active roadmap (v5, FastAPI, MapLibre, planned AI integration and uMap/MapSwipe hooks). Provides the volunteer-scale orchestration the brief's 'volunteer + AI-assisted' constraint calls for (e.g. campaigns on the ~170,000 unmapped villages).

Assembly

Tools: Docker Engine >= 20.10.0 with Docker Compose v2.0.0 (documented minimums for Traefik v3.6.1), git (clone hotosm/tasking-manager, pin the commit deployed), Linux shell (env files, docker compose ps/logs, ports), psql / postgresql-client (admin-role bootstrap, pg_dump backups), Web browser (OSM OAuth registration, TM admin UI, first project), Optional for project-geometry import: QGIS + Overpass Turbo + geojson.io (GeoJSON/KML AoI files, 1 MB / 5000 km2 import limits)
Skills: Linux shell + Docker (containers, env files, ports, logs), Basic GIS file handling (GeoJSON/KML) when project areas are imported rather than drawn, OSM account setup and OAuth2 client registration, OSM mapping etiquette (instance-unique changeset comment; small, correctly attributed test edits)
Time: 2-4 hours first time: ~30 min server + Docker, ~30 min OSM OAuth + env config, ~30-60 min image pull/startup (large images), ~30 min admin bootstrap + first project + functional test; more if a domain + TLS is added for public use (not documented for the compose path).

  1. Provision one internet-connected Linux server and install Docker A modest 2-vCPU box suffices: the compose file caps the stack at 2.5 vCPU / ~1.75 GB RAM reserved (backend 1 CPU/1500 MB, cron 0.5 CPU/256 MB, DB on the same box). Install Docker Engine >= 20.10.0 and Compose v2 (older Docker: revert traefik to v2.10 per the Traefik doc). Open/plan port 3000, the default published port.
    Caution: Keep the DB named volume (tm-db-data-main) restorable: a pg_dump is the only restore path documented for this deployment.
  2. Clone the source repository git clone github.com and work on branch develop (the trunk; it is what HOT deploys to tasks-stage.hotosm.org). The repo already contains docker-compose.yml, example.env, Dockerfiles and alembic migrations, so no other download is needed.
    Caution: Pin and record the commit you deploy (develop head at research time: bef165716356f62bf6a100cbdcf293667538c2e6), because develop moves.
  3. Register an OAuth2 client application on OpenStreetMap Log in to openstreetmap.org, My Settings, register an OAuth 2.0 application with redirect URI 127.0.0.1:3000 (local) or your public https URL (production - all redirect URIs must be https except 127.0.0.1), scopes read_prefs and write_api (TM's default TM_SCOPE). Save the client ID and client secret.
    Caution: The client secret is shown only once and is a credential - store it only in the env file with restricted permissions, never in the repo.
  4. Configure the environment file cp example.env tasking-manager.env; set required TM_CLIENT_ID, TM_CLIENT_SECRET (from step 3), TM_SECRET (long random string), and confirm TM_REDIRECT_URI/TM_SCOPE match the registered app; set TM_APP_BASE_URL to the frontend URL (default 127.0.0.1:3000, public URL in production). Optional: TM_MAPBOX_TOKEN (free under 50,000 map loads/month; without it TM falls back to the free raster HOT Humanitarian Layer), OHSOME_STATS_TOKEN (required on every project-stats request), SMTP vars (TLS or SSL, not both), TM_DEFAULT_CHANGESET_COMMENT (must be unique per instance).
    Caution: Do not ship example.env placeholder values (e.g. the ohsome test token) on a public instance - generate real secrets.
  5. Start the stack docker compose --env-file tasking-manager.env up -d. Compose starts 6 services in dependency order: tm-db (postgis/postgis:14-3.3, pg_isready healthcheck, 35 s start period), tm-migration (one-shot alembic upgrade head), tm-backend (uvicorn/FastAPI, waits for migration success), tm-cron-jobs (task auto-unlock, default 2 h), tm-frontend (React build on nginx:3000), traefik v3.6.1 (port 3000; /api/ to backend :5000, everything else to frontend :3000; DB has traefik.enable=false).
    Caution: Always pass --env-file tasking-manager.env: the compose .env default otherwise triggers a 'postgres user does not exist' health-check warning. Watch startup with docker compose ps / logs; the backend healthchecks /api/docs.
  6. Verify the web interface and API Open 127.0.0.1:3000 (or the public URL) - the TM homepage should load. The interactive API docs are at /api/docs (the backend's healthcheck endpoint). A running instance of the same stack answers GET /api/v2/projects?per-page=1 with live project GeoJSON - HOT's staging API returned HTTP 200 when tested on 2026-10-14.
    Caution: None.
  7. Log in and promote your account to administrator Click 'Login to OpenStreetMap' on the frontend and authorize the app (populates the user row in the DB), then as the database owner run: psql -d tasking-manager -c "UPDATE users set role = 1 where username = '<your_osm_username>'". TM has three access levels (User, Project Manager, Administrator); only the elevated role creates projects and manages users.
    Caution: Run the psql statement against the correct database name from your env file (default tasking-manager).
  8. Create and publish the first project As administrator: 'Create a New Project'; draw the area of interest on the map or import a GeoJSON/KML file (import is the documented-preferred route - build the AoI in JOSM/QGIS, export via geojson.io). Choose a square-grid task split and tune tile size, write description and mapper instructions, set imagery and permissions, then Publish (draft projects are invisible to mappers). For geometry-heavy projects the documented builder workflow is to prepare the AoI from existing data first (e.g. process MapSwipe tasks and already-mapped areas in Overpass Turbo + QGIS and import the resulting GeoJSON to exclude tasks needing no mapping).
    Caution: Keep the AoI within the import limits - 1 MB file / 5000 km2 area by default - or raise them deliberately in the env file.
  9. Functional end-to-end test (the 'test' gate) Sign in as a mapper, lock a task of the published project (locking prevents duplicate work), open the linked OSM editor, make a small edit, save the changeset, mark the task 'done' in TM, then have an experienced mapper validate it - the core lock/map/validate workflow. Check the project stats panel loads (exercises the ohsomeNow token) and the basemap renders (HOT Humanitarian Layer if no Mapbox token).
    Caution: Keep any throwaway test edit small and correctly attributed - it lands in the shared OSM database.
  10. Put the instance online (public use only) The compose stack serves HTTP only on port 3000 (traefik ships no TLS listener). For public use add TLS termination in front of traefik (e.g. reverse proxy + Let's Encrypt), set TM_APP_BASE_URL to the public URL, and register that https URL as an additional OAuth redirect URI. This step is filled from the retrieved compose file + OSM OAuth wiki (upstream documents TLS only for the AWS path, where HOT runs ALB + ACM).
    Caution: OSM rejects non-https redirect URIs (except 127.0.0.1), so login breaks if TLS is half-configured.
  11. Operating: backups and updates (documented parts) Before any update take a database backup - the documented command is pg_dump -Fc -h <host> -U <user> -f backup.dump <db> - and the migration doc stresses migrations 'are not production ready': run them in a test environment first. HOT's AWS path updates via cfn-config (infra) then a deployment-branch git push; the versions-and-releases doc describes HOT's internal release process (feature freeze, two code reviews, tag on master), not a self-hoster's update runbook.
    Caution: Never update without the prior pg_dump; a failed migration can leave the DB inconsistent.

Known gaps

What the original design does not document:

  • No dedicated self-hosting guide in upstream docs: docs/sysadmins/ only cover AWS CloudFormation (HOT production), CI/CD, CORS, customization, migration, Traefik; there is no single 'run your own instance in production' walkthrough (docs/sysadmins/self-hosting.md returns 404).
  • No hardware sizing guidance: no RAM/disk/instance recommendation anywhere; only per-container CPU/RAM limits in docker-compose.yml and '>=100 GB disk recommended' for the AWS RDS variant in the architecture doc.
  • No TLS/HTTPS setup in the compose stack: traefik ships HTTP-only on :80; production TLS (ALB+ACM) is only documented for the AWS path.
  • No database backup/restore procedure for the docker-compose deployment (pg_dump/snapshot steps are written for the AWS RDS path only).
  • Image pull locations: compose references ghcr.io/hotosm tags; the README badges also mention a Quay mirror (quay.io/hotosm/tasking-manager) but the compose file never references it - unclear which registry is canonical.
  • No documented free basemap alternative to Mapbox in the repo (HOT Humanitarian Layer fallback is mentioned only in the example.env comment; no config for e.g. OpenFreeMap/MapTiler).
  • AI integrations (chat assistant, task assignment, difficulty estimation, validation) and external tool hooks (MapSwipe, uMap, MapRoulette) are roadmap In Progress/Planned, not shipped - any BOM line for them would be speculative.
  • No cost/TCO documentation of any kind from upstream (expected for a DPG, but it leaves the operator to price their own hosting).
  • No bill of materials with concrete hardware specs or cost figures for a self-hosted deployment; only per-container CPU/memory limits appear in docker-compose.yml (backend 1 CPU/1500MB, db 1 CPU/1500MB, cron 0.5 CPU/256MB) and RDS instance-type examples (e.g. db.t3.large) in the CloudFormation docs, with no pricing.
  • No offline / air-gapped deployment path documented: a hosted, internet-connected server, OSM OAuth2 client, and a basemap tile source are required, and there is no native offline mode (offline field capture is delegated to a separate editor/field tool).
  • Deployment documentation is AWS/CloudFormation-centric (docs/sysadmins/deployment.md); the docker-compose self-host path exists in-repo but has no dedicated self-host runbook stating minimal sizing, backup, or update steps for non-AWS hosts.
  • AI task-assignment / difficulty-estimation / validation integrations referenced in the roadmap are a proposal, not shipped, so no design or build files exist for them in this section.
  • Third-party runtime services (Mapbox basemap tiles above 50k loads/month, HeiGIT ohsomeNow API token, optional SMTP) carry their own licensing/usage terms that are not consolidated into the repo's single BSD-2-Clause statement.
  • No self-hosting runbook: docs/sysadmins/ cover only the AWS/CloudFormation production path, CI/CD, migration and Traefik; there is no single 'run your own non-AWS instance' guide (no self-hosting.md in the docs tree referenced by the dev-setup page).
  • No hardware sizing guidance: no RAM/disk/instance recommendation anywhere; only per-container CPU/RAM limits in docker-compose.yml and a '>=100 GB disk' note for the AWS RDS variant.
  • No TLS/HTTPS setup for the compose stack: traefik ships HTTP-only on :80; TLS is documented only for the AWS path (ALB + ACM certificate).
  • No database backup/restore procedure for the docker-compose deployment (the pg_dump / RDS-snapshot steps are written for the AWS path only).
  • No operator-level update runbook for a self-hosted compose instance: 'Performing Updates' is HOT's internal cfn-config + deployment-branch process and the major-release procedure is HOT's internal release process, not instructions for third-party operators.
  • No guidance on which image tag to deploy: compose defaults to the :main (develop) tag via TAG_OVERRIDE; release tags exist (v5.6.1, v5.6, v5.5.4) but the docs never say to pin a tag for a stable instance.
  • No cost basis, expected performance, or load figures for a self-hosted instance of any kind.
  • AI integrations (chat assistant, task assignment, difficulty estimation, validation) and external-tool hooks (MapSwipe, uMap, MapRoulette) are roadmap In Progress/Planned, not shipped - no assembly steps exist for them.
  • No dedicated self-hosting acceptance-test runbook: docs/sysadmins covers AWS CloudFormation (HOT production), architecture, migration, customize, CI/CD, traefik and CORS, but there is no standalone 'how to verify your own docker-compose instance works' checklist for operators.
  • No load / performance / concurrency targets (max simultaneous mappers, tasks per project, requests/second, memory under load) are documented, so scale acceptance has no published threshold.
  • No offline / air-gapped acceptance path: the instance requires an internet-connected server, an OSM OAuth2 account and a basemap tile source, and there is no native offline mode to test.
  • No documented end-to-end (browser) test of the full lock->map->validate flow; the frontend suite is jest component/unit + eslint only, and the software-testers group validates manually on staging rather than via an automated E2E gate.
  • No security / penetration-test report or OWASP checklist beyond the CORS 'tiny steps'; there is no documented per-role authorization matrix test (ADMIN/PROJECT_MANAGER/VALIDATOR/BEGINNER permission boundaries).
  • The canonical full backend test command is ambiguous across docs: CI runs pytest tests/api/unit/ and pytest tests/api/integration/, while development-setup.md documents python3 -m unittest discover tests/backend - the repo contains both tests/api and tests/backend trees and upstream does not state which is the complete set.
  • No availability/SLA or uptime-verification procedure is documented for a running instance (only the container-level compose healthchecks).
  • The AI-integration test plan (fAIr task-level prediction, difficulty scoring, iD AI assist) does not exist because those features are unshipped (proposal only, #7310).
  • No documented production hardening test that verifies EXTRA_CORS_ORIGINS is actually set (the default when unset allows all origins, a safety-relevant default).

Safety

Safe to build with the listed controls. No physical licensed-trade step is required, but public deployment realistically requires competent ops: add TLS in front of traefik, close the exposed 5678 debugger port, pin a release image tag, and put automated off-site backups in place before any update. A non-specialist should run the instance on 127.0.0.1 until TLS and a host firewall are configured. Note: the pack has no self-hosting runbook (upstream docs cover only the AWS/CloudFormation production path), which is itself a control gap.

HazardSeverityControls
The compose stack is HTTP-only: the traefik entrypoint is :80 with no TLS listener, and the only TLS path in the docs is AWS (ALB + SSL certificate). A public self-hosted instance therefore serves OSM OAuth tokens and session cookies over cleartext HTTP. The pack's own gap list confirms no TLS is documented for the compose path.highTerminate TLS in front of traefik (reverse proxy + Let's Encrypt / ACM) and set TM_APP_BASE_URL to the https URL; register that https URL as an OSM OAuth redirect URI, since OSM rejects non-https redirect URIs except 127.0.0.1; run on 127.0.0.1 only until TLS is in place
docker-compose.yml publishes a Python debugger (DebugPy) port on the backend (ports: 5678:5678 #DebugPy). The pack never mentions this port and gives no host-firewall guidance. If 5678 is internet-reachable on a public VPS, an attacker can attach a live debugger to the running backend process, a remote-code-execution-class exposure (effectively high if reachable; rated medium because reachability depends on host firewall posture the pack leaves to the operator).mediumRemove or comment out the 5678:5678 mapping in docker-compose.yml for production; if kept for debugging, block it at the host firewall (ufw/iptables); configure a default-deny inbound host firewall exposing only 3000
The prebuilt backend/migration/cron images default to the moving :main tag (TAG_OVERRIDE) that tracks the develop branch. The pack tells the operator to pin the git commit they deploy, but pinning the repo commit does not pin the prebuilt ghcr.io images, so the deployed binary can change out from under them (untested or compromised). The pack's own gap list flags 'no guidance on which image tag to deploy'.mediumPin a release tag (e.g. v5.6.1, the 2026-09-04 release confirmed via GitHub API) via TAG_OVERRIDE, or build from source at the pinned commit with TARGET_TAG=prod; record the exact image digest; upgrade deliberately rather than tracking develop
The only documented restore path is a manual pg_dump. The migration doc states migrations 'are not production ready. Therefore, please do always backups and run the migration first in a testing environment.' The pack documents a one-off pre-update pg_dump but provides no scheduled/off-site backup, no restore test, and no self-hoster staging environment, so a failed update or migration can lose the instance's project data with no verified recovery.mediumSchedule automated pg_dump (or RDS snapshot) to off-site storage; periodically restore into a scratch DB to verify the backup; run every migration in a throwaway staging stack before the production one; always keep at least one verified backup
Admin bootstrap is an unguarded raw SQL elevation: psql -d tasking-manager -c 'UPDATE users set role = 1 where username=<osm_user>'. A typo in the username, the wrong database name, or a missing/failed WHERE clause promotes unintended users to administrator. The pack notes the correct-DB-name caveat, but the intended audience is non-specialists.lowSELECT the row first to confirm a unique username; confirm the DB name from the env file; run the UPDATE from a restricted psql client; do not run an interactive shell where a bare UPDATE is easy to type
The OSM OAuth client secret (shown only once), TM_SECRET (frontend/backend shared secret), SMTP password, and Mapbox/ohsomeNow tokens are all required. A weak or placeholder value (e.g. the example.env ohsome test token) left on a public instance enables session forgery and data tampering.mediumGenerate a strong random TM_SECRET and a real SMTP app password; store secrets only in tasking-manager.env with 0600 permissions and never in the repo; do not ship example.env placeholder values
The end-to-end test has a (possibly non-specialist) mapper make a real edit to the live global OpenStreetMap database via the write_api scope. An incorrect or misattributed test edit pollutes the shared map for everyone.lowKeep test edits small and correctly attributed (the pack's note); prefer a test-only project or a local/sandbox OSM server; use an instance-unique changeset comment (TM_DEFAULT_CHANGESET_COMMENT)
The primary path is a cloud VPS (no operator electrical work, N/A). On the local path (an x86_64/arm64 Linux box in a home/farm/village) it is a standard mains-powered server on a normal outlet; the pack adds no unusual wiring. In areas with unstable mains or generator power, a surge or power loss can corrupt the Postgres volume.lowUse a standard grounded outlet; for unstable power, a UPS on the box; the pack keeps the DB on a restorable named volume (tm-db-data-main) so a dirty shutdown can be recovered from pg_dump
A single modest box (compose caps the stack at ~2.5 vCPU / ~1.75 GB RAM) is a very low thermal load, no fire risk beyond any standard server, unless it were enclosed in an unventilated space.lowLeave normal server ventilation in place; do not enclose the box in a sealed or insulated enclosure

Evidence

The strongest findings from Applied Commons research on this project:

  • Task polygons are exportable for offline work: the project-detail UI has a 'Download Tasks Grid' button (all task polygons as GeoJSON via /projects/<id>/tasks/?as_file=true) and a 'Download AOI' button (project area of interest as GeoJSON via /projects/<id>/queries/aoi/?as_file=true), both verified in TM source code.
  • MapSwipe has a production pipeline that converts AI/crowd-verified extraction output into HOT Tasking Manager task geometry: volunteer tile classifications are filtered (unreliable answers dropped), merged into at most 15-tile task shapes where >=35% of users said a building is present, aggregated onto a 500x500m grid, and exported as hot_tm_{project_id}.geojson 'ready to use in the HOT Tasking Manager'.
  • HOT's official 2025 Tasking Manager roadmap (TM product owner blog, Feb 2025) explicitly plans the 'planned AI integrations' from the question: 'AI-driven task management, introducing support for task assignment and difficulty estimation', plus 'integrations with MapSwipe, uMap, and MapRoulette to create a seamless user experience from data generation to validation' - confirming task assignment, difficulty estimation, and validation are the named integration points.
  • The ~170,000 unmapped villages figure is real and current: an OSM analysis of the Dec 7 2024 planet file found at least 170,000 unmapped village places (Asia 113,895 / 67%, Africa 51,443 / 30%, rest ~3%), with the layers published for reuse by mapathons and challenges.
  • TM is a web app; its core workflow (login, project/task browsing, locking a task, marking done, validation) requires a live connection to the instance and it has no native offline mode. A repo-wide issue search for 'offline' (19 hits) is dependency-bump and bug noise; no offline feature or roadmap issue was found.
  • Selected-task boundaries can also be exported as OSM XML (/projects/<id>/tasks/queries/xml/?as_file=true, filename HOT-project-<id>.osm) and as GPX (/projects/<id>/tasks/queries/gpx/?as_file=true), both implemented in the TM backend.
  • A documented field workflow (OSM diary, Missing Maps) pre-selects TM tasks from MapSwipe output by subtracting already-mapped OSM buildings (building=yes, landuse=residential) so 'any tasks that do not require mapping' are omitted from the project - direct evidence that pre-screened extraction output cuts manual mapping effort.
  • Pre-extracted building footprints have already been imported as TM task geometry in a real project: the Tanga (Tanzania) building import (HOT TM project 11112, 2021) documented loading ARU-TCRA pre-extracted footprints per task into JOSM alongside OSM data, conflation, building-by-building review against imagery, and upload via a dedicated import account.
