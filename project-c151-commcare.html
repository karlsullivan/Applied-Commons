The safety review found hazards that need controls when building or using this design.

Open-source (CommCareHQ, BSD-3-Clause) server + mobile platform described as 'the world's largest platform for designing, managing, and deploying robust, offline-first, mobile applications to frontline workers worldwide,' including community health workers. Offline-first apps keep full continuity of service with no connectivity and sync when available. Maturity: high, production platform (dimagi/commcare-hq, 524 stars, active).

Known gaps

What the original design does not document:

  • Field device model and unit price: Dimagi documents selection criteria only; JSI eCHIS case mentions ~300 high-spec tablets with no price.
  • Backup/DR hardware cost: described qualitatively (double storage cost or a second host), no figure.
  • SMS gateway device, SIM and airtime costs: listed as cost categories, no figures; operator per-message rates not published.
  • Sizing Buckets page (1k/2k/5k users) is an empty stub in current docs ('Infrastrucutre required for 1k,2k,5k users', no table); the resource model cannot size a new project (needs baseline load data from an existing deployment).
  • No power/solar kit or off-grid deployment guidance for the HQ server; power appears only as continuous-operation cost in the self-hosted model.
  • OS support license cost mentioned but not priced.
  • Personnel/administration cost rated qualitatively only (Low/Medium/High/Very high by deployment size), never quantified in dollars.
  • IVR/voice-call costs not published (messaging docs describe IVR support but no rates).
  • One-time install labor cost (professional services) not documented; Dimagi's open-source forum threads acknowledge self-hosting is 'extremely complicated' and supported by a small dedicated team.
  • No solar/off-grid power design: the HQ server is sized for a grid-powered monolith (>=32 GB RAM / 2 TB SSD, EC2 t3.2xlarge class) with no small solar-plus-battery deployment, power kit, or 8h/day off-grid sizing documented anywhere.
  • No field-device hardware bill of materials: only a 'Mobile Device Selection' doc exists (not in-repo); no device part numbers, procurement path, or $30-class handset list for the frontline Android client is provided.
  • commcare_resource_model carries no LICENSE file, so its licence is 'unknown' and its two sizing configs (echis.yml, reach_40k.yml) cannot be cleanly reused under an open licence.
  • No offline agricultural-advisory content/templates bundled: agriculture is a supported sector (pre-loaded offline content + SMS) but no ready-made smallholder advisory app, content dataset, or feature-phone delivery path is shipped.
  • No multi-hazard early-warning or radio-integration design: messaging is SMS/IVR/one-way+two-way to registered cases only; there is no hazard monitoring, community-broadcast, or radio-pillar design (not a WMO four-pillar EWS).
  • Feature-phone (J2ME) support is legacy and dormant: dimagi/commcare-j2me has no README and its last commit predates 2016; Android is recommended for all new projects, so low-end feature-phone operation is not a maintained design.
  • No containerised production deployment: running CommCare HQ in Docker is explicitly 'not supported/optimized for production' (dev only), so no docker-compose / container build design is provided.
  • No per-message SMS unit cost in-repo: self-hosted SMS cost depends on a third-party gateway (phone, SIM, credits, possible Telerivet subscription); the public pricing page lists hosted tiers ($100-$4,000+/mo, $2/mo per additional mobile user) but not a self-hosted per-SMS rate.
  • sizing-buckets.rst (the referenced new-project hardware guide) is nearly empty in the public repo - just the title 'Infrastructure required for 1k,2k,5k users'; new-project hardware must be inferred from the deployment-options table (single server <1,500 users) and the 5b-hardware-mgmt reference server (16-core/64GB, ~$5k)
  • No power budget, solar/UPS sizing guidance, or off-grid deployment documentation for the HQ stack - a solar-plus-battery kit cannot be sized from upstream docs
  • No published benchmark for the lowest-cost device segment (e.g. $30-100 phones); Dimagi's device catalog covers mid-range models and explicitly says to test unlisted phones yourself
  • J2ME/feature-phone support (commcare-j2me, Apache-2.0) is legacy: repo dormant since 2019-10 and 2014-era forum advice (Nokia C2-01) - no current feature-phone deployment path is documented
  • No documented end-to-end field endurance test (full-day battery, weak-signal sync duration) for the mobile client; the device-selection doc recommends testing battery life but provides no protocol or pass criteria
  • commcare_resource_model only works with a measured baseline (cannot size a new project) and its eCHIS config notes 'compute calculations are incorrect' (storage only)
  • SMS-triggered alerts require the worker device to sync with the server to fire - the docs do not quantify how stale the device state can be before scheduled reminders are skipped
  • Published test standards (e.g. ISO 27001/27017) are not claimed; the security guide points to industry references (NIST SP 800-123, BICSI 002-2019, Cisco/Oracle architectures) but does not certify conformance to any

Safety

Software + COTS hardware: no building, fuel, pressure, chemical or medical hazards. Uncovered gaps are all environmental: mains power quality for the always-on server, thermal siting/ventilation, and Li-ion charging practice; the pack's data-security controls are strong and already covered. Off-grid (solar/inverter/generator) power is explicitly outside the pack's scope and would need its own review.

Evidence

The strongest findings from Applied Commons research on this project:

  • The Android client's minimum supported OS is now Android 6.0 (API 23), effective from CommCare Android 2.60.0, which dropped Android 5.0 and 5.1 (previously the floor was Android 5.0 since 2.54, 2024). Confirmed three ways: the official Compatibility Map, the 2.60.0 forum announcement, and the 2.60.0 GitHub release note.
  • Documentation gap: the commcare-cloud 'Sizing Buckets' page, which is supposed to give infrastructure required for 1k/2k/5k users, is an empty stub (marked nosearch, containing only the heading); per-user-band specs have never been published there, so the 5-requirements.html single-server guidance is the most specific official number available.
  • The current commcare-android master builds with minSdkVersion 23 (Android 6.0), targetSdk 36, compileSdk 37, corroborating the OS floor of 6.0. Release 2.64.0 additionally raised the minimum to Android 9 only for the separate Connect & PersonalID flows, not for the core client.
  • Official Dimagi docs: the single-server (monolith) configuration is appropriate for projects with fewer than 1,500 users (each with <10,000 active cases) and no intention of growing; suggested spec is a mid-range server CPU, at least 32 GB RAM, 2 TB SSD, with EC2 t2.2xlarge/t3.2xlarge (8 vCPU, 32 GiB) cited as the equivalent machine. A ~1,000-worker deployment sits comfortably under the 1,500 threshold, so one monolith server is the officially supported topology (micro cluster of 2 servers is only needed for growth toward 3,500).
  • Coverage gap (stated, not smoothed over): searches for a published field deployment of CommCare HQ (or ODK Central) specifically on solar/off-grid power returned no relevant results; the solar answer is a first-principles derivation from generic server power data and standard solar sizing rules, and should be treated as an estimate to validate with a local load test and site-specific peak-sun-hours measurement before procurement.
  • Dimagi's written guidance (Selecting a J2ME Phone / Android selection pages) states that as of 2016 Dimagi only recommends beginning new projects on Android phones, that most active development is on Android, and that while the Java platform is 'still supported' no new projects should begin on a feature-phone platform. A 2014 Dimagi forum statement (Clayton Sims) said there were no plans to drop Java-phone support but that the J2ME client could move into a 'maintenance mode' where core functions are kept but it does not receive new features, and that CommCare HQ/toolchain would keep supporting old mobile versions indefinitely.
  • CommCare is designed offline-first: after the initial app install and first sync, the mobile app functions offline indefinitely; completed forms are stored locally and automatically sync when a connection is available, and users can control/queue sync actions.
  • Beneficiary workflows can run entirely over SMS without a household smartphone: official documentation lists 'reaching participants who do not have smartphones' as a core CommCare Messaging use case, with SMS reminders, SMS surveys collecting data with received responses, rule/time-based schedules, conditional alerts, and IVR voice calls.
